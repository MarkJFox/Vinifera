# AF-0004H4 — Native aircraft flight space and FixedWing attack turns

FixedWing attack flight points now use the outer TS `In_Radar` playfield,
including the margin outside `In_Local_Radar`. The entire allocated cell array
is **not** native flight space. Native Fly movement rejects positions outside
the outer diamond. H4 also restores that movement-edge correction for the
FixedWing Attack mission, whose custom Process bypasses native Movement_AI.

The user's native SCRIN/Banshee comparison establishes that it can leave the
visible map during an attack and return. That observation did not record
native `In_Radar`/`In_Local_Radar` flags. Interpreting visible-map departure as
`In_Radar == false` would therefore go beyond the evidence. The code supports
departure from Local Radar while remaining inside the outer In_Radar diamond.

## Native attack, firing and return to the target

**CONFIRMED FROM NATIVE/RECONSTRUCTED CODE:** Hunt acquires a target and assigns
Attack; player Attack supplies its own target. Guard/Area Guard and idle/service
can enter other missions. Native Guard is not the FixedWing CAP rectangle.
Aircraft AI continues base Foot processing and mission dispatch. Fly::Process
calls rotation, movement, destination approach, landing/takeoff and finally
Edge_Of_World_AI; the latter is an ordinary per-frame path, not limited to
scripted transports at its call site.

The attack states reconstructed from `aircraft.cpp::Do_MISSION_ATTACK` are
VALIDATE_AZ, PICK_ATTACK_LOCATION, the obsolete TAKE_OFF slot, FLY_TO_POSITION,
FIRE_AT_TARGET, FIRE_AT_TARGET2, STRAFE_SHOT2/3/4/LAST_SHOT and RETURN_TO_BASE.
They are not the FixedWing INGRESS/PASS/EGRESS/REGROUP status values.

For SCRIN + the supplied Proton:

1. `Is_Strafe` obtains the primary weapon/projectile. Projectile ROT greater
   than 1 returns false; an invisible projectile also returns false. ROT=1
   and visible ProtonTorpedo therefore select **strafing**. This threshold is
   directly confirmed at `0x0040EF08..0x0040EF26`.
2. `Good_Fire_Location` immediately returns the target for strafing
   (`0x0040CF20..0x0040CF3C`). A non-strafing aircraft instead searches local,
   usable firing cells in rings based on Weapon_Range. These are distinct
   attack modes even with the same AircraftType.
3. FLY_TO_POSITION consumes a pending spent round, clears straight-flight lock
   and checks target and actual `TechnoClass::Ammo`. For strafing, planar target
   distance below the primary Weapon.Range enters firing; otherwise NavCom is
   assigned to the target. The binary comparison is at `0x0040BB49..0x0040BB8D`.
4. Aircraft::Can_Fire checks facing using SecondaryFacing versus target
   direction: absolute signed raw angular difference above `0x800` (11.25
   degrees) returns FIRE_FACING. It then uses Techno::Can_Fire. The latter
   checks range, rearm, ammo, cloak, legality and projectile target capability.
5. FIRE_OK enters the strafe shot sequence, sets pending ammo spending and
   straight-flight lock. Subsequent states schedule shots with the primary
   ROF. The reconstructed nominal run contains five firing opportunities;
   actual shot/bullet count still depends on range, target survival, firing
   results and normal burst handling. Do not equate five opportunities to
   five ammo units.
6. After the last strafe opportunity, the native mission returns delay
   `(primary.Range + 4 * CELL_LEPTON) / Class->MaxSpeed`, and returns to
   FLY_TO_POSITION. The binary explicitly adds `0x400` and divides by type
   MaxSpeed at `0x0040C42C..0x0040C437`. Straight flight remains locked until
   the subsequent mission processing releases it. This is a timed post-shot
   extension, not a generated off-radar egress waypoint.
7. Once unlocked, Nearing_Target steers back toward DestinationCoord/the
   target through PrimaryFacing/SecondaryFacing. Its strafe proximity/turn
   gate avoids some immediate near-target turns. The curved path arises from
   current speed, desired facing and ROT. The aircraft can cross Local Radar
   during this path without losing its target or being deleted.
8. Pending ammo is spent by the mission/AI, not the empty aircraft
   Reduce_Ammunition override. Ammo=0 leads to RETURN_TO_BASE/idle and the
   existing docking/service path. With surviving target and ammunition the
   state machine can approach/fire again.

Thus AircraftClass supplies attack mode, lock and timing; Fly destination
steering and FacingClass produce the actual turn. There is no native
FixedWing-style lateral REGROUP waypoint in this strafe chain. No generic
aircraft mechanism needs to set a turn destination outside outer In_Radar to
explain the user's visible off-map turn.

## Radar, local map, allocation and the real edge

**CONFIRMED FROM NATIVE CODE:** In_Radar(Cell) at `0x00510FB0` reads PlayRect
Width/Height. For cell x,y and width W, height H it accepts:

```text
x + y > W
x - y < W
y - x < W
x + y <= W + 2*H
```

This diamond is not the current camera viewport and not just the minimap's
visible scenario rectangle. Coord::As_Cell divides X/Y by 256 into signed-short
cell coordinates; negative or very large unvalidated coordinates must not be
treated as allocated simply because a cell conversion wrapped/truncated.

| Boundary / value | Meaning and aircraft relevance |
| --- | --- |
| Tactical camera viewport | Screen window on terrain; leaving it alone has no flight-space meaning |
| MapRect / visible scenario extent | Scenario/radar presentation dimensions; used by several native conversion/display paths |
| LocalRect / In_Local_Radar | Playable/local subregion inside PlayRect; test can include ground height and ramp adjustment. It is not a hard normal aircraft movement boundary |
| PlayRect / In_Radar | Outer isometric playfield; native Movement_AI only commits a proposed/corrected XY position inside it |
| Array, XSize/YSize | Technical allocated cell storage, including cells outside the diamond. Being in storage does not make a point native flight space |
| Actual cell lookup | Array/index validation can return the engine's invalid-cell sentinel; it must not be confused with permission to fly there |
| FixedWing Inside_Array | Existing one-cell allocation guard for Mark/adjacency safety; stricter than a raw allocation test and retained as a FixedWing precaution |
| H4 Native_Flight_Point | Nonnegative, allocated coordinate plus native In_Radar; no Local Radar requirement |

Reconstructed `map.cpp::Set_Local_Dimensions` intersects the local rectangle
with PlayRect and pulls edges inward. This explains an outer non-playable
margin, but it does not establish an unlimited or fixed-width aircraft safety
ring. Its available size depends on the scenario. The coordinate
In_Local_Radar overload's call uses the cell predicate; its ground/ramp
behavior should not be replaced by a screen-rectangle approximation.

### Native per-frame world protection

The native Movement_AI block at `0x0049A5A3..0x0049A6D2` does the following:

1. Test the proposed movement coordinate with outer In_Radar.
2. If outside, convert its cell to local-rectangle coordinates. Compare its
   local column with MapRect.Width/2 and adjust world X by +128 or -128.
3. If still outside, call native Coord_Scatter with distance 64, lock=false.
4. Commit Set_Coord only if the resulting cell is inside In_Radar. Otherwise
   retain the old position.

The binary confirms both the correction and the final conditional Set_Coord.
OpenTS `fly.cpp::Movement_AI` mirrors these branches. H4 uses the verified
Cell_To_LocalRect column formula (including odd PlayRect width), the existing
Coord_Scatter declaration and the same final rejection. This correction acts
at the **outer world edge**, not when passing the visible/local map edge.
Scatter uses the engine's simulation RNG only on the native fallback branch;
developer logging never calls it or changes selection.

Fly::Edge_Of_World_AI (`0x00499E40`) is a separate operation: outside Local
Radar it deletes a Retreat aircraft, handling cargo/team departure; inside it
marks the inherited Techno map-entry lock. It does not delete an ordinary
attacking player aircraft solely for leaving Local Radar. Aircraft::AI also
checks outside-local plus the virtual off-map deletion predicate. Native
`0x0040EF50` requires no TarCom, the inherited map-entry lock, and loaner/no-team
or leaving-team conditions. This predicate is unrelated to the aircraft's
separate straight-flight flag (TSpp unfortunately calls both fields IsLocked
in different classes).

Normal attacking Banshees consequently keep being simulated in the outer
margin, retaining target/facing/movement. Off-local is not automatic limbo or
death. True outer-world crossing is corrected/rejected, not permission for
unbounded flight. Scripted Retreat and off-map loaner cleanup remain distinct.

## FixedWing comparison and implementation

H3's hard Local Radar assumption was too strict for transient attack movement.
Its outer In_Radar check was justified. The hypothesis that **only array
bounds** matter is contradicted by native Movement_AI.

| FixedWing function / validation | Native does the same? | H4 decision |
| --- | --- | --- |
| Valid_Point / Valid_Segment: Radar AND Local, sampled every half-cell | PARTIALLY: local checks exist for firing-cell selection/landing; not for every aircraft movement point or strafe segment | Keep for target, dock and holding geometry; remove from attack flight segments |
| Inside_Array: one-cell technical margin | PARTIALLY: allocated-cell safety matters, but this exact guard is a FixedWing precaution | Retain; diagnostics now distinguish raw array and arrayGuard |
| Safe_Attack_Segment: endpoint array guard and sampled Radar+Local | NO full segment preflight in native strafe; YES outer In_Radar during actual movement | Keep existing segment preflight, sample native outer flight-space predicate instead of Local Radar |
| Find_Safe_Egress: full exit, then shorter same-axis candidate above 2*Turn_Room | NO native geometric candidate search or this minimum | Retain as a FixedWing state-machine fallback only at outer flight-space/array guard failure; no shortening merely for leaving Local Radar |
| Start_CAP_Ingress: current->ingress->target and immediate egress, then opposite direction | NO native full-runup/opposite matrix | Preserve controller and ordering, use outer flight space |
| Start_Ingress for explicit Attack | NO native FixedWing full-runup waypoint | Apply the same outer flight bounds as automatic attack |
| Start_Pass / Break_Off moving-target extension | PARTIALLY: native straight lock and target updates exist, but not these frozen pass-plane/exit coordinates | Apply outer flight bounds to both armed and positioning passes and exit extensions |
| Start_Regroup: lateral staging->next ingress->target | NO native explicit regroup waypoint | Permit off-local turn points inside outer flight space; keep ordering and distances |
| Process: custom XY/altitude transaction | PARTIALLY: preserves several native interactions but bypassed native Movement_AI world correction | Restore that correction for Attack movement before height reads and Set_Coord |
| Controlled: original engine fallback at invalid array trajectory/failure/Retreat | Existing FixedWing ownership gate, not native attack geometry | Unchanged |

The H3 decision is **C, with corrected terminology**: standard egress may leave
Local Radar, but must remain in native outer In_Radar space and the existing
array guard. Only there can the same-axis H3 shortening still be necessary for
this custom geometric controller. Its distances, minimum, descending integer
search, preferred/opposite ingress ordering and late regroup selection remain
unchanged. H4 removes the Local Radar constraint from those attack points;
it does not add distance levels, clamps, a new loop solver or edge-specific
directions.

The native movement safeguard is necessary in addition to waypoint checks:
a curved speed/ROT-limited trajectory can overshoot a valid planned segment.
If the world correction produces no XY movement, FixedWing ends that run via
its existing End_Attack/CAP-or-RTB decision. This is a **FixedWing adaptation**:
native strafe later releases its lock through the mission timer, whereas a
geometric FixedWing exit could otherwise remain unreachable at the boundary.
No new world-escape deletion or teleport to an ingress/target is introduced.

This does not make the attack state machine a copy of native TS. Full ingress
distance `R + 4*Turn_Room`, explicit regroup clearance, heading tolerance and
H3's minimum may still reject a run that native timed strafing would attempt.
Safe planned points also do not prove a whole curved future loop fits. A map
with little outer margin can still fail immediate-pass/regroup selection and
resume CAP/return. Those limitations are explicit; runtime equivalence at every
edge has not been established.

Target validation remains unchanged: live, non-self ground target and the
existing playable Radar+Local point check. Permanent CAP holding corners retain
the previous local geometry and turning clearance. Returning from a transient
off-local attack selects holding points through the existing nearest-corner
path; it does not create a permanent off-map orbit. Escort context/ownership,
dock geometry, service/reload and `[FWDOCK]` code were not edited.

## Diagnostics, layout and changed files

All H2/H3 `[FWCAP]` events remain. ATTACK_DIRECTION_PROBE, ingress/pass/regroup
segment flags now use the same attack bounds as gameplay. Every diagnostic
Point includes:

```text
radar=<outer In_Radar>
local=<In_Local_Radar, only looked up for allocated coordinates>
array=<raw coordinate lies in allocated XSize/YSize>
arrayGuard=<existing one-cell FixedWing guard>
valid=<legacy playable/holding point validity with arrayGuard>
nativeFlightValid=<allocated coordinate AND outer In_Radar>
```

An accepted off-local attack point can therefore report
`radar=true local=false array=true nativeFlightValid=true`. A point with
`radar=false local=false array=true` remains invalid for native flight.
Old H3 `array` represented the guarded test; H4 labels that separately as
`arrayGuard`, so compare old and new logs accordingly.

ATTACK_WORLD_EDGE reports proposed/accepted coordinates and whether the old
position was retained. This is only an outer-world correction observation.
Theoretical probe continuation flags still do not choose the flight route.

No new `[NATAIR]` hooks were added. Existing Aircraft AI entry tracing would
only sample pre-processing state; it cannot report the actual downstream
Can_Fire return without additional observation points. H4 therefore uses the
statically confirmed native path and extends existing FixedWing diagnostics,
as allowed by the task. A future native trace must distinguish observed
Can_Fire results from an extra speculative call to Can_Fire.

H4 changes only:

- `src/extensions/aircraft/fixedwing.cpp`: attack bounds; per-step native world
  correction and existing-run termination when pinned; matching diagnostic
  bounds/raw allocation labels and ATTACK_WORLD_EDGE; raw selected weapon
  range without the old one-cell geometry floor.
- `docs/AF-0004H4.md`: this evidence report, configuration comparison and plan.
- `docs/Whats-New.md`: an experimental H4 entry describing these changes.

No headers, native helper ABI, hook addresses/lengths, persistent fields, CRC
layout, save/load or save basis (`0x140000`) changed. H4 uses existing
`Coord_Scatter(const Coord&, unsigned, bool)` and `Coord_Move(const Coord&,

remain untouched. Pre-existing workspace modifications belong to prior work.
