# AF-0004G2 — Edge-safe FixedWing dock approach

## Confirmed runtime cause

The supplied G1 runtime capture identifies an approach geometry rejection,
not a stopped STACK search or an inventory/radio/occupancy failure.
GAHPAD 1034788 has a valid docking coordinate D=(17664,39424,104), but its
preferred facing 0 produces S=(19198,43008,104), G=(17662,43008,104) and
P=(17663,41472,104). All three approach points and sampled segments are invalid.
The finder keeps enumerating the dock; the FixedWing candidate filter rejects
it with REJECT_APPROACH_GEOMETRY. Presence deliberately does not require a
usable approach, so a visible compatible base can still be an invalid candidate.
The later dock 1034918 at D=(8960,26880,104) has valid approach geometry and is
reserved immediately. Rebuilding in a different location changed the geometry.

## One deterministic geometry path

`src/extensions/aircraft/fixedwing.cpp` keeps `Geometry()` as the sole approach
selector. Its existing coordinate construction is extracted into
`Build_Approach()`; there is no second implementation in the finder or controller.

The primary direction is unchanged: while mutually reserved, use the native
eight-way `AircraftClass::Landing_Direction()` at 0x0040EE70; otherwise use the
candidate building's `PrimaryFacing.Current().Get_Facing<8>()`. Native TS reads
the radio peer's primary facing when in contact, so both cases identify the
same building direction before and after HELLO. The native entry was checked
in `references/ts-patches/input.dat`; TSpp declares the corresponding method.

1. Build and validate the complete primary approach.
2. Return it immediately if valid; never evaluate the opposite first.
3. Otherwise rebuild with `primary + DirType(DIR_S)` and validate again.
4. Return false if that complete opposite approach is also invalid.

`DIR_S` is 128 in Dir256. `DirType` converts it to raw 0x8000, and its
unsigned 16-bit addition wraps correctly, giving exactly 180 degrees.
There is no RNG or 45/90-degree search, clamping, or shortened leg.

The unchanged construction is:

```text
back = selected direction + 180 degrees
side = selected direction + 90 degrees
P = Move(D, back, 8 cells)
G = Move(P, back, 6 cells)
S = Move(G, side, 6 cells)
```

D/S/G/P must all pass `Valid_Point()`, SG/GP/PD must pass the existing sampled
`Valid_Segment()`, and D must not be under a bridge. Existing radar/local-map
checks are retained. When both directions fail, Dock_Candidate remains false
and the existing retry/holding behavior applies.

## Candidate, flight phases and final facing

`Dock_Candidate`, both reserved and post-HELLO branches of `Find_Dock`,
`Go_Around`, `Arrived` and the controlled `Process` all use `Geometry()`.
Given unchanged map geometry, docking coordinate and building facing, every
invocation selects the same direction without storing a new aircraft field.

| Phase / check | Selected geometry / heading |
|---|---|
| Reservation / DOWNWIND entry | S from Geometry |
| DOWNWIND arrival | G from Geometry; enter CROSSWIND |
| CROSSWIND arrival | P from Geometry; enter TRAVEL |
| TRAVEL arrival | Check selected Direction; commit it to existing SecondaryFacing.Desired; target D |
| LANDING | Recompute Geometry; compare selected Direction with the saved committed heading |
| Final descent / touchdown | Use selected Direction for the descent-axis projection and heading tolerance |
| Grounded Mission_Enter service handoff | Compare PrimaryFacing with Geometry.Direction before the existing IM_IN |

Movement still steers PrimaryFacing toward the selected goals. The fallback
does not rotate the building, override native Landing_Direction, or change
VTOL behavior. Native `Process_Landing` at 0x0049B360 remains the touchdown
bookkeeping call; it does not choose the approach direction. The existing
go-around routines and transitions are retained; their heading comparisons now
refer to the selected approach instead of incorrectly requiring primary.
Normal docks with a valid primary retain their original coordinates and heading.

## G1 diagnosis retained and corrected

The deduplicated candidate geometry snapshot includes the primary and selected
eight-way facings, selected raw heading and complete selected coordinates.
It reports one of:

- `APPROACH_PRIMARY_VALID`
- `APPROACH_PRIMARY_INVALID_FALLBACK_OPPOSITE APPROACH_OPPOSITE_VALID`
- `APPROACH_PRIMARY_INVALID_FALLBACK_OPPOSITE APPROACH_OPPOSITE_INVALID`

No logging is added to the per-frame geometry selector. Existing snapshot
deduplication and 15-tick observation/search throttles remain in effect.

The false `REJECT_RADIO_CAN_LOAD` event has a separate, confirmed cause.
`TechnoClassExtension_Hooks` patches the call at 0x00637FF5 to
`TechnoClassExt::_Cell_Distance_Squared`, bypassing G1's PASS observation at
the original Relative_Distance entry 0x00586CC0. Native code requires ROGER
at 0x00637FED/0x00637FF0 before the distance call; best selection at 0x0063800D
therefore proves success. At the common join 0x00638013, EAX can already be
a squared cell distance, not the original radio reply.

The diagnostic condition now gives `Progress.Best` priority and reports
`NATIVE_ACCEPTED_SO_FAR`. A separately observed PASS without best selection
still reports `NATIVE_NOT_BEST_DISTANCE_PRIORITY`. If neither success marker
was observed after CAN_LOAD began, the event is
`NATIVE_CAN_LOAD_OUTCOME_UNCONFIRMED`, with raw EAX for context. An absent
marker alone is not proof of rejection; non-best success and actual rejection
cannot reliably be distinguished at that join without further instrumentation.
No hooks, native comparisons, radio calls or distance calculations were changed.

## Completion transition: analysis only

`Dock_Exists` requires an active, living, non-limbo, own compatible reload/repair
building, a valid docking coordinate, no current Construction/Deconstruction
mission and no construction BState. It does not inspect MissionQueue,
QueueBState, IsReadyToCommence or HasOpened. Consequently the reported
ready=false/opened=false snapshot still counts as presence if those existing
predicates pass.

The static TS path supports a placement/mission-transition window:

- `Enter_Idle_Mode` at 0x00433300 begins construction for normal player placement
  and requests MISSION_CONSTRUCTION through Assign_Mission.
- Assign_Mission at 0x00559490 writes MissionQueue; it does not immediately
  replace CurrentMission. Animation state can also have a queued transition.
- Mission_Construction at 0x004304A0 starts the construction mode, then waits
  for IsReadyToCommence. Completion sends COMPLETE and OVER_OUT, begins idle,
  calls virtual Grand_Opening, queues GUARD and sets the final facing.
- Grand_Opening at 0x0042E170 sets IsReadyToCommence at 0x0042E4C0 and HasOpened
  at 0x0042E4DA. Building AI clears IsReadyToCommence after a successful
  Commence (0x00429AC3 and 0x00429B28). It is a transition flag, not a permanent
  "building finished" bit; requiring it would exclude completed buildings.

The exact entry into the particular logged intermediate snapshot cannot be
established from ready/opened alone. Under the reported brief transition, an
active no-dock counter is reset to zero, then starts a fresh 2700-tick grace
period when Construction becomes visible. This can extend the deadline once
for that transition; it does not explain the persistent approach rejection.
Repeated qualifying presence transitions would cause repeated resets under
the existing G semantics, so this is not claimed to be universally one frame.

HasOpened is the more relevant potential completion-history guard; checking
queued construction is another possible way to exclude pending placement.
Neither is added here: their treatment of preplaced/revealed/captured/loaded
buildings needs separate evidence and review. No presence fix is proposed as
established from this trace, and no timer/eligibility change is mixed into G2.

## Scope, persistence and validation

No new persistent field or save-version change is needed. `Approach.PrimaryValid`
is only a local diagnostic result; the existing SecondaryFacing.Desired already
stores the committed final heading and survives save/load. Save basis remains
**0x130000**; no extension size or CRC layout changes.

Holding, 15-tick dock retry, radio reservation, survival countdown, attack runs,
dynamic landing speed, go-around mechanics, Ammo, Move/Stop, native service/reload
and FixedWing=no remain unchanged. Reference repositories are read-only.

Changed in G2: `src/extensions/aircraft/fixedwing.cpp`, `docs/AF-0004G2.md`,
the G1 diagnosis notes in `docs/AF-0004G1.md`, and `docs/Whats-New.md`.
Validation is limited to git diff --check, git status and diff review, including
the existing untracked FixedWing source. No build, tests, commit or push.
