# AF-0004H5A — Preserve the clicked Escort object through the mission event

The two existing FixedWing click hooks used reversed native entry addresses.
The native Object entry is **0x0040B690**, and the native Cell entry is
**0x0040B740**. H5A assigns each hook to the correct entry and instruction
length. Object Guard Area clicks can then use the existing synchronized
object-target pipeline into Begin_CAP.

There is no new event, target field, hotkey, pointer side channel or cell-to-unit
lookup. Begin_CAP, Escort tracking and the H4 attack controller are unchanged.
Runtime success remains to be checked locally; no build or tests were run.

## Runtime evidence and root cause

The supplied H4 trace showed an own-unit CTRL+ALT click producing:

```text
COMMAND_QUEUED source=UI_CELL_GUARD_AREA actualTarget=kind=CELL
COMMAND_RECEIVED newMission=10 target(kind=11,...) resolved kind=CELL
targetPayload=CELL_ONLY_NO_OBJECT_RECONSTRUCTION
CAP_SET_STATIC CAPAnchor=(40064,20352,0) CAPEscort=NULL
```

The trace had no CAP_SET_ESCORT, ESCORT_STATE or ESCORT_CENTER_UPDATE. The
aircraft flew to the transmitted static anchor because no Escort context had
been created. That behavior does not require a tracking or detach failure.

The source label UI_CELL_GUARD_AREA identified **which FixedWing callback ran**,
not which native overload was actually entered. Before H5A, that callback was
installed on the native Object entry. Its
`GET_STACK(Cell*, cell, 0x8)` interpreted an ObjectClass pointer as a pointer to
two signed-short cell coordinates. `&Map[*cell]` then converted those unrelated
object bytes into a CellClass target. Object identity was lost **there, before
Player_Assign_Mission and before event construction**.

The object pointer was the real click parameter, not a temporary Cell or a
reconstructed screen target. The original object was not intentionally reduced
to its position by the UI or the event constructor.

### Native evidence, including the misleading TSpp labels

Addresses and instructions below were inspected in
`C:/dev/Aftermath-Engine/references/ts-patches/input.dat` with MSVC dumpbin.
The OpenTS reconstruction was used to interpret the matching paths. Reference
repositories and the working TSpp bindings were not edited.

| Native entry | Binary evidence | Before H5A | After H5A |
| --- | --- | --- | --- |
| `0x0040B690`, Aircraft Object click | Calls object What_Action through vtable `+0x74` with object and bool; handles TOTE/ENTER/SELF and delegates to `0x004A2EB0` | Cell callback, length 5, reads the object as `Cell*` | Object callback, length 5, reads `ObjectClass*` |
| `0x0040B740`, Aircraft Cell click | Forwards its three arguments directly to `0x004A35A0` | Object callback, length 8, could cast a real `Cell*` as an Object pointer | Cell callback, length 8, reads `Cell*` representing the Cell reference |
| `0x004A2EB0`, Foot Object click | Uses the target's virtual RTTI; Guard Area forwards the object to Player_Assign_Mission at `0x004A2F6A..0x004A2F73` | TSpp labels it as the Cell overload | No binding change; native evidence determines H5A hooks |
| `0x004A35A0`, Foot Cell click | Re-evaluates cell What_Action with three arguments and calls In_Local_Radar; Guard Area uses Map[cell] | TSpp labels it as the Object overload | No binding change |

`TSpp/src/tspp/tspp_definitions.cpp` currently associates both Aircraft and
Foot Active_Click_With overload names with the opposite addresses. The prior
H/H2 hook assignments and H2 documentation followed those labels. This H5A
report supersedes that address mapping; the binary argument use and forwarding
calls establish the corrected mapping independently.

OpenTS `code/aircraft.cpp::Active_Click_With(ObjectClass*,...)` re-evaluates
object action, handles aircraft-specific TOTE/ENTER/SELF, then delegates to
Foot. Its Cell overload simply delegates to Foot. OpenTS
`code/foot.cpp::Active_Click_With(ObjectClass*,...)` already supports
ACTION_GUARD_AREA with the clicked object as the mission target. These are
reconstructed sources; the entry classification above is binary-confirmed.

### Hook instruction and ABI contracts

The hook count remains unchanged. Only the assignment of the two existing
callbacks to their native entries changes:

| Callback | Old address / length | Correct address / length | Complete displaced instructions |
| --- | --- | --- | --- |
| `_Aircraft_GuardClickObject_FixedWing` | `0x0040B740` / 8 | `0x0040B690` / 5 | `55` push ebp; `8B 6C 24 10` mov ebp,[esp+10h] |
| `_Aircraft_GuardClickCell_FixedWing` | `0x0040B690` / 5 | `0x0040B740` / 8 | `8B 44 24 0C` mov eax,[esp+0Ch]; `8B 54 24 08` mov edx,[esp+8] |

Both are entry hooks before displaced instructions. ECX is AircraftClass*;
original stack +4 is ActionType, +8 the Object pointer or Cell-reference
pointer respectively, and +0xC the bool argument. Both native methods return
bool with `ret 0Ch`. The existing handled path sets EAX=true and uses
FixedWing_Return12. Return 0 keeps the existing Syringe displaced-instruction
path. Neither displaced region contains a relative branch or call.

The FixedWing/action/movement-permission gates remain intact. Non-FixedWing
aircraft and other actions return to native processing; no shared action
selection, cursor behavior or modifier interpretation was changed.

## UI and synchronized target transport

CTRL+ALT means the configured force-attack and force-move modifiers. In the
reconstructed `techno.cpp::What_Action(ObjectClass*, bool)`, the combination
returns ACTION_GUARD_AREA for player-controlled movable objects. The current
`AircraftClassExt::_What_Action` delegates through Foot and retains that action.
`mouseext_hooks.cpp::Get_Action` chooses the object overload when a mouse
object exists; its attack-cursor customization does not discard Guard Area
objects.

OpenTS `display.cpp::Mouse_Left_Release` passes the clicked object and cell to
`DisplayClass::Active_Click`. With an object, Active_Click loops through the
selection, re-evaluates What_Action for each selected object and invokes its
Object click overload. Without an object, it invokes Cell paths. Both object
and cell are available at the display level; native dispatch preserves the
object when one was clicked. Hidden-object filtering can leave no UI object;
H5A does not override visibility or reconstruct such a target.

| Stage | Before H5A object click | After H5A object click |
| --- | --- | --- |
| UI / action selection | Actual clicked ObjectClass*, plus clicked cell; Guard Area | Same |
| Aircraft click entry | Native Object entry `0x0040B690` | Same native entry |
| FixedWing callback interpretation | Mistaken Cell* -> Map[unrelated object bytes] | Actual ObjectClass* -> existing own-Techno gate |
| Player_Assign_Mission input | GuardArea, wrong CellClass*, destination=null | GuardArea, clicked ObjectClass*, destination=null |
| Event Target | RTTI_CELL=11, encoded cell | RTTI_ABSTRACT=52, object's Fetch_ID/UID |
| Synchronized reconstruction | As_Abstract resolves the transmitted cell | As_Abstract resolves the UID through the native target tracker |
| FixedWing::Command input | Resolved CellClass* | Resolved clicked Techno as AbstractClass* |
| Begin_CAP input / result | Cell -> Static, CAPEscort=null | Own valid Techno -> Escort, CAPEscort=that exact object |

The event's raw kind need not equal the target's concrete Unit/Infantry/etc.
RTTI. For a normal Techno, the native constructor uses **RTTI_ABSTRACT=52**;
COMMAND_RECEIVED then reports its resolved reference as **TECHNO_OBJECT**, with
the concrete RTTI, UID, heap ID, owner and coordinate.

The native transport was already sufficient:

- AircraftClass::Player_Assign_Mission at `0x0040B760` receives mission, target,
  destination, constructs separate TargetClass values and calls Queue_Mission
  at `0x005B0FC0`. Target is the second source-level argument; Destination is
  the third. A null destination for Guard Area is intentional.
- TargetClass(AbstractClass*) at `0x0061FEE0` distinguishes cells from other
  objects. Cells use kind 11 and value `cell.X + 1000*cell.Y`. Other objects
  use kind 52 and their native Fetch_ID. Null produces kind/value zero.
- Queue_Mission constructs native EVENT_MEGAMISSION (type 4) via
  EventClass's constructor at `0x00493FA0`. It copies Whom, Mission, Target and
  Destination without an Object-to-Cell conversion. MEGAMISSION_F retains
  that prefix and adds formation speed fields. Existing compression and event
  payload lengths remain unchanged.
- In the native EventClass layout, Whom starts at +0x0A, Mission at +0x12,
  Target at +0x16 and Destination at +0x1E. Target and Destination each contain
  Kind and Value. No raw pointer is stored in these fields.
- The unchanged accepted-event hook `0x004948A5` (length 6) receives ESI=event,
  EDI=controlled techno, EAX=mission. Trace_CAP_Command reads the payload;
  FixedWing::Command receives `MegaMission.Target.As_Abstract()`.
- As_Abstract at `0x00620290` resolves kind 52 through the native ID tracker.
  Its cell branch decodes the cell value and calls Map's cell lookup. The
  native Guard Area event branch at `0x004948E5` also resolves the actual target
  for destination/archive handling. Existing FixedWing Assign_Destination
  preserves the explicit CAP context already captured by Command.

Attack and Enter use the same native target representation; which field a
mission uses differs. Native object Guard Area already places the object in
Target. No new command or semantically unrelated mission is required.

### Why the local and accepted cell coordinates were misleading

Before H5A, COMMAND_QUEUED logged `Ref(&Map[*cell])`, not the original click
object. The Map lookup at `0x0050F280` flattens signed-short cell coordinates
as `x + 512*y`; it can alias a real allocated cell or return the shared
BlubCell scratch reference. Invalid lookups overwrite BlubCell.CellID.
TargetClass then encodes a cell using the different base-1000 formula, and
As_Abstract decodes and looks it up again. Invalid x/y inputs and the mutable
scratch cell therefore cannot be interpreted as stable click coordinates.

The exact numeric transformation to the supplied `(40064,20352,0)` is not
claimed without the original pointer bytes and full matching payload trace.
What is confirmed is that object identity had already been replaced by a bad
cell lookup before either log/event. The plausible accepted cell is not
evidence that event serialization discarded a previously correct object.

After H5A, the Object callback never performs that Map lookup: it logs and
passes the correctly typed clicked object directly. The Cell callback receives
an actual Cell reference. COMMAND_QUEUED remains an observation before the
native enqueue operation, not proof that the outgoing queue accepted an event;
COMMAND_RECEIVED remains the accepted synchronized evidence.

## Escort semantics, ownership, lifetime and determinism

The object callback retains its existing same-House Techno gate. Begin_CAP
retains its active, alive, non-limbo, own-House checks. A non-self Techno enters
Escort; self does not become an Escort target and follows the existing static
branch. The design accepts Techno generally, including Unit, Infantry,
Building and Aircraft, with no new Unit-only restriction or allied-House
extension. Enemy/other-House clicks retain native fallthrough and cannot pass
Begin_CAP's own-House Escort validation.

Only accepted synchronized events create/replace CAP. The UI callback queues
the normal mission and never writes CAPEscort or CAPMode. All participants
resolve the same UID using engine target tracking; no screen-coordinate
reconstruction, local object search or singleplayer special case is introduced.
The existing event ownership checks remain before accepted command handling.
Each selected FixedWing queues the same clicked target through its ordinary
Whom field; other selected types keep their native behavior.

If a target disappears before execution, native ID resolution may return null;
the existing Begin_CAP null/static behavior remains. If an active Escort is
destroyed/detached, existing On_Detach clears CAPEscort before later AI checks
take the existing invalid/return path. H5A adds no retained UI pointer or new
lifetime state. Center sampling remains CAPEscort->Center_Coord() at the
existing CAP-leg selection points; current legs are not continuously rebuilt.

AircraftClassExtension::Save still uses the inherited blob, Load still requests
CAPEscort swizzling, and CRC still includes the Escort's ID. The current
global save basis was checked in `src/extensions/extension.cpp`: **0x140000**.
H5A changes neither that value nor any persistent field/layout.

## Logging and expected validation

Existing developer-only COMMAND_QUEUED, COMMAND_RECEIVED, CAP_SET_ESCORT,
ESCORT_STATE and CAP_GEOMETRY messages remain. Their existing Ref/State
formatters include actual target kind/RTTI/UID/owner/coordinate, CAPMode,
CAPOwner and CAPEscort. ESCORT_STATE now also reports escortValid using the
existing CAP_Valid predicate, plus the last selected effective geometry center
(or UNSELECTED before its first leg). The current Escort coordinate remains
in the CAPEscort reference. The repaired Object callback now correctly emits
UI_OBJECT_GUARD_AREA for a handled own-Techno
click. No additional gameplay hook is needed for logging.

Another diagnostic-only adjustment gates ESCORT_CENTER_UPDATE on the first center
selection or a changed effective geometry center (`!HaveCenter || Center !=
used`). An unchanged center at another corner no longer emits a center-update
event. CAP_GEOMETRY still describes each chosen leg; center sampling and all
gameplay decisions are untouched.

Expected sequence for a valid own-Techno click, not an H5A runtime result:

```text
COMMAND_QUEUED source=UI_OBJECT_GUARD_AREA actualTarget=[kind=TECHNO_OBJECT,uid=U,...]
COMMAND_RECEIVED target(kind=52,value=U,resolved=[kind=TECHNO_OBJECT,uid=U,...])
                 targetPayload=OBJECT_OR_OTHER_REFERENCE
CAP_SET_ESCORT actualBeginTarget=[kind=TECHNO_OBJECT,uid=U,...]
              state: CAPMode=2 CAPEscort=[uid=U,...] CAPOwner=<aircraft owner>
ESCORT_STATE
CAP_GEOMETRY requestedCenter=<escort center>
ESCORT_CENTER_UPDATE <on first selection or changed effective center>
```

The conceptual example abbreviates the actual formatter output. Static Cell
commands still encode kind 11 and produce CAP_SET_STATIC. G uses its existing
keyboard command path and does not traverse these mouse hooks.

## Scope and handoff checks

`docs/Whats-New.md`. Source changes are the two existing hook address/length
assignments, their explanatory comment, the diagnostic validity/center fields
and the center-update gate. CAP_Valid gains a forward declaration solely for
the diagnostic call; its implementation is unchanged.

H4/autoattack, INITIAL/INGRESS/PASS/EGRESS/REGROUP, Find_Safe_Egress,
