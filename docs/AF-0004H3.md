# AF-0004H3 — Safe dynamic CAP egress near map boundaries

H3 implements only immediate-pass egress adaptation and a two-direction ingress
fallback. It does not implement the superseded full future-loop scale/candidate
matrix. This increment was statically reviewed; no build or tests were run.

## Confirmed H2 result supplied by the user

In the map center, H2 already executed repeated armed passes with alternating
raw directions approximately 20074, 52358, 20070 and 52318. The existing
INITIAL -> INGRESS -> ATTACK_PASS -> EGRESS -> REGROUP -> INGRESS controller
therefore supports counter passes. Acquisition, ammunition spending and RTB
also worked in that local test.

Near the lower boundary, direction A could have a valid ingress/target but an
invalid standard exit; B could have a valid exit but an invalid ingress.
For example, target Y was approximately 45248 and a requested standard exit
Y approximately 50539. Rejecting that exit rejected the whole armed pass,
followed by CAP resume, reacquisition and another attempt. These coordinates
are the supplied H2 observation, not an H3 runtime measurement.

The old Start_Pass required the full standard target-to-exit distance. There
was no gameplay full-loop precheck in H2: its chainValid was observational.
H3 preserves that separation and makes it explicit in the trace.

## Distances and minimum

All distances are leptons; CELL_LEPTON is 256. Let R be the unchanged existing
Attack_Range and U be the unchanged Turn_Room:

```text
rot = max(1, PrimaryFacing.ROT.Get_Dir())
U = max(128, ceil(max(1, Full_Speed) * 256 / (6 * rot)))
standard egress = max(4 * U, R + 2 * U)     // unchanged
minimum safe egress = 2 * U                // H3
ingress runup = R + 4 * U                  // unchanged
search step = 1 lepton
```

Full_Speed already includes the existing aircraft/House speed bias and FASTER
handling. Minimum therefore follows existing Speed/ROT behavior rather than a
new fixed range. Two turn-room units are also the existing straight beyond-
ingress separation used in REGROUP. This gives a real straight post-target
distance of at least one cell, versus the half-cell ARRIVAL tolerance, without
requiring the full standard four-turn-room exit or the whole future turn.
R still controls the normal standard distance; the firing window/range is not
changed. This is a simple safety floor, not a simulation of a future curved
turn or a guarantee that regroup will succeed.

For illustration only: U=1024 and R=1536 produce standard=4096, minimum=2048
leptons (16 versus 8 cells). Actual values must be read from each aircraft's
trace; no hardcoded values from the supplied map are used.

The quantized selected coordinate must also have squared XY distance from the
pass plane >= minimum squared. Thus coordinate rounding cannot accept an
actual sub-minimum point even if its nominal Coord_Move distance equals the
minimum. Logged selectedDistance is the nominal integer Coord_Move argument.

## Small helper and deterministic search

Find_Safe_Egress takes the immediate pass start, target/pass plane, unchanged
DirType attack direction, standard distance and minimum distance. Its output
EgressSelection is a stack-local value, not extension or save state.

1. Construct requested exit with the existing Coord_Move(plane,direction,standard).
2. Validate start->plane with the attack-only Safe_Attack_Segment wrapper.
3. Validate requested exit, actual minimum distance, plane->exit and start->exit.
4. If valid, return the exact requested coordinate and original distance.
   No shortening or new direction heuristic is applied to this successful path.
5. Otherwise try standard-1, standard-2, ... down to minimum, using the same
   Coord_Move direction every time. Return the first fully valid candidate.
6. If none qualifies, return failure without writing any aircraft/Fly field.

Descending one-lepton search deliberately verifies the greatest integer-distance
candidate rather than returning the first coarse cell step or assuming a
monotone boundary for binary search. Existing local-radar/terrain and sampled
segment validity can be quantized; no monotonicity assumption is needed.
There are at most standard-minimum candidate retries, only on a failed standard
exit. No internal candidate is logged and there is no scale matrix or future
regroup candidate search in this helper.

Safe_Attack_Segment combines the existing allocated-array guard with the
existing Valid_Segment (half-cell sampling, Radar and Local Radar). The array
guard is a convex rectangle, so guarding both endpoints also guards the
interpolated segment against allocated-array escape. Existing dock/holding
validation helpers are not modified. No X/Y coordinate clamp, validation
bypass, off-map allowance, RNG or time-dependent selection is introduced.
Integer Coord_Move quantization is retained along the same direction.
Diagnostic point formatting also guards Local Radar/valid-point reads with
the array margin before inspecting theoretical out-of-array candidates.

## Direction selection and committing a pass

Only an existing CAP parent context enables H3 gameplay adaptation. Explicit
manual Attack clears that context through the existing command path and keeps
its previous standard attack geometry.

Before starting each new CAP ingress, Start_CAP_Ingress first tries the existing
preferred direction. Ingress distance remains R+4U. It requires current->ingress
and ingress->target to be safe, and checks an immediate safe egress from that
ingress/target geometry. If it fails, it tries exactly the opposite direction
with the same original ingress distance. There is no shortened ingress.
The first safe direction wins; the opposite is not preferred merely to enforce
alternation. NEXT_INGRESS_SELECTED reports rejected/accepted attempts and the
opposite-after-preferred-failure reason. If neither works, the existing caller
ends the attack and resumes CAP (or returns for ammunition).

When the actual alignment reaches Start_Pass, Find_Safe_Egress runs again from
the actual current aircraft position to the current target. This accounts for
movement since ingress planning. No preliminary exit was committed or saved.
If that actual commit fails, CAP tries a fresh full ingress with the opposite
direction preferred, through the same two-direction helper. Failure to establish
a safe new ingress uses the existing clean attack-end path. It does not suddenly
reverse an armed pass at the target: a new attempt must first fly its ingress
and satisfy the existing alignment checks. Manual Attack keeps its original
failure/end behavior.

On success the existing fields are written exactly as before:

```text
Fly.HeadToCoord = target / frozen pass plane
Fly.DestinationCoord = selected safe exit
NavCom = TarCom
Status = ATTACK_PASS
```

There is no adaptive search, axis reversal or shortening during a committed
pass/egress. The existing one-time forward moving-target extension at Break_Off
is retained on the same axis with safe segments; it requires real positive
along-track target movement for a CAP pass, and keeps the previous exit when
extension is unsafe. It cannot restore a shortened exit to standard length for
an unchanged static target. Pass-plane semantics and target-motion behavior
otherwise remain the existing E/H2 mechanism.

The initial close-range Break_Off positioning path is explicitly excluded from
adaptive armed-pass selection. It still uses its old standard straight exit
and then EGRESS/REGROUP. H3 does not force an immediate armed pass on acquisition.

## Pass validity versus continuation

PASS_COMMITTED is blocked by:

- Existing invalid/lost target, weapon/range/ammunition and alignment conditions.
- Invalid or unreachable ingress when selecting a new direction.
- Invalid actual start/target prefix when committing the armed pass.
- No valid same-axis exit meeting the safe minimum, including all endpoint,
  Radar/Local/Array and immediate segment checks.

It is **not** blocked by hypothetical nextIngress, turnRight, turnLeft, staging,
full future REGROUP or next counter-pass validity. No such field is read by
the immediate-pass selection helper.

The committed exit plane must be reached by the existing Attack_Arrived logic
before Start_Regroup is called. Start_Regroup is unchanged: it reads the actual
aircraft position and current target and tries its existing E/W lateral staging
candidates and their segments. No adaptive regroup distances are added.

If regroup succeeds and target/ammo remain valid, continue through the existing
next ingress. If it fails, End_Attack resumes CAP. A safe shortened single pass
followed by CAP resume is an intentional successful outcome. Near an extreme
boundary, same-direction repetition or CAP resume is preferable to forcing an
unsafe counter pass. In the center, the preferred existing alternating direction
continues to win with its unchanged standard coordinates and distances.

## Logging

All H2 event names remain available, including command/escort lifetime, geometry,
acquisition, pass, egress, regroup, ingress, breakoff, alignment rejection and
resume. No [FWDOCK] implementation, call or hook is changed.

New ATTACK_EGRESS_ADJUSTED is emitted only after an actual armed-pass commit
selected a shorter exit. It records sequence, next committed run number,
directionRaw, pass plane, requested/selected exits and distances, minimum,
requested/selected validity and segment validity. Standard-success passes do
not emit it. Successful provisional shortening during ingress preflight and
read-only direction probes do not emit it either.

ATTACK_EGRESS_UNAVAILABLE records an actual failed egress search, stage
INGRESS_PREFLIGHT or PASS_COMMIT, requested exit, minimum candidate and reason
NO_SAFE_EGRESS (or INVALID_PASS_APPROACH for an invalid prefix). If preflight
then finds a safe opposite direction, it may continue; rejected directions are
not a claim that the entire sequence ended. ATTACK_PASS_REJECTED records
NO_SAFE_EGRESS/NO_VALID_INGRESS/INVALID_PASS_APPROACH. A failed actual commit
may be followed by a newly validated full ingress; only when no safe new
ingress is available does the existing abort/resume path end the sequence.

ATTACK_DIRECTION_PROBE still shows theoretical ingress, standard requested exit,
selected immediate exit, next ingress and both turn-out points. It now separates:

- passValid: current ingress reachability plus immediate safe target/exit geometry.
- continuationValid: later next-ingress/staging segments from the selected exit.
- chainValid: their combined diagnostic result, never a gameplay decision.

The selected candidate is computed with the same pure Find_Safe_Egress helper;
these probes do not write it into Fly fields or emit adjustment events. H2's
labels remain relative to each attempt; compare raw directions and sequence/run
identifiers. No per-distance or per-frame logging loop is added.
