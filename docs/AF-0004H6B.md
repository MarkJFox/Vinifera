# AF-0004H6B — Native TS attack as the only FixedWing attack controller

FixedWing now delegates every Attack mission to the complete native Aircraft
attack mission and Fly process. The former custom attack planner and its
diagnostics are removed. FixedWing keeps its takeoff, Move, landing, docking,
service/reload, no-dock survival, Holding/CAP, Escort and target acquisition.

The user confirmed H6A at runtime: a docked FixedWing retained the transmitted
object target, took off with the FixedWing controller, attacked the known map
edge target repeatedly, turned through native Facing/ROT, consumed Ammo from
5 to 0, selected MISSION_ENTER and successfully handed off to FixedWing dock
search, approach and landing. This is **user-supplied H6A evidence**, not a
Codex H6B runtime result. H6B itself has not been built or runtime-tested here.

## Architecture and retained native handoff

Before H6B, manual human object attacks used the H6A bypass, while CAP and
other attacks could still use CAP_TO_E -> INGRESS -> ATTACK_PASS -> EGRESS ->
REGROUP/TURNBACK. Both paths shared Aircraft Status and Fly coordinates, but
implemented separate attack movement and firing controllers.

After H6B there is one attack path:

```text
manual / CAP / Escort / AI / team / script / other native Attack assignment
  -> AttackControl NativePending
  -> initialize native Status=0 and native navigation once
  -> NativeTakeoff when FixedWing startup is still necessary
  -> Native: full Aircraft::Mission_Attack + full Fly::Process
  -> native Idle/end decision and actual mission change
       no CAP parent: preserve native outcome; adapt Enter to FixedWing landing
       valid CAP parent, Ammo != 0: resume its current CAP/escort context
       valid CAP parent, Ammo == 0: existing Return/service/reload path
       invalid parent: existing cancel/return path after Attack ends
       explicit replacement: new command wins; no old parent resurrection
```

No FixedWing path calls Can_Fire or Fire_At, modifies ammo, selects an attack
axis, creates a pass plane or plans a later regroup. Is_Strafe, weapon range,
ROF, projectile behavior, target movement, post-shot extension and repeated
passes belong to native TS, including the ordinary Vinifera patches already
present inside the native functions. There are no Proton/TESTPLANE special
cases and no PlayerPtr-controlled simulation decisions.

H6A's proved adapters remain: native Status=0 startup, original Aircraft
Assign_Destination(TarCom), original stop/destination/Idle processing while
native owns the attack, custom takeoff, full native mission/Fly release and
clean Return-to-FixedWing landing. Human-only, manual-only, Object-only and
the parallel custom-controller fallback are removed.

Update_Native_Attack detects both a queued Attack and a current Attack without
a queued replacement. It runs from existing Aircraft AI, Fly Process and
mission/destination entry hooks. Thus AI/script/team orders do not need to pass
through the player event hook. A queued Move/Guard/Enter replacement is never
re-enrolled merely because the previous current mission is still Attack.

Command still handles accepted synchronized explicit orders: cancel the old
CAP, reset ownership and either mark a new native Attack or create the new
Guard/GuardArea context. It never reconstructs an object from a cell. The
original event subsequently installs the actual TarCom. An initial empty
destination is consumed once, as in H6A; native navigation is primed through
the original Aircraft destination method, including dock wake/radio release.
Later native destination writes do not reset mission Status.

## Ownership and actual completion

The existing saved enum field AttackControl is retained. Its original numeric
values remain Custom=0, NativePending=1, NativeTakeoff=2 and Native=3. The
additional value NativeEnding=4 records a native Idle decision using the same
enum storage; it is not another attack flight phase.

| Ownership | Responsibility |
| --- | --- |
| Custom | FixedWing non-Attack missions |
| NativePending | Accepted/detected Attack; initialize native mission/navigation once |
| NativeTakeoff | Existing FixedWing forward takeoff/climb; no custom attack planning or firing; native mission temporarily delayed |
| Native | Entire native Mission_Attack and Fly::Process; custom Process declines ownership |
| NativeEnding | Native Idle has been reached; native still owns movement until its chosen mission actually changes |

The existing Idle hook at 0x0040B35A observes native completion by marking
NativeEnding. It does not choose the next mission there, short-circuit native
Idle or resume CAP before the original body returns. Once the mission has
actually left Attack, Update_Native_Attack evaluates the parent. If native
Idle retains Attack without a queued change, ownership returns to Native.

This distinguishes native completion from an AI/script Move replacing Attack:
the latter cancels the old parent instead of being overwritten by CAP resume.
The existing native suspended-mission restore bypasses the Idle observation
point; restoration of the same saved parent Guard/GuardArea mission is also
accepted as completion. Explicit synchronized commands already cancel that
parent and cannot be mistaken for a resume.

Neither Native nor NativeEnding enters custom physical movement. If the
existing custom Process commences a new airborne Attack before moving, it
re-enters Fly::Process only after ownership has switched; the existing entry
hook then falls through to the original native body. That bounded re-entry
runs one movement transaction, not native plus custom movement in a frame.
Takeoff completion at the end of an already performed custom step releases
the native controller for the next frame.

All old custom AttackStatus values and interpretations are gone. Native
Status 3/4/6/etc. are never interpreted as old INGRESS/PASS/EGRESS/REGROUP.
Mission Status and timer initialize only at handoff/takeoff release, not every
native frame. Native mission delays and straight-flight lock remain native.

## CAP, Escort and service

CAP search still uses Target_Something_Nearby, Threat_Range and the existing
CAP area/target validity checks. It only selects an enemy and assigns native
MISSION_ATTACK. It does not select an ingress or require a safe future loop.
The previous acquisition-only weapon-range flight-planner gate is removed;
the existing armed/Ammo checks and native acquisition/attack legality remain.

CAPMode, CAPMission, CAPOwner, CAPAnchor and the existing saved/swizzled
CAPEscort distinguish normal, Static CAP and Escort origins. No separate
persistent attack-origin field or new pointer is needed. CAPRearming retains
the established service/resume state. Diagnostic origin strings are not read
by gameplay.

During native Attack, CAP_AI does not change TarCom, enforce the old attack
area leash, fly CAP legs or abort because Escort was destroyed. Native TS
decides target loss and attack ending. Detach still clears CAPEscort safely;
after actual completion the existing validity/ESCORT_INVALID/ESCORT_ABORT_RTB
path handles a lost, dead or changed-owner Escort.

On completion with a valid parent and remaining ammunition, Resume_CAP clears
old attack navigation, restores the saved Guard mission and selects a new leg
through the existing CAP flight code. Escort center selection reads the
Escort's **current** position, not a frozen attack-time location. Native
reload/service state is not entered just to resume a valid CAP.

The resume adapter uses the existing DOCK_RETRY / TICKS_PER_SECOND scan cadence
for the next target search. CAP flight and corner progression continue each
frame; CAP_Leg does not reset that timer. If completion is handled at the Enter
entry, that hook returns the same cadence instead of running a stale Enter
body after CAP was restored. This avoids immediate next-frame reacquisition
without a new long cooldown, target blacklist or adjacent-unit search.

At Ammo=0 CAP does not resume. Native TS completes its own Attack/Return
decision; the adapter sets the existing CAPRearming state and hands Enter to
the unchanged FixedWing approach/service path. Native Idle's no-dock Move
fallback is routed into CAP's established Return/Holding path after completion.
After full reload the already established Resume_After_Service behavior may
resume CAP; the former attack target is not restored. A subsequent enemy is
found only by ordinary CAP acquisition. Unlimited negative ammo retains the
existing nonzero-ammo semantics; no new ammo accounting is introduced.

## Command priority

| Explicit order | Effect on an existing CAP/native attack |
| --- | --- |
| Attack, including a new airborne target | Cancel prior CAP, initialize a new native attack with the exact transmitted target; no fresh takeoff at cruise altitude |
| Move/QMove | Cancel prior CAP/ownership; the queued replacement blocks automatic Attack enrollment and existing FixedWing Move takes over |
| Guard | Replace old parent with the new explicit Static CAP context |
| GuardArea | Replace old parent using the existing cell/static or own-object/Escort semantics |
| Enter/Return | Cancel prior parent and use the existing Return/landing adapter |
| Existing Stop/IDLE event | Existing CAP cancellation remains; Request_Return now explicitly releases attack ownership before custom return movement |

H5A Object 0x0040B690/5 and Cell 0x0040B740/8 hooks, EventClass transport,
kind-52 object UID encoding, swizzling and accepted-command ownership checks
are unchanged. No new click/UI hook, raw-pointer transport or cell-to-unit
search was added.

## Cell attacks and native evidence

Cell targets are passed unchanged into native Attack. Native attack validation
checks TarCom/Ammo rather than requiring a Techno target. For strafe,
Good_Fire_Location returns the supplied abstract target. Techno::Can_Fire has
Techno-conditional checks and a common weapon/ground/range/rearm path, not a
blanket non-Techno rejection. A Cell attack therefore uses native ground-target
semantics where the actual weapon/projectile and native command legality allow
it. It is not converted to a nearby Unit. H6A's runtime proof covers Object
attacks; Cell/weapon combinations still need the user's local validation.

Primary evidence remains TS input.dat, read only. H6A's documented entries
remain: Aircraft AI 0x004090C0, Mission_Attack 0x0040BA40, Good_Fire_Location
0x0040CF00, Can_Fire 0x0040E110, Fire_At 0x00409B70, Is_Strafe 0x0040EEE0,
Fly Process 0x00499600 and Movement_AI 0x00499F20. This increment additionally
inspected native Idle 0x0040B310..0x0040B38D: suspended restoration returns
before 0x0040B35A, while the normal branch calls Foot Idle at 0x0040B355 and
continues native mission selection afterward. Native Techno::Can_Fire
0x0062F980..0x0062FA4F confirms the null-target check and nullable Techno branch
(0x0062F9C1..0x0062F9C5), followed by the shared path. OpenTS aircraft.cpp,
techno.cpp and foot.cpp explain the matching reconstruction. TSpp declarations
remain unchanged; no new raw native function call or ABI is introduced.

## Bounds and retained non-attack geometry

Full native Attack uses native Movement_AI/Edge_Of_World_AI. Local Radar is
not a hard aircraft flight boundary; outer In_Radar remains the native world
boundary, and raw array storage is not flight permission.

Only NativeTakeoff still bypasses native Movement_AI. The existing correction
is retained as Takeoff_Movement_Coord and applied only there, without attack
edge logs, aborts or a parallel native-flight wrapper. Native_Flight_Point
also serves that guard and CAP diagnostic point formatting. Inside_Array,
Passed, Heading_OK, Valid_Point/Valid_Segment, approach construction and holding
geometry remain because takeoff/Move/docking/CAP still call them.

Holding dimensions, corner selection, approach distances, approach speed,
reservation/radio selection, touchdown, service/reload and No-Dock survival
were not redesigned. H5C radius tuning is excluded. Non-FixedWing aircraft
remain on the previous native paths; new state writes are gated by Enabled.

H3/H4/H5B reports remain historical records. Their diagnostics established

## Logging and persistence

Developer-only bounded events retained/adapted: NATIVE_ATTACK_HANDOFF with
origin MANUAL/CAP/ESCORT/AI/NATIVE, AIRBORNE/RELEASE, MISSION_ENTER/FLY_ENTER
observations, AMMO_CHANGE, TARGET_GONE, END/RTB, and the new
NATIVE_ATTACK_RESUME_CAP with current center and prior target identity.
CAP_SET_STATIC/ESCORT, ESCORT_STATE/CENTER_UPDATE, AUTO_TARGET_ACQUIRED and
FWDOCK diagnostics remain. No per-frame attack-planner probes or fire hooks.
Logging does not decide ownership, targeting or resume.

The save basis remains **0x150000**. No AircraftClassExtension member was
added/removed/reordered; AttackControl remains the same enum/int-sized field.
Adding NativeEnding changes its possible value, not its storage or raw blob
size. Existing constructor, raw save/load, NoInit preservation, CRC and
CAPEscort swizzling remain sufficient and unchanged. CAP origin is already
represented by the saved CAP parent fields. Native TarCom/NavCom, Status,
mission timer and Fly state retain native serialization.

Loading H6A's saved Custom CAP-attack ownership is detected as Attack and starts
the native adapter, discarding old planner coordinates through normal startup;
it cannot resume removed phases. H6B save/load still requires local validation.
The final save version also includes extension sizes and the existing debug
offset; 0x150000 is its basis, not the complete calculated value.
