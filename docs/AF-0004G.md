# AF-0004G — Fixed-Wing No-Dock Survival Timeout

Implemented locally; no build or tests were run for this increment.

## Scope and timing

Ordinary supported `FixedWing=yes` aircraft receive a three-minute emergency
period when no completed compatible own dock exists. The timer runs from the
Aircraft AI entry (`0x004090C0`), independently of the flight mission and of
whether the aircraft is airborne, parked, EMP-disabled or currently moving.
There is no new INI key or global dock manager.

TS defines `TICKS_PER_SECOND=15` and `TICKS_PER_MINUTE=900` in
`TSpp/src/tibsun/tibsun_defines.h`. `NO_DOCK_GRACE` is
`3 * TICKS_PER_MINUTE`, exactly **2700 simulation ticks / 180 game seconds**.
Game speed affects elapsed wall time; pausing the simulation does not consume
the counter. No system clock, UI timer or custom RNG is involved.

At the first no-dock AI call, the counter becomes 2700 without consuming a tick.
At the following calls it counts down. If absence is first observed in frame F,
expiration is handled in frame F+2700, assuming the usual one Aircraft AI call
per simulation frame. The existence check precedes expiration: a dock completed
before that aircraft's AI call rescues it even in the expiration frame. A dock
completed later in the simulation's deterministic processing order cannot
retroactively cancel an already initiated death.

## Persistent state, Save/Load and CRC

The single new field is
`AircraftClassExtension::FixedWingNoDockTimer`, an `int`:

- `0`: no active emergency.
- Positive: remaining simulation ticks; `1` is the final pending expiration
  step. If native ground-damage protection refuses death, expiration stays
  pending at 1 and is retried; no new three-minute period is granted.

The ordinary constructor initializes it to 0. The NoInit constructor deliberately
does not initialize it: inherited `Internal_Load` has already restored the raw
object blob. `Get_Object_Size()` returns `sizeof(*this)`, so the existing inherited
Save/Load path includes the new integer automatically. No duplicate stream item
is appended. An active counter resumes at its saved value after Load.

`AircraftClassExtension::Object_CRC` now calls the inherited CRC implementation
and includes the counter. Dock queries use the synchronized `Buildings` vector,
current ownership and simulation state. Logging does not change simulation state.

The save basis changes from **0x120000 to 0x130000**. The final version still
adds the existing extension/type sizes and the Debug offset when applicable.
Older saves, including AF-0004E saves, are rejected globally. Multiplayer clients
must use the same new build and data.

## Dock presence versus availability

`Dock_Exists` centralizes the structural checks shared with the existing landing
filter. `Has_Compatible_Dock` scans `Buildings` and asks only whether any such
building exists:

- Active building, not in Limbo, `Strength > 0`.
- Exactly the same House as the aircraft, as in the previous FixedWing filter.
- Building type appears in `AircraftType.Dock`.
- Supports unit reload or unit repair.
- Not in construction or deconstruction; construction animation is finished.
- Docking coordinate is a valid local map point.

Radio contact, occupancy and reservation are deliberately not presence tests.
A dock being serviced or occupied by another aircraft counts. A temporarily
switched-off dock also counts as an existing base. Approach geometry and whether
it can currently be reserved remain questions for the landing finder.

`Dock_Status` retains its previous availability rules, including `IsOn`, radio
ownership, cell occupants and mutual reservation. `Dock_Candidate` additionally
retains the existing approach geometry checks. No landing/search/radio rules are
relaxed by the survival check.

Consequences:

| Situation | Survival counter | Existing flight controller |
|---|---|---|
| One dock, occupied by another aircraft | Remains/reset to 0 | May hold and retry reservation |
| No compatible own dock | Starts/continues | May Move, Attack, Return or hold |
| Enemy/allied dock only | Starts/continues | Same-House rule still applies |
| Incompatible dock only | Starts/continues | Cannot reserve it |
| Dock under construction | Starts/continues | Not usable until completion |
| Replacement completes, even occupied | Resets to 0 on next Aircraft AI | Current player order is preserved |
| Existing dock becomes free | Stays 0 | Normal finder can reserve it |
| Replacement is lost again | New complete 2700-tick period | Existing return/holding behavior |

No mission function writes the counter. Move, Attack, target changes, Stop,
Guard/GuardArea, ingress, egress, regroup and return attempts neither reset it
nor pause it. Only a compatible dock being present clears an active emergency.
The reset itself never assigns a target, destination or mission.

## Expiration and native death handling

Airborne expiration calls **`AircraftClass::On_Death(nullptr)` at 0x0040EFB0**,
the native Aircraft crash routine (named `Crash` in the readable OpenTS source).
It records the loss, runs relevant triggers, sets the native zero-health/rocking
state, releases radio contact, stuns the aircraft and starts native tumbling and
cleanup. The existing native crash/impact handling supplies the visual aftermath
and debris behavior according to the aircraft data. No new explosion or debris
implementation is added. The native crash uses the synchronized engine RNG for
its normal tumbling; the countdown and dock decision use no RNG.

`source=nullptr` supplies no artificial enemy killer or veterancy beneficiary.
The existing native ownership/loss and trigger bookkeeping remains responsible
for attribution.

On the ground `On_Death` cannot initiate a fall. Expiration therefore calls
**`AircraftClass::Take_Damage` at 0x0040A1E0**, with current Strength as damage,
distance 0, `Rule->C4Warhead`, null source and `forced=true`. This invokes normal
Aircraft explosion/death handling and its native removal fallback. AF-0004G does
not directly delete, Limbo, reposition or set the aircraft's Strength.

Existing Vinifera damage protections can refuse ground damage (for example an
active Iron Curtain). They are not bypassed or redesigned here. The counter then
stays expired/pending at 1; subsequent AI calls retry without restarting the grace
period or logging every frame. Airborne expiration uses the direct native crash
entry and is not postponed by those damage filters.

The hook runs before the Aircraft AI prologue. Its five displaced bytes are
`sub esp,10h; push ebx; push ebp`. After initiating death, it returns through the
existing leaf-return stub instead of entering native AI with a possibly deleted
object. The helper saves only the heap ID for logging before calling death logic
and never dereferences the aircraft/extension afterward on that path.

Already dead, inactive or Limbo aircraft are excluded. The existing
`Controlled()` guard rejects zero-health/crashing flyers, leaving subsequent
crash movement to the native locomotor.

## Dock loss at ground level, during service and during approach

These existing behaviors are retained, rather than replaced by the timeout:

- **Dock destroyed:** native `BuildingClass::Take_Damage` (`0x0042B330`) can
  deal lethal forced damage to a radio-contact aircraft within one cell. A
  parked or servicing aircraft can therefore die immediately with its pad.
  A more distant contact is sent `RADIO_RUN_AWAY`. AF-0004G does not grant
  immunity from ordinary dock destruction and does not start a second death
  sequence for an aircraft already at zero health.
- **Dock sold:** native deconstruction (`0x00430630`) sends `RADIO_RUN_AWAY`.
  The existing FixedWing receiver releases contact and returns while airborne,
  or queues Enter/takeoff when grounded. A repair-depot sale can instead sell
  its nearby serviced unit through the native sale branch; that remains intact.
- **Dock captured:** native capture (`0x0042F660`) can capture a docked nearby
  contact with the building; a distant contact can instead be sent away.
  Presence is evaluated against the aircraft's resulting current House. It is
  not assumed that capture always leaves the aircraft with its original owner.
- **Approach loses its dock:** existing reserved-dock validation and Go-Around
  continue. If another compatible own dock exists, the counter remains/reset
  to 0 even while that replacement is occupied.
- **Surviving aircraft without any dock:** the next Aircraft AI starts or
  continues the counter, including during service-exit takeoff, Move or Attack.

The structural/native paths above were inspected in local code and the relevant
original Aircraft entry points in the original TS binary. This is static
analysis, not a runtime verification of all map, capture and radio situations.

## Exclusions and unchanged behavior

`Enabled`/`Supported_Type` continue to reject Carryall, transport/passenger,
Dropship, Hunter-Seeker, spawned/missile-spawn, Kamikaze and inappropriate
locomotor/type combinations. Existing warnings remain unchanged.

For `FixedWing=no`, the new AI helper returns without changing gameplay state.
The extension field remains at its constructor default. The new save layout and
CRC support are global versioning changes, not new VTOL behavior.

AF-0004E Attack geometry, weapon selection, firing and ammo accounting are not
changed. Ammo reaching zero still triggers ordinary Return; missing free docks
still cause holding. The independent survival counter continues in the background.
No CAP, new holding geometry, AI Hunt, slots, runway/taxiing or new INI options
are added.

Development logging records start, dock-restored reset and actual expiration
handling. There is no counter log on every simulation frame.

## Manual test plan — not executed

Use ordinary supported FixedWing types and measure **simulation frames**, not
wall-clock minutes. Development logs expose start/reset/expiration transitions;
the debugger can inspect `FixedWingNoDockTimer`. Start airborne when testing the
timeout separately from native pad-destruction damage.

| Case | Procedure | Expected result |
|---|---|---|
| A | One airborne FixedWing; destroy its only dock; do not rebuild | Holding remains possible; counter starts at 2700; crash begins at F+2700 |
| B | Destroy only dock; complete a replacement about 1800 ticks after timer start | Counter resets to 0; aircraft survives and existing return can find the replacement |
| C | Two FixedWings, one completed dock occupied/in service; second holds for over 2700 ticks | Second counter stays 0; no timeout loss; freeing the dock permits normal reservation |
| D | No dock; issue repeated Move/Stop/Guard/GuardArea orders and change destinations | Counter does not restart; timeout can initiate crash during Move |
| E | No dock; order Attack and change targets through ingress/pass/egress/regroup | Counter continues; with Ammo=0 ordinary Return/holding continues until timeout |
| F | Complete replacement just before expiration | If present before that Aircraft AI call, counter resets and no timeout loss occurs; also check a replacement already occupied by another aircraft |
| G | After a replacement reset, destroy it again | A new full 2700-tick period starts, not the previous remainder |
| H | Save with, for example, 900 ticks remaining; Load and continue without dock | Counter resumes at 900; no new full grace period; pause/save UI time is not consumed |
| I | Repeat destruction/sale and orders with FixedWing=no Orca/Harpy and special aircraft | No new survival behavior; supported-type restrictions remain intact |
| J | Destroy dock while aircraft is parked/in service; separately sell and capture the dock | Native shared destruction, evacuation or capture remains; surviving own aircraft starts only one timer if no alternative exists |
| K | Lose dock during final approach; provide an occupied compatible alternative | Go-Around/holding remains; counter stays/reset to 0 |
| L | Only enemy, incompatible, Limbo, dead or unfinished docks exist; then finish a valid own dock | Invalid candidates do not reset; completed compatible own dock does |
| M | Run at different speed settings; pause; repeat in multiplayer with identical builds | Expiration is at the same simulation-frame interval; no timer-related CRC divergence |
| N | Save inactive and nearly expired states; try loading an AF-0004E save | New states restore correctly; old save is rejected by the version check |
| O | Test a surviving grounded no-dock aircraft, including damage protection if configured | Normal native ground death at expiration; protected ground damage stays pending and does not receive a fresh grace period |

Only `git diff --check`, `git status` and diff review are used for local validation.
No build, automated/manual tests, commit or push; reference repositories unchanged.
