# AF-0004G1 — Dock reacquisition diagnostics

Diagnostic instrumentation only. No gameplay fix, build or tests in G1.
The subsequent runtime capture identified an out-of-bounds preferred approach;
see [AF-0004G2](AF-0004G2.md) for the central opposite-direction fallback and
the correction to the CAN_LOAD outcome label described below.

## Enable and collect

Use the existing `-DEVELOPER` command-line option for Release/RelWithDebInfo.
Debug builds enable these diagnostics automatically. There is no new INI key.
Search the normal `Debug/DEBUG_DD-MM-YYYY_HH-MM-SS.LOG` file for **`[FWDOCK]`**.
The directory is the existing `Vinifera_DebugDirectory`, normally `Debug`.
Do not enable the mode on only some multiplayer clients when comparing logs;
the debug data is observational and excluded from simulation state/CRC.

Keep the log from before the last dock is lost through the failed replacement,
its sale, and the successful second replacement. Do not send just the last few
lines. Required comparisons use aircraft ID + frame and both buildings' unique
IDs, heap IDs, type, House, coordinates, radio endpoints and occupant identities.
Heap slots and pointers can be reused; unique IDs and the frame history matter.

## Exact search path and retry cadence

1. The existing Aircraft Mission_Enter hook (`0x0040D360`) invokes
   `FixedWing::Mission_Enter` for supported controlled aircraft.
2. `Status == STACK` invokes `Find_Dock`.
3. An existing valid mutual reservation and approach geometry are tried first.
4. Otherwise `Release` sends the existing `RADIO_OVER_OUT`, if there is contact.
5. In `AircraftType.Dock` order, the controller calls native
   `TechnoClass::Find_Docking_Bay(type, false, true)` at **0x00637E60**.
6. The native function checks House `BQuantity` for the requested type before
   scanning `Buildings`. It checks owner, Limbo and exact type, then reaches the
   existing FixedWing candidate hook at **0x00637F0B**.
7. After that filter, native `only_unoccupied` rejects **any** building Radio
   contact. Aircraft skip the ground-unit same-zone test. The original finder
   sends **one** `RADIO_CAN_LOAD` and requires `RADIO_ROGER`. Distance and primary
   building priority choose the returned candidate.
8. The controller checks the returned `Dock_Candidate`, sends its existing
   `RADIO_HELLO`, and checks mutual `Dock_Status(..., true)` and geometry again.
   Success replaces the holding-cell `NavCom` with the building, sets the Fly
   goal to approach S, and enters DOWNWIND.
9. A failed STACK search returns `DOCK_RETRY = TICKS_PER_SECOND = 15` to the
   existing Mission timer. Nominal retry cadence is **one game second**. A
   successful search returns 1. No diagnostic code writes either timer.

`Process` additionally handles ALTITUDE directly. It does not directly search
each frame in STACK. STACK's `Arrived` branch advances holding corners and
returns before the later approach code that clears the mission timer.
Mission changes can alter the mission/status/queue; the trace records these
values rather than assuming that an aircraft visually circling is still STACK.

## Existing candidate checks and presence differences

The snapshots list PASS/FAIL for the existing checks in filter order:

- Active, not Limbo, positive Strength.
- Same House; type in `AircraftType.Dock`.
- Not construction/deconstruction; BState not construction.
- Reload or Repair support; valid local docking coordinate.
- `IsOn`.
- Building Radio empty or pointing to this aircraft.
- No other active non-Limbo Aircraft/Unit/Infantry in the docking-cell chain.
- For an existing/post-HELLO reservation, mutual Aircraft/Building Radio.
- Valid approach segments S→G→P→D and no bridge overlay over D.

`Has_Compatible_Dock` and `Dock_Status` share exactly the same structural
`Dock_Exists` checks. Presence does not check power, radio, occupancy, approach
geometry, the House quantity shortcut or the response to `RADIO_CAN_LOAD`.
Therefore **presence=true and candidate=false is possible and expected** for
several reasons. It is not itself proof of the sporadic bug.

The `REJECT_*={PASS|FAIL}` entries describe whether the corresponding exclusion
check was passed; `firstProbe` identifies the first failed candidate check.
These are explicitly **read-only probes**, not claims that native code executed
every check. `candidateProbe` is unreserved eligibility. A foreign-reservation
FAIL is normal before HELLO; it matters for the existing/post-HELLO reservation.
`reservedProbe` captures the complete reserved-status result separately.

Actual native control-flow markers are recorded independently. This separation
shows both a building present in the inventory and whether that same ID was
visited by the real finder.

## Log events and interpretation

| Event / value | Meaning |
|---|---|
| `INVENTORY_CHANGE` | First relevant building or changed candidate snapshot while watching a no-dock/reacquisition episode |
| `NO_DOCK_PRESENCE_RESTORED` | Presence became true while the real survival counter was still active; logged before its existing reset |
| `SEARCH_BEGIN` | A real `Find_Dock` invocation, including mission/status/timer, queue, NavCom, radio, destination and controller eligibility |
| `NATIVE_TYPE_BEGIN` | Requested type and the read-only House quantity immediately before the original call |
| `REJECT_NATIVE_HOUSE_INVENTORY` in `inventoryProbe` | The quantity shortcut sees zero; expect no native enumeration for this type |
| `HOUSE_INVENTORY_PASS` | Actual execution passed the native quantity gate |
| `NATIVE_ENUMERATED` | The native Buildings loop reached this candidate ID before its owner/Limbo/type tests |
| `FIXED_FILTER_PASS` | Native execution passed the existing FixedWing filter and reached the native Radio occupancy check |
| `REJECT_NATIVE_RADIO_CONTACT` | Native `only_unoccupied` rejects a still-populated Building.Radio, including a contact with this aircraft |
| `NATIVE_SKIP_BEFORE_CAN_LOAD` | Candidate skipped before the native radio request; inspect its snapshot's firstProbe and actual filter marker |
| `RADIO_CAN_LOAD_BEGIN` | Reached the original radio request; no extra request is sent by diagnostics |
| `RADIO_CAN_LOAD_PASS` | Original execution took the ROGER branch and reached the distance call |
| `NATIVE_CAN_LOAD_OUTCOME_UNCONFIRMED` | CAN_LOAD began, but neither the distance-entry PASS marker nor the best-selection marker was observed; `value` is raw EAX at the join, potentially a radio reply or distance |
| `NATIVE_BEST_SO_FAR` | Candidate became the native best choice; `value` is the native distance |
| `NATIVE_ACCEPTED_SO_FAR` | The best-selection marker proves CAN_LOAD passed, even when the original distance-entry hook was bypassed |
| `NATIVE_NOT_BEST_DISTANCE_PRIORITY` | CAN_LOAD passed, but another candidate retained priority |
| `nativeResult` | Building returned by the original function, or null |
| `RADIO_OVER_OUT` / `RADIO_HELLO` | Original call's result and Aircraft/peer Radio afterward |
| `REJECT_POST_HELLO` | HELLO was accepted but reserved status or approach validation then failed |
| `RESERVED_SUCCESS` | Reservation reused/obtained; records the actual replacement NavCom, destination S and DOWNWIND status |
| `STACK_SEARCH_OVERDUE` | Aircraft remains in STACK without a Find_Dock call for more than two retry periods; observational warning, no timer repair |

Snapshots include Building BState, QueueBState, CurrentMission, Status,
IsReadyToCommence, HasOpened, IsOn, reload/repair/helipad flags, House BQuantity,
Docking_Coord, both Radio references, main and alternate cell occupancy, bridge
state and the complete approach coordinates/validity. Aircraft data includes
its heap/unique ID, House, mission/queue/suspended mission, Status, mission timer,
survival timer, NavCom including a resolved holding cell, Fly destination and
movement/takeoff/power/tumbling/controller flags.

## Radio and holding-anchor risks

`Release` is still called before the native search; logging captures the existing
OVER_OUT result without sending another message. A reference to a destroyed old
dock is expected to be cleared by native detach. An unresolved logged pointer is
not automatically proof of a stale allocation: logs resolve only known live
object registries and map cells, and never repair or dereference an unresolved
radio pointer.

A specific asymmetry is worth checking: the FixedWing unreserved filter allows
`dock->Radio == aircraft`, but native `only_unoccupied` later requires **null**.
`RADIO_CAN_LOAD` also has its own building-class acceptance rules: the current
Vinifera building receiver treats helipads and repair depots separately. General
Reload capability alone is not a guarantee of a ROGER reply.

The holding-cell NavCom is not an exclusion in the FixedWing candidate filter.
It remains until successful reservation replaces it with the building. If all
native markers succeed but NavCom/destination remain a cell/holding point,
compare HELLO, post-HELLO status and `RESERVED_SUCCESS`; do not attribute that
case to an unseen building.

## Completion, cell occupancy, geometry and rebuilding

Construction enters `MISSION_CONSTRUCTION` / `BSTATE_CONSTRUCTION`.
Animation completion sets `IsReadyToCommence`. Native Mission_Construction
(`0x004304A0`) sends COMPLETE and OVER_OUT, begins IDLE, calls Grand_Opening
(`0x0042E170`), queues GUARD and sets the final facing. The current mission can
still be CONSTRUCTION until the queued mission commences. Active alone does not
mean finished; HasOpened/ready are logged but are not new eligibility conditions.

The two structural filters cannot disagree solely because one checks construction
earlier: they call the same helper. Additional native quantity/radio checks,
power, occupancy and geometry can still make actual landing eligibility later.
A short completion transition is plausible; a persistent difference needs the
trace rather than a presumed one-tick timing explanation.

The cell filter examines the primary `Cell_Occupier()` chain. The dock itself is
ignored, and building/animation/terrain nodes do not block by their RTTI alone.
A bib/animation is therefore not inherently a rejected mobile occupant. A real
remaining Aircraft/Unit/Infantry node can block. Alternate occupancy and bridge
state are logged as context; an under-bridge dock fails geometry independently.
Diagnostic walks stop at 16 nodes, a cycle or an unresolved object. Such a case
logs a skipped/unknown probe (`-1`), not a fabricated PASS or a memory repair.

Geometry records D/S/G/P, the facing source (mutual Landing_Direction or building
facing), point validity and all three sampled segment results. Valid endpoints
do not guarantee a valid entire segment. Selling/rebuilding can change identity,
radio links, cell occupants, construction state and facing/approach. Without a
failed and working log, none of these differences is established as the cause.

## Diagnostic scope and validation

Aircraft watchers run read-only observations at most once per 15 simulation
ticks and emit full candidate snapshots only on changes. Real search traces are
also bounded to once per 15 ticks per aircraft, even if a scheduling bug calls
the finder each frame. Successful reservation and presence restoration are
transition events. A search-stall warning is emitted once until another search
or a departure from STACK. No per-frame log output is introduced.

The caches/progress flags are static diagnostic helpers keyed by unique IDs,
never persistent gameplay fields. They are cleared on frame rollback/observed
load and do not influence selection, radio results, missions, timers or CRC.
No-Dock duration, conditions and reset assignments are unchanged. Save basis
remains **0x130000**.

The native observation hooks displace only branch-free, non-relative
instructions. The distance-entry observation is gated by the original return
address `0x00637FFA`; reaching it proves CAN_LOAD==ROGER without an extra radio
call or replacing the original comparison. However, Vinifera's existing
`Patch_Call(0x00637FF5, &TechnoClassExt::_Cell_Distance_Squared)` bypasses that
original entry. G1 incorrectly treated its absent PASS marker as rejection even
after NATIVE_BEST_SO_FAR. G2 gives the best-selection proof priority and labels
otherwise unobserved outcomes as unconfirmed, without interpreting a distance
as a radio reply. Hook addresses, native radio and distance selection are unchanged.
This avoids relying on newer Syringe
relative-instruction/flag-preservation extensions (see the
[SyringeEx feature documentation](https://github.com/Phobos-developers/SyringeEx#current-feature-flags)).
All new hooks return 0, preserving original execution and register values.

Changed for G1: `src/extensions/aircraft/fixedwing.cpp`, this document, and
`docs/Whats-New.md`. No header, persistent extension layout, save version,
Dock_Exists/Dock_Status/Dock_Candidate/Has_Compatible_Dock predicate, holding
geometry or gameplay transition was changed. Existing radio calls are merely
captured once and logged; their arguments, order and branching are retained.

Validation is limited to `git diff --check`, `git status` and complete diff review,
including the already-untracked FixedWing source. No build, tests, commit or push.
Reference repositories remain unchanged.
