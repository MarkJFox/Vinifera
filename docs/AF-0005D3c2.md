# AF-0005D3c2 - FixedWing MultiDock integration

Baseline: `6f0cedd6440bfefb54ffad05309c54d138533fdd`,
`feat: add aircraft helipad multidock support`, branch `aftermath-dev`.
The initial implementation working tree was clean. Closeout status: the user
successfully built D3c2 and runtime-confirmed the specific scenarios recorded below,
including two/four FixedWing slots, mixed visitors, approach save/load, CAP rearm
and slot-relative opposite-direction approaches. This is not a complete A-P test
matrix. Codex performed static review only; no build, automated test or runtime
test was performed by Codex. The closeout changes documentation only.

## User build confirmation

The first user build failed at the diagnostic declaration `Approach approach{};`
because its DirType member has an explicit default constructor. The minimal fix
uses the existing declaration form `Approach approach;`. Geometry supplies the
actual direction before valid diagnostic reads; no artificial direction, gameplay
or geometry change was added. This buildfix is included in the D3c2 source being
committed. The user subsequently built successfully. No further source or diagnostic
change was made during closeout.

## Scope and configuration

Supported FixedWing Aircraft share the existing D3c1 aircraft-factory helipad:
Factory=AircraftType, Helipad=yes, UnitReload=yes and NumberOfDocks=2..16.
The AircraftType must retain the pad in its Dock list. FixedWing::Enabled and its
existing Supported_Type/dynamic exclusions still apply; unsupported FixedWing and
Carryall requesters are not admitted by removing a blanket guard.

No new public keys are introduced. Example, using an already valid 5x5 occupied
CustomFoundation mask with these cells (the existing mask definition is omitted):

Rules:

```ini
[GAHPAD]
Factory=AircraftType
Helipad=yes
UnitReload=yes
NumberOfDocks=4

[TESTPLANE]
FixedWing=yes
Dock=GAHPAD
```

Art, in the pad's Image/GraphicName section:

```ini
[GAHPAD]
DockingCell0=1,1
DockingCell1=3,1
DockingCell2=1,3
DockingCell3=3,3
```

Native-foundation MultiDock uses the same D3c1 occupied-cell validation; it does
not acquire new geometry rules. Absent count/count=1 still uses the existing
Single-Dock path. CustomDockCell and the Single-Dock DockingCell0 alias are unchanged.
No parser, CustomFoundation or BibShape change is made.

UnitRepair/repair bays, refineries, weeders, ground/infantry/weapon factories,
Carryall extensions, outside-foundation dock points, XYZ offsets, per-slot facing,
taxiways, runways, parking nodes and traffic/queue scheduling are excluded.

## Shared ownership, capacity and presence

No second slot system or Aircraft dock index is added. Ownership is reconstructed:

```text
Aircraft.Radio -> Building -> BuildingExtension.AircraftDockVisitors[index]
```

The index comes from Find_Aircraft_Dock_Slot(aircraft). Existing D3c1 first-free
reservation, idempotent HELLO, null holes, targeted OVER_OUT and lifecycle cleanup
are retained. Normal and FixedWing visitors consume the same capacity and use
the same AircraftDockVisitors[16]/AircraftDockReloadTimers[16] arrays.

Can_Accept_Aircraft_Dock, the production capacity guard and post-swizzle validation
now accept a FixedWing-tagged Aircraft only when FixedWing::Enabled accepts it.
The ordinary-Aircraft path is unchanged. Find_Docking_Bay's existing MultiDock
branch additionally applies Dock_Candidate for enabled FixedWing, so a native
search does not rank a pad whose predicted slot has an invalid FixedWing approach.
Native type-list order, candidate distance ranking and full-pad branches remain.

Dock_Point separates two read-only cases:

- Registered visitor: only Aircraft_Dock_Coord(aircraft), requiring its Radio to
  match the Building; never first-free lookup or parameterless Building geometry.
- Before HELLO: inspect the first free slot without reserving it. HELLO performs
  the actual D3c1 reservation; Find_Dock then validates the registered point again.

A registered high-index slot never moves when a lower slot becomes free. A stale
registered entry with the wrong Radio cannot silently become another slot.
Coordinate queries do not reserve slots. An invalid first-free approach does not
cause a search for a different slot inside the same pad; D3c1 slot order is retained.

Dock_Status uses shared acceptance for a new visitor, or array membership plus
Aircraft.Radio for a reserved visitor. Occupancy is checked on that slot's Cell,
not at the Building center or another visitor's slot. Existing reservations survive
temporary Building power-off/EMP as in D3c1; new acceptance and service remain gated.
Capture, destruction and detach still use D3c1 cleanup without special FW policy.

Dock_Exists is presence, not availability: an active, finished, compatible pad
with a valid configured point exists even when all slots are full, power is off
or approach geometry is unusable. MultiDock compatibility uses D3c1 alliance rules.
Has_Compatible_Dock explicitly restricts the AF-0004G survival inventory to own
Buildings, preserving the ZERO-compatible-own-docks contract. A full own pad does
not start the no-dock timeout; allied service does not redefine that own-base rule.
Single-Dock presence, availability and scalar reciprocity retain their old branches.

## Slot-relative approach and touchdown

Geometry obtains D from Dock_Point. For a registered visitor this is exactly its
assigned Cell center and the existing Building Z. The existing Build_Approach body
and lengths are unchanged:

```text
P = D - 2048*u
G = P - 1536*u
S = G + 1536*v
flight: S -> G -> P -> D
```

u remains the existing eight-way landing direction and v its lateral direction.
With contact, Landing_Direction reads the Aircraft's Building partner; before
contact, the Building facing is used. All slots share this same direction contract.
There is no DockingFacing# key. Geometry first tests the original direction, then
only the existing opposite direction with the same D and unchanged lengths.
No +/-90-degree, clamping, shortening, snapping or random fallback is added.

Mission_Enter's parked-service distance uses approach.D. Its approach states remain
INITIAL, TAKEOFF, ALTITUDE, STACK, DOWNWIND, CROSSWIND, TRAVEL and LANDING. Arrived
and Process already use Geometry, so the slot point propagates to every leg,
heading commitment, final glide and exact touchdown. Cruise altitude's dock-Z
floor and the parked Assign_Destination distance also use the per-Aircraft point.
Mission_Move locally resolves an already-owned MultiDock Building target to its
slot; other destinations retain the existing virtual Destination_Coord call.

The native Is_LZ_Clear implementation at 0x4A8300 reads the supplied Abstract's
Center_Coord at 0x4A831B..0x4A8324. Passing the whole MultiDock Building would test
the Building-center Cell. The FixedWing touchdown call therefore passes the
reserved Cell object for MultiDock, while Single-Dock still passes the Building.
The native routine retains its ordinary Cell/Building/Radio checks. Native
Process_Landing and Process_Takeoff are not replaced or rewritten.

RADIO_MOVE_HERE maintenance accepts the D3c1 array counterpart for MultiDock and
the original Building.Radio counterpart for Single-Dock. It still requires the
existing Aircraft.Radio/target match and a legal candidate. It does not Commence,
restart the approach or allocate another slot.

## Service, departure, CAP and attacks

After touchdown, the existing FixedWing Mission_Enter clears NavCom and sends
targeted IM_IN. D3c1 queues Sleep/Repair, establishes per-visitor tether and owns
the independent service deadline and native RELOAD messages. No service algorithm,
ReloadRate conversion, timer state or direct Ammo mutation is added for FixedWing.
The shared SERVICE_IM_IN/START/RELOAD/COMPLETE events identify the actual slot.
An existing CAP resume may leave service immediately after the final successful
RELOAD, so SERVICE_COMPLETE is not mandatory for a successful CAP rearm cycle.

Reserved now recognizes array membership, allowing existing Idle, CAP_AI and
Resume_After_Service to see a MultiDock service contact. The existing CAP rearm
handoff can therefore resume CAP after full ammunition without a separate callback
or new CAP/attack state machine. Manual attack rearm retains the existing parked/
post-service behavior. The user confirmed repeated CAP rearm/resume cycles and the
Single-Dock attack/RTB regression; the exact confirmed subset is recorded below.

Production uses D3c1's capacity, reserve-before-Unlimbo, native Pose_Dir/Z and
rollback paths. Supported FixedWing no longer takes the exclusion-only edge route;
unsupported types/Carryall remain excluded. Full-pad/ion-storm/nearby/rally behavior
is unchanged. No independent FW production queue or automatic CAP/launch order is
created. Departure follows the existing accepted flight order/takeoff behavior.

Existing FixedWing Release transmits OVER_OUT to its Aircraft.Radio partner.
D3c1 releases only that visitor and preserves pending player orders; other visitors
and deadlines remain. Existing CAP departure, destination abort, layer-change
takeoff handling and Building/visitor lifecycle cleanup use that same protocol.
The FixedWing takeoff mechanics themselves are unchanged.

## Persistence and unchanged behavior

No new persistent fields, Aircraft dock index or slot containers are introduced.
Save basis remains 0x190000. Existing raw arrays and NoInit constructors are
unchanged. Every non-null AircraftDockVisitors entry already requests a swizzle,
independent of the AircraftType's FixedWing flag. Post-swizzle validation now allows
supported FixedWing entries while retaining RTTI/list/type/uniqueness/contact
checks. Older D3c1 executables still reject FW visitor claims they do not support;
an unchanged layout/version does not add this feature to those executables.

CRC architecture is unchanged: D3c1 hashes slot indices, empty markers, stable
Aircraft HeapIDs and deadlines; AircraftType already hashes IsFixedWing. No pointer
address or new FixedWing-specific state is hashed. Mixed visitors use the same
slot iteration and capacity.

ROT, turn radius/turning, landing-speed factors, holding geometry, no-dock grace
duration, attack/native Fly ownership, weapon behavior, CAP and escort planners,
takeoff mechanics and L/M/W constants are unchanged. No global RadioClass port,
D4 work or investigation/change of the separate pre-existing load/shutdown issue
is included. That issue is not attributed to D3c2, FixedWing or MultiDock.

## Developer diagnostics

Existing snapshot/rate-limited FWDOCK candidate logs now contain multiDock, slot,
slotSource=REGISTERED/FIRST_FREE_PROBE/SINGLE and the actual/probed D/S/G/P geometry.
A full pad without a registration has no predicted point; no center is substituted.
LANDING_SLOT records the assigned slot and D once at touchdown. Existing MDOCK
reservation/release and service transition logs remain. All additions are gated
by Vinifera_DeveloperMode; no new per-frame log, diagnostic state or save field.

The following evidence was actually observed in game and reported by the user.
Codex did not execute these tests. Unless noted otherwise, the pad used a 5x5
CustomFoundation.

| Scenario | Runtime-confirmed result |
|---|---|
| Single-Dock regression | One dock/one FixedWing retained the existing Single-Dock path without a MultiDock slot. Production, takeoff, attack, RTB, landing and service/reload worked, with the existing geometry and no visible AF-0004/D3 regression. This does not mark every API/parameter variant in test A passed. |
| Two FixedWing docks | NumberOfDocks=2 used separate slots 0/1 for production, takeoff, return and landing. Each Aircraft kept its reservation; LANDING_SLOT matched it. Per-slot approach and parallel D3c1 service/reload worked; both reached full ammunition. |
| Four FixedWing docks | NumberOfDocks=4 used slots 0..3 independently without a hidden fifth slot. All four retained their approach slots, landed on four distinct DockingCells matching LANDING_SLOT, and used parallel per-slot D3c1 service/reload. |
| Slot stability | A reservation remained authoritative throughout approach. No switch to a subsequently freed lower slot was observed. The shared D3c1 visitor registration supplied the identity. |
| Slot-relative geometry | The reserved slot supplied D for the existing P=D-2048*u, G=P-1536*u and S=G+1536*v chain. L/M/W, LandingDirection, ROT and speed factors retained their existing values; no new geometry was introduced. |
| Mixed visitors | Two normal Aircraft and two FixedWing shared the same four-slot pad and AircraftDockVisitors capacity, using different slots and parallel service. FixedWing retained its slot-relative approach; no separate FW capacity was used. |
| Save/load during approach | A four-FixedWing save contained existing reservations and active approach states. CAP rearm completion was evidenced by Ammo=5, SLOT_RELEASE reason=OVER_OUT,
rearming=false, CAPMode=1, renewed CAP_GEOMETRY, AUTO_TARGET_ACQUIRED and another
native CAP attack. A missing SERVICE_COMPLETE after the last RELOAD to 5/5 is not
a failure when this existing resume path completes the cycle.

## Open and statically covered cases

The original A-P checklist is not fully runtime-confirmed. In particular, Building
destruction, EMP and ownership changes during active approach, exotic aborts,
FixedWing save/load during active service, mixed-type save/load, all Single-Dock
key/parameter combinations, native-foundation MultiDock, the complete 2..16 count
range and unsupported-type/lifecycle combinations remain open unless separately
confirmed. No multiplayer/framesync result is claimed.

The rule that a full compatible own pad still prevents the no-dock timeout is
statically implemented and unchanged; a complete grace-period timeout test is not
claimed by the reported capacity observations. Approach save/load confirmation
does not by itself confirm every service-save or corrupt-save case.

## Deliberate limits

Independent slot ownership does not provide collision-free parallel corridors,
air-traffic sequencing, runway locks, staggered landings, slot-based holding
priorities or physical separation of overlapping S/G/P paths. Crossing approaches
can intersect. No queue, corridor reservation, extra approach direction or parking
system is implemented. If the first free slot has no legal primary/opposite
approach, the pad is unavailable for that new FW request under the existing slot
order; no alternative-slot search is introduced.
