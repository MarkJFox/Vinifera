# AF-0004H — FixedWing Guard / Combat Air Patrol

Implementation with static source/binary review only. No build or tests were run.
G2's locally confirmed approach behavior is retained.

## Native TS command and mission reconstruction

The UI name is not the mission name. The existing Guard command (normally G)
executes GuardCommandClass::Process around **0x004E9590**. The native call at
0x004E95EB supplies mission **0x0A = MISSION_GUARD_AREA**, with the selected
object's current cell as the target. Vinifera already replaces the command's
eligibility/assignment block at **0x004E95C2**, including its harvester handling.
H only permits supported FixedWing aircraft through its existing weapon gate,
so an unarmed or empty aircraft can still receive the same Guard command.
No key binding or new command is introduced.

CTRL+ALT is the existing force-attack plus force-move modifier combination.
Techno::What_Action(ObjectClass) returns **ACTION_GUARD_AREA** when both are down
and Can_Player_Move permits it. Aircraft's existing What_Action replacement
delegates to Foot/Techno. Aircraft Active_Click_With(ObjectClass) at **0x0040B740**
forwards to Foot at **0x004A35A0**, whose GuardArea case sends
Player_Assign_Mission(MISSION_GUARD_AREA, object). The cell overload goes through
Aircraft at **0x0040B690**, then Foot at **0x004A2EB0**. H's two narrowly gated
click hooks send that same mission for supported FixedWing GuardArea clicks;
the own-object hook accepts only the same House. They bypass the native fire
permission gate for CAP, not movement permission. They change no local CAP
simulation state: the normal event must execute first.

Aircraft::Player_Assign_Mission at **0x0040B760** creates the ordinary synchronized
MEGAMISSION event. The accepted event path performs Assign_Mission, clears
SuspendedNavCom/SuspendedTarCom, and treats GuardArea specially:

```text
Assign_Target(nullptr)
Assign_Destination(event.Target)
Assign_Archive_Target(event.Target)
```

In the original binary this is **0x004948E5–0x00494926**. The guarded object is
the event Target, then NavCom and ArchiveTarget; it is not an enemy TarCom.
The archive assignment is the nonvirtual helper **0x00639130**. H captures the
original event target before assignment, in the existing **0x004948A5** hook,
after ownership/liveness/target validation. Later native event writes remain.
All clients therefore distinguish an explicit Attack from an automatic attack
at the same simulation event, including while already attacking or reloading.
MEGAMISSION_F follows the native shared MEGAMISSION execution path.

| Native mission | Original aircraft behavior | H behavior |
|---|---|---|
| MISSION_GUARD (5) | At flight level, non-team aircraft enter Idle; below that, handles repair/rearm/current TarCom and eventually Foot Guard | Static CAP at the current position; native THREAT_RANGE acquisition |
| MISSION_GUARD_AREA (10) | At flight level, non-team aircraft enter Idle; with TarCom, queue Attack; otherwise Foot GuardArea | Static CAP at its cell anchor, or Escort CAP around its own Techno; native THREAT_AREA acquisition |
| Guard of a concrete Techno | Not a third mission; GuardArea's ArchiveTarget names the object | Persist an Escort reference and follow that object's current center |

Native Aircraft::Mission_Guard is **0x0040DD10**, Mission_Guard_Area is
**0x0040E0A0**. Foot::Mission_Guard at **0x004A1A90** uses
Target_Something_Nearby(..., THREAT_RANGE); Foot::Mission_Guard_Area at
**0x004A2830** uses ArchiveTarget as the home area, applies a return-distance
check, and scans with THREAT_AREA. Ground-native Guard can fire without a
separate Attack mission; Aircraft instead hands an existing TarCom to Attack.
Ordinary Aircraft Attack can return through Idle/restore paths, depending on
its mission override. Existing FixedWing E replaces that attack controller;
its End_Attack called Idle, which returned an airborne aircraft to Enter.
FixedWing Process also explicitly converted airborne Guard/Sleep into Return
or Move. Those two VTOL/idle exits explain the previous Guard-to-dock behavior.

SuspendedMission and its target/navigation partners are a single native
override slot; they are not a stack for Guard -> Attack -> Enter -> Sleep.
Radio is the service/reservation contact. Fly DestinationCoord/HeadToCoord
store committed flight legs. None can independently retain the parent CAP,
escort identity and original center across all those missions without changing
the existing dock/attack protocols.

## Native target acquisition, reused

CAP calls the existing virtual **Target_Something_Nearby**, TSpp address
**0x00637450**. Vinifera already replaces this entry with
TechnoClassExt::_Target_Something_Nearby. It retains/validates the current TarCom
with weapon selection/Can_Fire, or assigns virtual Greatest_Threat. For Aircraft,
Foot::Greatest_Threat (**0x004A4DC0**) applies scan-limit/cloak rules, adds the
normal native ground threat mask (0x38) when needed, then calls
Techno::Greatest_Threat (**0x0062DC80**). This preserves native ownership,
weapon suitability, GuardRange/Threat_Range, NoAutoFire and threat scoring.
No enemy enumeration loop or alternative scanner is added.

Guard uses THREAT_RANGE and GuardArea uses THREAT_AREA around the saved static
anchor or current Escort center. Scans run at a deterministic 15-tick mission
cadence; flight progression runs every locomotor frame. A valid target enters
the existing AF-0004E ATTACK_INITIAL/INGRESS -> ATTACK_PASS -> EGRESS -> REGROUP
controller. Can_Fire, Fire_At, ammunition spending, flight levels, run geometry
and the existing target-loss breakoff remain shared with manual Attack.

CAP alone also retains its native home-area constraint during the run:
Threat_Range(0/1), with weapon range fallback, limits the target around the
current CAP center. An allied, lost or out-of-area target is cleared and takes
E's existing target-loss/egress path back to CAP; it cannot drag CAP into an
unbounded pursuit. Manual attacks keep their existing behavior.

## CAP flight and parent-order transitions

```text
Guard / GuardArea command
  -> CAP_INITIAL -> nearest valid holding corner -> next corners 0/1/2/3
  -> native acquisition -> AF-0004E Attack
       -> target gone / breakoff, ammo remaining -> CAP_INITIAL
       -> ammo empty -> CAPRearming + normal Enter
            -> existing STACK/Find_Dock/Approach/Landing/Sleep/Reload
            -> grounded, reserved, full ammo -> CAP_INITIAL -> takeoff
```

Guard Status values are mission-local: 0 = CAP_INITIAL, 1–4 = the committed
corner index. They do not alter Enter's Status interpretation. CAP reuses the
existing Holding_Points rectangle sizes, clearance and validation. Its existing
anchor relocation is extracted into Orbit_Points, shared with Start_Holding
without changing that algorithm or STACK's retry/arrival handling. Nearest-corner
selection and subsequent cyclic order are deterministic. No RNG, waypoints,
Speed/ROT-dependent holding size or new locomotor is introduced.

G stores the original position as CAPAnchor (its native target is the current
cell). A distinct GuardArea cell uses that cell center. The existing holding
geometry quantizes the flight anchor to cells and relocates the complete
rectangle deterministically if needed near map edges; it never clamps corners.

Escort stores a protected own-Techno reference. At CAP entry/resume and only
after each reached corner, CAP_Leg reads its current Center_Coord and computes
the next corner. DestinationCoord remains unchanged throughout the current leg.
The current leg can therefore finish even while the escorted unit moves.
Target acquisition/leash evaluation may inspect the current center without
changing that flight leg. After Attack or Reload, Escort resumes around the
object's latest position, not its previous waypoint.

NavCom stores the current safe CAP geometry cell only in Guard/GuardArea.
ArchiveTarget initially receives the native Guard command target; it is not
the persistent CAP source because other commands/mission paths overwrite it.
TarCom is only the current enemy. During Attack and Enter, NavCom and both Fly
coordinates retain their original E/G meanings. No CAP cell is interpreted as
a dock: reservation still uses the existing mutual Radio/building checks.

The existing forward takeoff/climb and Cruise routines provide continuous
forward flight. Missing targets never cause a CAP landing or zero target speed.
An unarmed aircraft can fly CAP and does not scan/fire. An armed aircraft with
Ammo=0 and positive MaxAmmo requests the existing return/reload path instead.

End_Attack consults CAP context centrally: automatic CAP Attack resumes it
when ammunition remains, otherwise marks CAPRearming and returns through E/G.
An explicit synchronized Attack clears context before native mission/target
assignment, so its completion uses the original normal Return behavior.
New Guard commands replace the context, even if the native mission is unchanged.
Move/QMove and other explicit MEGAMISSION orders cancel it. Direct AI/script
movement orders also cancel it; native automatic Attack retains it.
Canceling CAP also clears a native suspended Guard/GuardArea override and its
target/navigation references, preventing a later Restore_Mission from reviving
the canceled order. Explicit Guard clears an older navigation list/waypoint
path so the previous flight plan cannot replace CAP after service.

Vinifera's existing EventClassExt::Do_IDLE is the Stop path. It clears CAP,
including a queued/resumable CAP on a tethered dock; airborne aircraft request
normal Return, grounded aircraft stay asleep. Navigation/waypoint state is also
cleared for a tethered CAP aircraft. The remaining native Stop
cleanup still runs where its original guards permit it. A native facility's
internal Guard -> Enter_Idle_Mode handoff after ordinary non-CAP service is
consumed by the normal grounded Idle path, so manual Move/Attack/Stop cannot
silently create a new CAP when reloading finishes.

CAP_AI runs after the existing No_Dock_AI check, not in its place. While
CAPRearming it can resume only when grounded in Sleep or the native facility's
Guard handoff, stationary, not landing
or taking off, with a valid reserved dock and a full magazine. The native
facility's full-ammo Idle handoff can resume through the same helper. No Ammo
or reload timer is written by CAP. An occupied dock keeps normal STACK waiting;
a missing base keeps the normal 2700-tick survival countdown. A rebuilt/freed
dock allows the normal landing/reload/resume sequence; no CAP-specific reset.

The Sleep polling shortcut is restricted to non-repair reload docks. Repair
depots can power off their client and later issue an internal ground exit/rally
Move; starting CAP just because Ammo became full could interrupt repair, while
treating that internal Move as a player command would lose CAP. The existing
`_BuildingClass_Mission_Repair_Assign_Unit_Destination` helper therefore calls
Resume_After_Service at its already-established service-complete boundary.
Only a valid, fully reloaded, stationary CAP client resumes; the original
OVER_OUT and field_20C cleanup still happen exactly once. Other clients retain
the original exit/rally Move, including a FixedWing whose explicit command
already canceled CAP. Reload/repair steps and timers are untouched.
If the CAP client is still unpowered/EMP-disabled or not fully reloaded, this
existing helper reports "not ready" and retains contact for the facility's
normal retry/Power_On path. CAP does not force power on or bypass EMP.

Destroyed, detached, inactive, limbo or foreign-house Escort objects invalidate
CAP. Aircraft ownership changes also invalidate the saved owner. The context
is cleared and normal Return requested; no orbit around the last known position.
The same mission controller serves player and AI Guard/GuardArea. Hunt and
Patrol are not implemented or redirected into CAP.

## Minimal persistent context and save/load

AircraftClassExtension adds exactly:

| Field | Purpose |
|---|---|
| FixedWingCAPMode CAPMode | None / Static / Escort; a null detached Escort must not become Static |
| MissionType CAPMission | Preserve Guard versus GuardArea's acquisition policy across other missions |
| Coord CAPAnchor | Original static CAP center survives changing flight/navigation coordinates |
| TechnoClass* CAPEscort | Original guarded object survives TarCom/NavCom/ArchiveTarget changes |
| bool CAPRearming | Retain the parent order during Enter/Sleep; permit resume only after full dock reload |
| int CAPOwner | Original House heap ID; discard the old order after aircraft capture |

There is no separate persistent autoattack state machine or corner field:
active context identifies automatic Attack after explicit commands clear it;
native Guard Status and saved Fly coordinates retain the committed leg.

The normal constructor initializes all six fields. NoInit preserves their
streamed bytes; Coord's default constructor and its Point3D bases intentionally
do nothing. Inherited raw-blob Save/Load already uses the derived Get_Object_Size.
Load then registers CAPEscort with VINIFERA_SWIZZLE_REQUEST_POINTER_REMAP.
The existing inherited Techno detach listener dispatches to the Aircraft
override, which calls its parent and clears the Escort pointer before lifetime
ends, leaving Escort mode for the next AI's explicit loss handling. It neither
dereferences the invalid target nor changes missions during Detach.

CRC includes mode, mission, anchor XYZ, Escort Fetch_ID (never its address),
rearming and owner, in addition to the existing parent/timer CRC. Save basis
changes **0x130000 -> 0x140000** because the extension layout changes.
Start a new game; G/G2 and earlier saves are rejected. New H saves retain CAP
through orbit, Escort, Attack, Return and Sleep/service without new raw pointers
lacking swizzle/detach handling. No INI key is added.

## Hook verification and changed files

New entry hooks were compared with TSpp and the original input.dat disassembly:

| Entry | Length / displaced instructions | H scope / return |
|---|---|---|
| Aircraft Mission_Guard 0x0040DD10 | 5: sub esp,0Ch; push ebx; push esi | Supported controlled FixedWing calls Mission_CAP, EAX delay, leaf ret |
| Aircraft Mission_Guard_Area 0x0040E0A0 | 10: push esi; mov esi,ecx; push edi; mov ecx,[esi+354h] | Same; leaf ret |
| Aircraft Active_Click_With(Object) 0x0040B740 | 8: mov eax,[esp+0Ch]; mov edx,[esp+8] | Existing GuardArea action, own Techno, supported FixedWing; ordinary Player_Assign_Mission; true with ret 12 |
| Aircraft Active_Click_With(Cell) 0x0040B690 | 5: push ebp; mov ebp,[esp+10h] | Existing GuardArea cell action only; same ordinary event; true with ret 12 |

All displaced sequences are complete, branch-free and non-relative. Other
aircraft/actions return zero and replay original instructions unchanged.
The existing synchronized event hook **0x004948A5**, length 6 (cmp eax,3;
push eax; mov ecx,edi), is extended without changing its address or displaced
sequence. ESI is the event, EDI the techno, EAX the accepted mission.
The existing Guard hotkey hook **0x004E95C2** only gains the FixedWing eligibility
exception. The existing Aircraft AI entry **0x004090C0** gains CAP lifecycle
maintenance after No_Dock_AI. Dock and attack hook addresses are unchanged.
The existing destination entry **0x0040E1B0** and Idle hook **0x0040B35A** retain
their addresses/lengths and call the now CAP-aware destination/Idle helpers.
The existing service-completion helper called by hooks **0x00432184** and
**0x00431DAB** gains only the CAP handoff described above; those hook addresses,
return targets and repair/reload logic are unchanged.
