# AF-0005D3c1 - normal Aircraft MultiDock

Implementation baseline: `de12f27cad54636a795fc5fcfd7d3209988c5b58`.
Closeout status (2026-11-01): the user manually built and runtime-confirmed legacy
and modern Single-Dock, two- and four-dock operation, parallel reload and save/load
with active service timers. The reload-entry correction is runtime-confirmed in
those scenarios. The exact evidence and remaining checks are separated below;
this does not establish that the entire test matrix passed. No build, automated
test or runtime test was performed by Codex. Save basis remains 0x190000.

## Scope and public configuration

Only ordinary Aircraft and pure aircraft factories with `Helipad=yes` and
`UnitReload=yes` are supported. Native and CustomFoundation masks are supported.
UnitRepair, ground/infantry service, refinery/weeder, mixed factory/service roles,
Carryall extensions, external dock points, platforms, bridges/cliffs, taxiing,
parking systems, queues and corridor scheduling are excluded. FixedWing MultiDock
is explicitly deferred to D3c2. An AircraftType still needs the BuildingType in
its own `Dock=` list; MultiDock creates no compatibility relationships.

### Single-Dock: unified spelling and legacy compatibility

For an absent `NumberOfDocks` or `NumberOfDocks=1`, Art `DockingCell0=X,Y` is
the modern spelling of the existing D3 Single-Dock override. `CustomDockCell=X,Y`
remains the compatible legacy spelling. Both use D3's existing eligibility:
a valid CustomFoundation on a pure Aircraft factory/Helipad/UnitReload building.
This parsing update does not extend the Single-Dock override to native foundations
or change the existing Single-Dock FixedWing compatibility.

Modern Single-Dock, Rules:

```ini
[MYAIRFIELD]
NumberOfDocks=1
```

Art (Image/GraphicName section):

```ini
[MYAIRFIELD]
DockingCell0=2,2
```

The explicit Rules count may also be omitted; effective count remains one.
Legacy Single-Dock, Art (with absent count or count=1):

```ini
[MYAIRFIELD]
CustomDockCell=2,2
```

| Art keys for a Single-Dock request | Effective result |
|---|---|
| Neither | Existing native/D3 center fallback. |
| CustomDockCell only | Existing D3 contract. |
| DockingCell0 only | Valid point is copied into the existing D3 Single-Dock fields. |
| Both, same valid point | One effective point; no conflict warning. |
| Both, different points | Developer reason=CONFLICTING_SINGLE_DOCK_KEYS; DockingCell0 is not adopted, and the legacy contract remains authoritative. |
| Invalid DockingCell0 | Developer rejection; valid legacy point, otherwise the existing center fallback under its original conditions. |

Both spellings use the same strict parser and occupied-cell validator: exactly
two decimal integers, within effective Width/Height and the occupied mask. Holes,
halo points, XYZ, floats, hex, suffix garbage, truncated strings and overflow are
rejected before Cell conversion. An invalid alias does not itself reject the
CustomFoundation; the original fallback safety requirements still apply. A present
legacy key retains its own validation/fallback behavior even if it is malformed;
a different modern value does not silently repair or replace it.

DockingCell1 and higher indices without MultiDock are unexpected. They produce
a Developer warning with reason=UNEXPECTED_CELL, including when NumberOfDocks is
omitted. They do not reject the Building/Foundation or prevent a valid DockingCell0,
legacy point or native fallback from supplying the one effective point. Noncanonical
DockingCell key names are also reported as unexpected.

Resolution happens in the existing complete-type/foundation finalizer rather than
deciding precedence during early Art parsing. Key presence and parsed coordinates
are local variables. An unsaved parser map remembers whether the last applicable
INI pass requested absent count/count=1; later passes omitting the type do not
overwrite this information. It is initialized/removed with the type extension and
is neither saved nor hashed. No persistent parser flags are added. A failed
NumberOfDocks>1 configuration retains the existing legacy-only Single-Dock fallback,
rather than reinterpreting its slot zero as a Single-Dock alias. Loaded games use
their saved effective D3 state and do not need this parser metadata.

The final point is stored only in CustomAircraftDockCellSet/CustomAircraftDockCell.
There is no Single-Dock slot or parallel geometry. Existing hooks, MultiContact,
reservation, production, landing, reload, cleanup and FixedWing logic are unchanged.
Save layout and basis 0x190000 are unchanged. Existing CRC code hashes this effective
D3 state, so equivalent legacy/modern spellings have the same canonical CRC input.

### MultiDock

Rules, BuildingType section:

```ini
[MYAIRFIELD]
Factory=AircraftType
Helipad=yes
UnitReload=yes
NumberOfDocks=4
```

Art, the BuildingType's Image/GraphicName section:

```ini
[MYAIRFIELD]
DockingCell0=1,1
DockingCell1=3,1
DockingCell2=1,3
DockingCell3=3,3
```

`DockingCell#` is an Aftermath cell API, not RA2/YR's `DockingOffset#`.
`DockingOffset#` and free XYZ offsets are not implemented.

`MAX_AIRCRAFT_DOCKS=16` is an Aftermath project limit for bounded state, swizzle,
CRC and iteration. It is not a native RA2/YR limit or a foundation limit.
Absent `NumberOfDocks`, or `NumberOfDocks=1`, selects the existing Single-Dock
path. MultiDock accepts counts 2..16. Counts are parsed as complete decimal
integers, without prefix acceptance or overflow.

Each of the N required, canonical keys must contain exactly two decimal integers.
Whitespace is allowed; floats, hex, a third component, suffix garbage, overflow,
missing keys and unexpected/out-of-count DockingCell indices are rejected.
All points must be unique, inside effective Width/Height, and present in the
effective Occupy_List. Custom masks use their actual cells, including holes;
native masks use the native list. There is no replacement-cell search or
automatic distribution.

World coordinate for relative `(X,Y)` and building anchor Cell `A`:

```text
world.X = (A.X + X) * 256 + 128
world.Y = (A.Y + Y) * 256 + 128
world.Z = Building.Get_Coord().Z
```

Any invalid MultiDock configuration resets only DockCount/Cells to the
Single-Dock defaults. Reasons include COUNT_INVALID, MISSING_CELL,
MALFORMED_CELL, UNEXPECTED_CELL, OUT_OF_RANGE, NOT_OCCUPIED, DUPLICATE_CELL and
ROLE_CONFLICT. Independently valid CustomFoundation data is retained.
Final role/reverse-reference validation runs after all TechnoTypes are read.
Parsing resets the bounded array on each applicable INI pass; it never appends.
There is no live migration of occupied pads to a new configuration.

The saved D3 fields `CustomAircraftDockCellSet` and `CustomAircraftDockCell`
remain separate. A valid MultiDock does not use CustomDockCell for geometry or
require its unused native-center fallback to be occupied. The optional legacy
field is still parsed separately. Invalid MultiDock falls back to the original
D3/native contract, including that contract's own eligibility requirements.
For a MultiDock request, CustomDockCell remains separate legacy/fallback data:
only DockingCell0..N-1 define MultiDock geometry, and the legacy key is not a
Single-Dock conflict. The modern Single-Dock alias described above applies only
to absent count/count=1 requests.

## State and contact architecture

BuildingTypeExtension adds POD only:

```cpp
int AircraftDockCount;               // default 1
Cell AircraftDockCells[16];          // default all (0,0)
```

BuildingExtension adds POD only:

```cpp
AircraftClass* AircraftDockVisitors[16]; // default null
int AircraftDockReloadTimers[16];        // default -1
bool AircraftDockFullReported;           // diagnostic suppression only
```

The timer is an absolute simulation Frame deadline: -1 means reserved/not yet
servicing, -2 means service completed, and nonnegative values are active deadlines.
No new AircraftExtension fields, heap containers or native RadioClass layout
changes are introduced.

```text
BuildingExtension.Visitors[0] --> Aircraft A -- Radio --> Building
BuildingExtension.Visitors[1] --> Aircraft B -- Radio --> Building
BuildingExtension.Visitors[2] --> null
BuildingExtension.Visitors[3] --> Aircraft C -- Radio --> Building
```

Array position is the slot identity. HELLO reserves the first null entry in
ascending order. An existing registration retains its index. Release writes
null at that index; no compaction, sorting, RNG or round-robin is used.
Aircraft-side HELLO goes through native RadioClass acceptance. The Building
counterpart is the extension array, not a temporarily switched native Radio
pointer. Member lookup and coordinate helpers do not allocate or reserve slots.

The native construction-yard contact remains a separate legacy exception while
the pad is under construction. Its non-Aircraft HELLO/TX/unlink follows the old
protocol. Aircraft acceptance is blocked until construction and that contact have
finished. Thus MultiDock does not break construction of its own Building.

The two BuildingClass TX vtable slots are adapted. Single-Dock always
delegates to native RadioClass. MultiDock TX uses an explicit visitor; an implicit
OVER_OUT releases all contacts for native Building Limbo. It never guesses a
visitor for another implicit message. Native construction contacts retain their
legacy dispatch. The patch uses Change_Virtual_Address for protected .rdata.

One AircraftClass TX-data vtable adapter handles a TS-specific idempotency issue:
native TX unconditionally emits OVER_OUT before HELLO. If the recipient is already
this Aircraft's registered MultiDock, the adapter forwards HELLO without that
pre-unlink, retaining the original index even when lower indices became free.
Native basic TX already forwards through TX-data. All other Aircraft TX calls,
including every Single-Dock/FixedWing call, delegate to native RadioClass. This
adds no AircraftExtension state and makes no global RadioClass change.

Building Receive_Message intercepts the dock protocol before the Single-Dock
handler: HELLO, OVER_OUT, CAN_LOAD, DOCKING, MOVE_HERE, IM_IN, TETHER,
UNTETHER and ON_DEPOT. Unrelated building messages retain the existing handler.

CAN_LOAD retains Aircraft RTTI, Dock[], alliance, active/finished/not-deconstructing,
IsOn, power and EMP checks, plus existing-or-free capacity. FixedWing and Carryall
requesters are rejected. Tether/untether echoes use the Aircraft's individual flag;
they never borrow another visitor or install one as Building.Radio.

MOVE_HERE's TS payload remains an AbstractClass pointer to the Building, not a
Coord pointer. Caller-specific adapters resolve that visitor's position.
IM_IN preserves native Sleep/service handoff; actual reload waits for touchdown
on that visitor's reserved point. TS ON_DEPOT remains cell/building based.

## Production, return and landing

Find_Docking_Bay keeps the TS owner/type/limbo/CAN_LOAD/distance search. Its existing
capacity hook consults the slot array for MultiDock and bypasses only the scalar
Radio gate. No YR PrimaryFactory ranking rule is ported.

Production tests existing-or-free capacity, reserves before pad Unlimbo and supplies
the selected point to the original Aircraft Unlimbo interface with its original
Pose_Dir and building Z. Failure releases that reservation and returns through
the existing native failure/ScenarioInit unwind. If native Unlimbo unexpectedly
loses the contact, it is restored; failure to restore rolls the object back to Limbo.

Full-pad handling retains TS's existing edge/nearby/rally/ion-storm branches.
The ion-storm Nearby branch does not acquire a phantom slot. FixedWing/Carryall
production cannot enter the MultiDock pad branch and uses the existing edge route.
There is still one production queue.

The parameterless Building Docking_Coord remains a legacy query and does not
select a MultiDock visitor. Explicit requester adapters cover production,
Foot's destination result, Fly's local landing result and Mission_Enter's local
landing correction. Fly accepts a cleared NavCom during final approach only when
the Aircraft still owns this Building contact and slot. Enemy/other destinations
are not redirected. Facing, Z processing, native status and +/-5-lepton nudge remain.

Aircraft Assign_Destination has an additional reciprocal-contact adapter. Without
it, a null Building.Radio could trigger another HELLO/DOCKING cycle even though
the Aircraft already owns an extension slot.

## Service and lifecycle

The MultiDock-only Mission_Repair entry iterates visitors in slot order. It does
not run the native single-visitor body for an active MultiDock type. The native
body, including ReloadRate hooks 0x43266C and 0x4325FE, remains the Single-Dock path.

A visitor must be landed, tethered, on its own point within the native final
nudge tolerance, and on a Cell whose Cell_Building is this pad. An entering or
airborne visitor is not reloaded. Initial service queries NEED_TO_MOVE/PREPARED,
queues Sleep itself and starts the first deadline; it does not require Sleep to
have survived Mission_Enter. Subsequent RELOAD steps require the Sleep mission.
Delay uses its AircraftType Get_ReloadRate() * TICKS_PER_MINUTE (900 simulation
frames per minute), with a minimum scheduling delay of one frame. Subsequent
arrivals never reset another slot's deadline. Power/EMP gate servicing without
freeing occupied/reserved slots.

PREPARED, targeted RELOAD, Guard, Enter_Idle_Mode(false,true) and entry_2C8 preserve
the native UnitReload completion sequence per visitor. Ammo is never directly
incremented by the adapter. All radio commands use TS enums: their numeric values
are not interchangeable with the later YR enum.

OVER_OUT releases only its sender. The adapter handles native Aircraft TX clearing
Aircraft.Radio before the Building receives OVER_OUT: this visitor is still
untethered. Reentrant radio echoes see an already-cleared slot. A newer different
Aircraft radio peer is never disturbed.
Visitor-initiated OVER_OUT preserves its queued mission and destination; only
forced cleanup wakes a visitor stranded in Sleep/Enter. Native Assign_Mission
(0x559490) writes the queued mission, so normal departure must not inject Guard.

Detach clears matching array entries without callbacks into a dying object.
Maintenance removes inactive/limbo/dead/disconnected/incompatible stale contacts.
It also supplies native Mission_Guard's scalar-contact service wake-up for a
registered sleeping visitor; it never resets another visitor's timer.
Building Limbo's implicit OVER_OUT and extension destruction release contacts;
the Building does not own or delete Aircraft. Forced removal wakes parked Sleep
visitors to Guard. OwnerChange conservatively unlinks all
visitors before the native owner change. Power-off/EMP alone never clear slots.

BibShape and IsBibbed eligibility retain D3b's rendering/role policy. No selection,
ground occupation or general pathfinding replacement is introduced.

### Reload entry correction (runtime-confirmed for two/four docks and active save/load)

The native TS Single-Dock sequence was checked against the original binary and
the existing Vinifera source:

| Step | Native TS / existing Single-Dock contract |
|---|---|
| Aircraft arrival | Mission_Enter sends IM_IN=21 at 0x40D5AC..0x40D5C7. |
| Building RX | Existing source handler marks IsReadyToCommence, queues MISSION_REPAIR and queues visitor Sleep, then returns ROGER. |
| Aircraft continuation | After ROGER, the ordinary non-transport branch queues Guard=5 at 0x40D6D3..0x40D6D9, replacing the previously queued Sleep. |
| Queue semantics | Assign_Mission at 0x559490 writes MissionQueue. Commence at 0x559450 installs it as CurrentMission and resets Status/mission timer. Building Ready_To_Commence at 0x438230 reads IsReadyToCommence, without a Radio gate. |
| Service initialization | Mission_Repair at 0x432620 checks NEED_TO_MOVE=19 and PREPARED=27. A visitor needing reload returns ROGER/NEGATIVE. The Building enters ACTIVE and queues visitor Sleep at 0x432659..0x43265F, then returns the initial reload delay. |
| Reload | Native service sends RELOAD=29 at 0x43259D..0x4325AA. Aircraft source RX forwards it to Foot/Techno under its existing conditions; the native Techno handler increments Ammo and returns ROGER, or NEGATIVE at maximum. |
| Completion | PREPARED/full-ammo or native reload completion follows Guard, Enter_Idle_Mode(false,true), entry_2C8 and ordinary unlink/takeoff behavior. |

The earlier MultiDock helper incorrectly required visitor Mission==SLEEP before
initializing a -1 deadline. Successful IM_IN does not guarantee that state: native
Mission_Enter replaces its queued Sleep with Guard. The helper never performed the
native service-side Sleep assignment, leaving the deadline at -1 and never sending
RELOAD. Missing SERVICE_ENTER/RELOAD events are consistent with this blocker;
their absence alone does not establish whether IM_IN or the Mission_Repair hook
was reached in the user's historical run.
The Single-Dock CFPAD SERVICE_ENTER log is emitted in IM_IN, whereas the old
MultiDock SERVICE_ENTER log was emitted only when initializing the deadline;
those two log names therefore described different stages.

The correction is confined to MultiDock service initialization: a landed registered
visitor with a -1 deadline must acknowledge NEED_TO_MOVE; after the PREPARED check,
service queues Sleep and starts that visitor's deadline. Existing active deadlines
still require Sleep before RELOAD. No global per-frame forcing of Mission_Repair,
new hook, slot change, direct Ammo modification or persisted field is introduced.
The existing IM_IN acceptance, targeted tether, Building repair queue and Single-Dock
handlers are retained.

ReloadRate units are unchanged. Existing Vinifera Get_Aircraft_Reload_Time used by
0x43266C and 0x4325FE returns AircraftType Get_ReloadRate()*TICKS_PER_MINUTE.
TS defines this as 15*60=900 simulation ticks, matching the Frame-based deadline.
This bug does not require a time-unit correction.

Developer-only transition events are SERVICE_IM_IN, SERVICE_START, SERVICE_RELOAD
and SERVICE_COMPLETE. They report Building/slot/Aircraft IDs, Ammo/max/before,
current and queued missions, statuses, BState, deadline, radio/tether/height,
Building-cell and slot-cell matches, NavCom state, reason and reply. RELOAD records
the actual native reply and before/after Ammo. There are no per-frame wait/reject
logs, suppression fields or new diagnostic save state.

The subsequent user retest confirmed the correction with NumberOfDocks=2 and 4,
including actual stepwise Ammo increases, independent slot timers and completion
for every Aircraft. A four-dock save created during active reload also resumed
service to full ammunition after load. These results are detailed below. The
DeveloperMode transition logs remain unchanged for diagnosis; no further source
or logging change was made during closeout.

## Persistence and framesync

Save basis changes once from 0x180000 to 0x190000. New games/saves are required;
the existing version calculation also includes extension sizes.

The existing raw extension blob stores all bounded POD arrays. Default constructors
initialize them; NoInit constructors do not overwrite saved values. Every non-null
visitor pointer is individually registered for swizzling. Pre-swizzle Load checks
only owned scalar/array data, not ThisPtr, Class, RTTI or peer pointers.

After SwizzleManager.Reset processes remaps, and before Post_Load_Game, the loader
validates effective type configuration and all cyclic associations. Membership in
native object arrays is checked before dereferencing mapped visitor pointers.
Wrong types, duplicate slots/across-building claims, out-of-count claims and
structural radio corruption fail the load. Correctable inactive/disconnected stale
claims are cleared. Construction/handoff pads may retain a reciprocal native CY
link with no Aircraft slot claims; mixed CY/Aircraft claims fail validation.
The global swizzler's existing missing-ID error policy is unchanged.

Type CRC includes its MultiDock domain, active marker, count, each index and X/Y.
The cached framesync configuration includes native-foundation MultiDock types too.
Building CRC includes each index, empty/nonempty marker, stable Aircraft HeapID
and its deadline, including empty slots. No pointer address is hashed. Diagnostic
suppression is excluded from gameplay CRC.
