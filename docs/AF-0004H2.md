# AF-0004H2 — Escort CAP and bidirectional attack diagnostics

This increment adds observations, not a gameplay fix. H/H1's production, G,
Move cancellation and full reload/CAP resume passed the user's local runtime
checks. H2 itself has not been built or tested. The two reported failures still
need the new runtime trace; static analysis alone does not identify the actual
clicked payload, escort position or map boundary of that test.

## Enabling and reading the trace

Use Vinifera Developer Mode for a RelWithDebInfo/release build. Debug builds
also enable the existing DEV_DEBUG_INFO mechanism. All new lines use `[FWCAP]`;
the entire `[FWDOCK]` implementation and its calls remain unchanged.

Each line includes simulation Frame, Aircraft UniqueID (`AbstractClass::ID`),
HeapID, event, CurrentMission, MissionQueue, Status, Ammo, aircraft coordinate
and raw facing, CAPMode/CAPMission/CAPAnchor/CAPEscort, CAPRearming/CAPOwner,
NavCom, ArchiveTarget, TarCom and
the actual Fly DestinationCoord/HeadToCoord. References distinguish CELL,
TECHNO_OBJECT, OTHER and NULL, with pointer, RTTI, UniqueID, HeapID, owner and
current coordinate when present. CAPMode numbers: None=0, Static=1, Escort=2.
Attack Status numbers: INITIAL=0, INGRESS=1, ATTACK_PASS=2, EGRESS=3, REGROUP=4.
Guard Status 0 is initial and 1–4 identify corners 0–3; do not confuse the two
mission-local interpretations.

No per-frame output is added. Escort snapshots compare identity, ownership,
liveness, mission/status, parent context and native target pointers; changing
coordinates alone do not trigger them. First AI/flight observations, command,
Commence, takeoff completion, reached corners, resume and Detach are explicit
transition observations. Actual geometry is logged once when it is selected.

The diagnostic maps, sequence Frame and run counts are transient, outside all
extensions, serialization and CRC. They are cleared on load (before reading
the Aircraft extension), frame rollback, identity/pointer replacement, and
Developer Mode being disabled. Diagnostic reading is suppressed while loading,
before pointer swizzling completes. A trace started halfway through an existing
Attack does not reconstruct its earlier sequence/run history: use a fresh G or
Escort command for the complete run comparison.

## Object Guard command and real event payload

The source/binary path is:

1. CTRL+ALT is force attack plus force move. Native Techno/Foot What_Action
   selects ACTION_GUARD_AREA. Vinifera Aircraft What_Action delegates to that
   path; it does not turn GuardArea into a different aircraft action.
2. Aircraft Active_Click_With(Object) entry **0x0040B740**, H hook length 8,
   reads action at stack +4 and the Object pointer at +8. Its existing supported
   FixedWing, movement-permission and own-House gates are unchanged. H2 observes
   `COMMAND_QUEUED source=UI_OBJECT_GUARD_AREA` immediately before the existing
   `Player_Assign_Mission(MISSION_GUARD_AREA, object, nullptr)` call.
   The cell overload at **0x0040B690**, length 5, logs
   `source=UI_CELL_GUARD_AREA` with the actual CellClass reference. G uses the
   existing Guard command path **0x004E95C2**, sends the current cell directly,
   and does not traverse these mouse-click hooks.
3. Aircraft Player_Assign_Mission **0x0040B760** wraps the actual Target and
   Destination in TargetClass and calls Queue_Mission (**0x005B0FC0**).
   It does not search for a unit on a cell. The event contains **Whom, Mission,
   Target and Destination**. Target/Destination are typed `xTargetClass`
   references (Kind + Value), not just an untyped XY coordinate. MEGAMISSION_F
   has the same prefix, followed by formation Speed/MaxSpeed.
4. At the accepted synchronized event hook **0x004948A5**, length 6, EDI is the
   techno, ESI the event, EAX the new mission; the original binary loads that
   mission from `[esi+12h]` at **0x004948A0**. H2 logs COMMAND_RECEIVED immediately
   before the unchanged FixedWing::Command call. It reads the real event's
   target AND destination, their raw Kind/Value and resolved references. It
   explicitly labels a cell-only Target `CELL_ONLY_NO_OBJECT_RECONSTRUCTION`.
   It never guesses an object from a cell. Frame, event owner and payload
   mission also allow a register/payload mismatch to be noticed.
5. FixedWing::Command still passes **event.Target**, not event.Destination,
   to Begin_CAP. Destination is observed, not substituted. Begin_CAP first
   clears the old context. A `dynamic_cast<TechnoClass*>` target other than self
   becomes Escort only if active, not limbo, alive and the same House. It writes
   CAPMode=Escort and CAPEscort=that exact pointer. A non-self Techno failing
   those checks returns false with the context cleared; it does not fall back
   to Static. Only the null-cast/self branch stores a distinct cell's center,
   or the aircraft's position
   for its current cell/null/self. CAPMission and original owner are stored.
   CAP_SET_STATIC/ESCORT records the result and the actual Begin_CAP argument.
6. The event then natively assigns the mission and clears suspended target/
   navigation fields. Its GuardArea branch **0x004948E5–0x00494926** clears
   TarCom, calls Assign_Destination(event.Target), then assigns ArchiveTarget
   from that same Target using **0x00639130**. H1's destination helper consumes
   the already-created context and commences the queued GuardArea. Its snapshot
   is before the native archive assignment; the next AI snapshot captures that
   subsequent native change.
7. CAP_AI validates existing context and service state. CAP_Flight executes it;
   neither creates missing context after H1. First CAP_AI, first CAP_Flight,
   after-command, after-Commence and takeoff-complete snapshots identify exactly
   when the stored reference or native navigation state changes.

Expected values for the intended object case are therefore:

| Step | Mission / command data | Native target fields | CAP context |
|---|---|---|---|
| UI object click | new GuardArea; Target=own Techno; Destination=null | Still previous order | Still previous order |
| accepted event / Command entrance | same typed object Target and null Destination | Snapshot of old CurrentMission/queue/NavCom/ArchiveTarget/TarCom | Previous CAPMode |
| Begin_CAP / Command complete | GuardArea accepted | Native event assignment still follows | Escort, CAPMission=GuardArea, CAPEscort=object, CAPAnchor=COORD_NONE |
| destination/Commence | queued GuardArea becomes current | CAP destination helper clears NavCom/Fly goal; native event clears TarCom and then writes ArchiveTarget=object | Same Escort pointer |
| first flight leg | GuardArea | NavCom=safe geometry CELL; TarCom=null; ArchiveTarget may still name object | Escort center read from CAPEscort; CAPAnchor remains unused |
| autoattack / resume | Attack then saved GuardArea | Enemy TarCom; E meanings for NavCom/Fly fields; later CAP geometry cell | Original Escort remains across missions |

These are the static expected semantics, not a claim that the reported failing
run had that payload. Compare COMMAND_QUEUED with COMMAND_RECEIVED first:
object -> cell means information changed upstream of Begin_CAP; object ->
CAP_SET_STATIC means the actual Begin_CAP cast/branch needs investigation;
CAP_SET_ESCORT followed by pointer loss means examine the lifetime snapshots;
an unchanged pointer with a distant usedCenter points to geometry/anchor choice.
No such case is repaired in H2.

## Escort lifetime, native fields and CAP center

The complete existing CAPEscort write set is constructor initialization,
Begin_CAP's Escort assignment, Cancel_CAP's clearing, On_Detach's clearing,
and raw save load plus pointer swizzle. H2 changes none of those writes.
On_Detach still calls its parent and clears the pointer; only a snapshot after
that existing clear is added, with the previously observed object identity.

CAP_Valid rejects null/self/inactive/limbo/dead/foreign-House escort and aircraft
ownership changes. ESCORT_INVALID reports the existing rejection reason;
ESCORT_ABORT_RTB is emitted only at an existing invalid-context return path.
Unsupported RTTI can be identified as a diagnostic observation; H2 adds no
new type rejection or validity rule. Detach reports pointer loss first, and the
following AI decides the existing cancellation/Return transition.

Native fields are deliberately separate from CAPEscort:

- Event GuardArea writes ArchiveTarget=command Target after destination
  assignment; Cancel_CAP clears ArchiveTarget and suspended Guard references.
- CAP_Flight initially clears TarCom and releases dock radio contact. CAP_Leg
  writes NavCom to the safe geometry anchor cell and Fly goal to a corner.
- The existing mission/command handoff may clear NavCom/Fly goals. Native threat
  acquisition writes TarCom; the CAP-to-Attack handoff clears NavCom/Fly goals.
- E Start_Ingress/Start_Pass uses NavCom=TarCom, and stores target plane,
  ingress/exit/staging in Fly fields. Clear_Attack clears TarCom/NavCom/goals.
- Return, holding, approach, landing and service retain their dock/geometry
  meanings for NavCom/radio/Fly fields. None assigns CAPEscort from them.
- Resume_CAP clears attack fields and commences the saved CAP mission;
  it preserves CAPEscort. The next CAP_Leg samples its latest Center_Coord.

Static center is CAPAnchor. Escort center is **CAPEscort->Center_Coord()** in
CAP_Leg, native acquisition and CAP's target leash. Only the leg-selection call
updates the movement goal: initial entry, resume, or reached-corner Arrived.
Escort motion during a leg does not retarget DestinationCoord every frame.

Orbit_Points cell-quantizes the requested center. Holding_Points tries half-size
rectangles (6,4), (4,3), (3,2), (2,2) cells with corners (-w,-h), (+w,-h),
(+w,+h), (-w,+h), edge segments and two-cell corner clearance. If none fits,
Orbit_Points searches expanding cell rings, row-major within a ring, relocating
the whole rectangle. No corner is clamped. Initial choice is the nearest corner;
subsequent choice is cyclic. A distant safe anchor is therefore possible even
with an intact Escort pointer. Whether that occurred in the failing test is
unknown until the log shows requestedCenter versus usedCenter.

CAP_GEOMETRY logs the exact selected points and their validity, requested and
used centers, requested corner (-1 means initial nearest choice), chosen corner
and actual aircraft position. ESCORT_CENTER_UPDATE adds current Escort position,
previous observed used center, new requested/used center and next movement goal.
UNOBSERVED means no prior diagnostic center, not a gameplay center reset.

## Existing automatic attack state machine

Target acquisition is unchanged: virtual Target_Something_Nearby
**0x00637450**, Vinifera's existing replacement, and native Greatest_Threat
(Foot **0x004A4DC0**, Techno **0x0062DC80**). Guard uses THREAT_RANGE,
GuardArea THREAT_AREA around the actual CAP center. H2 observes only a target
which already passed the existing CAP attack predicates; it adds no enemy scan.

AUTO_TARGET_ACQUIRED records corner, movement goal, heading, enemy identity,
distance and Ammo before the existing Attack assignment. AUTO_ATTACK_BEGIN has
two stages: CAP_TO_E (geometry not committed yet) and PASS_COMMITTED (actual
Start_Pass succeeded). Sequence is the acquisition Frame; run counts only
committed armed passes, not an initial straight breakoff.

Let T be the current target, R the existing weapon range, U=Turn_Room, and F a
forward direction. The actual unmodified E code does the following:

| Phase / boundary | Existing geometry and decision |
|---|---|
| INITIAL | If distance < R+4U, Break_Off first gains room. Otherwise choose Direction(aircraft,T) and Start_Ingress. |
| Start_Ingress | I=T-F*(R+4U). Require current->I and I->T valid segments. Store Destination=I, HeadTo=T, Status=INGRESS. |
| Ingress waypoint reached | Goal becomes current T, so Destination==HeadTo; SecondaryFacing.Desired freezes the alignment heading. |
| Alignment | Before crossing the frozen target plane, require current heading within the existing 1024 raw-unit tolerance of the line, also for the moving current target. Otherwise the existing plane-crossing/heading rejection breaks off. |
| Start_Pass | Exit=T+F*L, L=max(4U,R+2U). Validate current->Exit. Freeze HeadTo=T and Destination=Exit; Status=ATTACK_PASS. |
| ATTACK_PASS | Only this phase calls Can_Fire/Fire_At. Target plane is passed when Along(position,HeadTo,Destination-HeadTo)>=0, observed by Attack_AI or movement Attack_Arrived. |
| Break_Off / EGRESS | Keep the committed axis; optionally extend exit once for target along-track movement. No firing. Non-pass breakoff can first create a straight safe exit from the aircraft position; this is not a successful armed pass. |
| EGRESS complete | Along(position,Exit,Exit-HeadTo)>=0. If target/ammo/range permit, Start_Regroup; otherwise End_Attack. |
| Start_Regroup | Outward=Direction(old HeadTo,old Exit). Next I=T+Outward*(R+4U), beyond=I+Outward*2U, staging=beyond+(Outward+E/W)*4U. Try E side then W; require current->staging, staging->I, I->T. Store Destination=staging and HeadTo=I, Status=REGROUP. |
| REGROUP waypoint reached | Start_Ingress(Direction(saved HeadTo,current T)). For stationary T this direction is opposite the previous outward/pass direction. |
| End_Attack | Existing H context resumes CAP with ammo, or retains CAPRearming through normal RTB/full reload. The next actual CAP corner/goal is logged by AUTO_ATTACK_RESUME_CAP. |

The pass axis is the saved Fly vector, not a new persistent aircraft field.
**The source does not always select the original direction**: stationary-target
Regroup explicitly prepares the opposite side. It also does not test both
ingress directions and choose the best; only regroup's lateral E/W staging has
a two-candidate fallback. A possible geometric counter approach is not armed
just because it passes near the enemy: EGRESS and REGROUP cannot fire. It must
successfully enter a new aligned ATTACK_PASS.

ATTACK_ALIGNMENT_REJECTED records the frozen alignment heading and target plane
before Break_Off overwrites them. It distinguishes reaching the plane before
alignment from a current target outside heading tolerance. ATTACK_PASS_REJECTED
records the actual attempted exit and failed segment. ATTACK_BREAKOFF records
the old phase and whether this was a straight-exit-only path. These observations
are essential when only one of several apparent fly-bys is really ATTACK_PASS.

## Counter ingress and map-edge probes

COUNTER_INGRESS_AVAILABLE is a conservative movement observation, once per
observed committed pass: the previous EGRESS endpoint was reached, aircraft is
on the opposite side of the current target along the last pass axis, actual XY
movement points against that axis and toward a target in front, its forward
projection is at least 90% of squared target distance and its projected ray miss
is <= ARRIVAL (half a cell). It logs the actual current mission/phase/TarCom,
CAP context and Ammo. It does not start a pass, alter heading or authorize fire.
Its absence is not proof of geometric impossibility: the detector is deliberately
conservative, and a new committed pass resets its comparison axis.

NEXT_INGRESS_SELECTED records the actual direction argument, ingress point,
previous phase/direction, accepted/rejected result and original validation
segments. For Regroup its reason is saved-regroup-ingress -> current target;
for INITIAL it is aircraft -> target. The log makes clear that gameplay did
not test an opposite ingress candidate at that selection.

ATTACK_DIRECTION_PROBE runs only at an ingress attempt or committed pass.
It calculates local theoretical A=current requested/committed direction and
B=its exact opposite using the same E distances/formulas above. Labels are
relative to that attempt; compare **axisRaw**, Sequence and run across attempts,
not the letter alone. Each direction includes:

- Ingress, exit, next opposite ingress, both E/W turn-out staging coordinates.
- Cell coordinates, In_Radar, In_Local_Radar, allocated-array margin and
  Valid_Point for every endpoint; negative-coordinate probes are guarded.
- Ingress->T, T->exit, exit->each staging, staging->next ingress and next
  ingress->T Valid_Segment results, plus current aircraft->candidate ingress.
- chainValid for the theoretical endpoint/segment chain, never read by gameplay.

This is not a second attack controller. Actual committed geometry is logged
from existing function locals/Fly fields, with not-yet-selected points explicitly
marked. The probes neither call Start_Ingress/Start_Regroup nor assign their
results. As with E's existing map checks, segment validity does not simulate a
wide curved turn or guarantee Heading_OK on arrival.

At a bottom-edge target, ingress may fit while exit or either turn-out side
does not. Compare rejected actual segment geometry with A/B probes. If only one
theoretical chain fits, that supports a map restriction; if both fit, inspect
actual regroup/ingress/alignment transitions. Possible A->A explanations still
requiring runtime evidence include failed opposite alignment, a rejected next
segment, initial close-range breakoff, or attack ending and CAP reacquisition
from a repeated nearest-corner geometry. H2 implements none of the later A->B
gameplay changes. The eventual goal remains separate armed passes with safe
egress and broad turns, with same-side repetition allowed when the opposite
geometry is unavailable.

## Event catalogue

| Event | Observation boundary |
|---|---|
| COMMAND_QUEUED | Actual object/cell mouse GuardArea argument before queuing |
| COMMAND_RECEIVED | Accepted synchronized event immediately before Command |
| CAP_SET_STATIC / CAP_SET_ESCORT | Actual Begin_CAP result |
| ESCORT_STATE | First AI/flight and lifecycle/native-field transitions |
| ESCORT_CENTER_UPDATE | Actual new corner/center selection |
| CAP_GEOMETRY | Selected rectangle, or failure with no committed corners |
| ESCORT_INVALID | Existing invalidity or Detach pointer-loss reason |
| ESCORT_ABORT_RTB | Existing invalid-context return boundary |
| AUTO_TARGET_ACQUIRED | Accepted existing native acquisition |
| AUTO_ATTACK_BEGIN | CAP_TO_E / actual PASS_COMMITTED |
| ATTACK_TARGET_PASSED | Existing target-plane crossing, once per pass |
| ATTACK_EGRESS_COMPLETE | Existing egress endpoint crossing |
| ATTACK_REGROUP | Each actual lateral staging candidate, rejected or selected |
| COUNTER_INGRESS_AVAILABLE | Once-per-pass conservative movement predicate |
| NEXT_INGRESS_SELECTED | Actual new ingress attempt and outcome |
| ATTACK_DIRECTION_PROBE | Local A/B endpoint and segment probes |
| AUTO_ATTACK_RESUME_CAP | First actual new CAP corner after resume |
| ATTACK_BREAKOFF | Transition to EGRESS, including non-armed straight exit |
| ATTACK_PASS_REJECTED | Actual pass-exit segment rejection |
| ATTACK_ALIGNMENT_REJECTED | Existing alignment failure before geometry changes |

Snapshots include current coordinates on each line, but movement alone is not
a logging trigger. Target-plane detection changes phase immediately, preventing
duplicate pass messages. Regroup candidates and A/B probes are per transition,
not repeated each frame. The counter predicate is evaluated on movement samples
without output until first satisfied. Pointer/ID keys are diagnostic identity,
not simulation references for acquiring enemies.

## User runtime plan — not executed by Codex

Use a fresh explicit command with Developer Mode active and retain full `[FWCAP]`
lines, rather than only the event names. Keep aircraft ID and acquisition Frame
when comparing sequences.

| Test | Action | Required comparison |
|---|---|---|
| A — static control | Full FixedWing at dock; G | COMMAND_RECEIVED cell-only, CAP_SET_STATIC, CAP_GEOMETRY; no Escort context |
| B — Escort | CTRL+ALT own stationary unit from dock | UI_OBJECT argument vs event Target/Destination; CAP_SET_ESCORT or STATIC; ESCORT_STATE; first CAP_GEOMETRY |
| C — moving Escort | Move that unit significantly; wait several CAP corners | Same CAPEscort UID/owner; ESCORT_CENTER_UPDATE follows current object; requested/used centers reveal relocation; current leg stays fixed |
| D — bottom map edge | Static CAP; robust target at prior edge position; observe >=2 passes | Acquired sequence, PASS_COMMITTED run 1/2, actual pass/egress/regroup, NEXT_INGRESS, A/B probes, alignment rejection and counter event if observed |
| E — map center | Same aircraft/weapon/robust target, well inside map; >=2 passes | Compare raw axes and rejected segments with D. Both probe chains valid plus rejected opposite alignment points toward state/turn handling rather than a proven map exclusion. |

If B sets Escort correctly and later loses it, retain the first Detach/invalid/
clear snapshot. If Escort remains intact but usedCenter is distant, retain the
exact rectangle. If D/E show EGRESS/REGROUP with COUNTER_INGRESS_AVAILABLE, retain
that phase and the next ingress outcome. A successfully committed opposite pass
is stronger evidence than a theoretical valid probe. No conclusion about the
reported map's actual A/B validity is claimed without these logs.

## Scope and validation

No gameplay assignment, condition, mission timer, RNG call, enemy search, radio
message or movement command is added by the diagnostic helpers. CAPMode,
CAPMission, CAPAnchor, CAPEscort, CAPRearming, CAPOwner, native attack phases,
acquisition, Ammo/reload, Move/Stop/Return, holding/search/reservation, G2 approach
and G survival logic keep their existing decisions. EGRESS/REGROUP remain unarmed.
Existing branches only receive observational calls; public diagnostic methods
are void and do not supply gameplay outcomes. No hook address/length changes.
No persistent fields; save basis remains **0x140000**.
