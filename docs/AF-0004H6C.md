# AF-0004H6C — Larger FixedWing CAP / holding geometry

The user confirmed H6B at runtime: Static CAP (G), Escort CAP, full native TS
Mission_Attack / Fly autoattacks, CAP resume after attack and following the
selected escort vehicle all work. This is user-supplied H6B evidence. Codex
has not built or runtime-tested H6C.

H6C changes only the preferred dimensions of the existing four-point holding
route. The H6B attack architecture, target acquisition, movement controllers,
takeoff, landing, docking and service logic are unchanged.

## Dimensions and shared construction

Previously, `Holding_Points` in `src/extensions/aircraft/fixedwing.cpp` defined
the preferred half-size as the first entry `{6, 4}` in its local `sizes` array,
then multiplied both entries by `CELL_LEPTON` (256).

The preferred dimensions are now defined centrally in that file as
`HOLDING_HALF_WIDTH = 12 * CELL_LEPTON` and
`HOLDING_HALF_HEIGHT = 8 * CELL_LEPTON`. The `sizes` array now stores Leptons
directly; the smaller fallback dimensions retain their previous values.

| Dimension | Before | H6C |
| --- | --- | --- |
| X half-width | 1536 Leptons / 6 cells | 3072 Leptons / 12 cells |
| Y half-height | 1024 Leptons / 4 cells | 2048 Leptons / 8 cells |
| Full preferred box | 12 x 8 cells | 24 x 16 cells |

Corner order is unchanged:

```text
0: center + (-halfWidth, -halfHeight)
1: center + (+halfWidth, -halfHeight)
2: center + (+halfWidth, +halfHeight)
3: center + (-halfWidth, +halfHeight)
then 0 again
```

For a used center `(25728, 29312)`, the preferred corners become
`(22656, 27264)`, `(28800, 27264)`, `(28800, 31360)`, `(22656, 31360)`.
Existing cell-center normalization and boundary fallbacks still apply.

Static CAP and Escort share `CAP_Leg -> Orbit_Points -> Holding_Points`:

- Static CAP supplies the saved `CAPAnchor` as its requested center.
- Escort supplies the current `CAPEscort->Center_Coord()` whenever the
  existing leg-selection logic samples it. Escort is still sampled on corner
  arrival; no timer, movement threshold or frozen center was introduced.
- `Resume_CAP` still restores `CAP_INITIAL`; the next `CAP_Flight` selects a
  leg through the same helpers. Post-attack and post-service CAP therefore use
  the enlarged preferred box automatically, including the current escort
  position.
- Dock-search holding also uses `Orbit_Points` / `Holding_Points`, so it shares
  the enlarged preferred route. Dock search, approach geometry, reservation,
  radio, landing, reload and no-dock timeout behavior were not changed.

Initial nearest-corner selection, subsequent `0 -> 1 -> 2 -> 3 -> 0`
progression, arrival handling and natural aircraft steering are unchanged.
There are still four points, with no new orbit algorithm or flight states.

## Existing boundary handling and failure path

`Holding_Points` validates the entire rectangle, not isolated corners. Every
leg must pass `Valid_Segment`, and every corner must retain the existing
two-cell turning-clearance checks through `Valid_Point`. `Valid_Point`
continues to require nonnegative coordinates, outer `In_Radar` and
`In_Local_Radar`.

At the requested, cell-normalized center, the preferred half-size is tried
first. If invalid, the existing smaller half-sizes remain, in this order:
`4 x 3`, `3 x 2`, `2 x 2` cells. Thus 24 x 16 is the preferred full box; near
boundaries a smaller existing fallback can still be selected.

If none fit there, `Orbit_Points` retains its expanding cell-ring search and
row-major tie breaking to relocate the whole rectangle. Individual corners
are never clamped. The saved Static `CAPAnchor` is not overwritten by this
temporary geometry anchor, and Escort continues to supply its current center.

If no supported rectangle fits anywhere, `Orbit_Points` returns false.
`CAP_Leg` logs the existing `corners=NOT_COMMITTED` rejection and returns
without installing invalid navigation. Existing callers cancel CAP and take
the existing Return path. `Start_Holding` likewise returns false without
committing an invalid anchor/goal; the existing Enter dock-search path remains
in place. No new failure handling was needed: the smallest supported
rectangles and all existing fallback choices remain available.

`Native_Flight_Point` and `Takeoff_Movement_Coord` are unchanged. Outer
`In_Radar` is not expanded, array allocation is not treated as flight
permission, and no new edge controller is introduced. Existing
`CAP_GEOMETRY` / `ESCORT_CENTER_UPDATE` logging remains unchanged and displays
the actual selected corners, including any smaller or relocated rectangle.

## Scope and persistence

Holding route dimensions do not change `Threat_Range`,
`Target_Something_Nearby`, `GuardRange`, CAP target acceptance or weapon range.
The aircraft now visits different positions along its route, but the target
search code and its configured ranges are unchanged.

H6B's native Attack handoff, AttackControl values, full native Fly movement,
weapon/ammo behavior, CAP-to-Attack, Attack-to-CAP and Attack-to-RTB paths are
untouched. No custom attack planner was restored. Takeoff climb, altitude and
movement are unchanged; CAP simply supplies the farther holding goal.
Aircraft without `FixedWing=yes` retain their existing paths.

No INI field, persistent member, pointer, enum value, serialization or raw
extension layout was added or changed. The actual save basis in
`src/extensions/extension.cpp` remains **0x150000**. No save-basis bump is
required for these constant dimensions.
