# AF-0004A implementation status

Historical AF-0004A report. The subsequent flight implementation and semantic
save-version boundary are documented in [AF-0004C](AF-0004C.md).

AF-0004A is incomplete. Only the AircraftType data foundation is implemented.
`FixedWing=yes` does not enable fixed-wing movement and logs a warning when
read from INI. It must not be presented as a playable flight-cycle PoC.

## Implemented data

```ini
[SOMEAIRCRAFT] ; AircraftType
FixedWing=no  ; boolean, defaults to no; movement is not implemented yet
```

`AircraftTypeClassExtension::IsFixedWing` is initialized to false by the normal
constructor. INI reading uses the current value as the fallback, preserving
the existing Rules/map overlay pattern. A new type without the key starts
false; an omitted key in a later overlay does not reset an earlier value.

There is no classification by aircraft name, image, speed, ROT, dock or weapon.
The value does not imply AirportBound. No Airfield tag or alternate dock list
was added. The native TS classes and Aircraft/Locomotor instance layouts are
unchanged.

The existing base Save/Load path writes and reads the complete extension using
`Get_Object_Size()`. The bool therefore travels in that raw data block; it
must not also be appended to the optional-value stream. The NoInit constructor
leaves it untouched after loading. The existing optional CurleyShuffle and
ReloadRate streams are unchanged. `Object_CRC` includes the bool.

`Extension::Get_Save_Version_Number()` already includes
`sizeof(AircraftTypeClassExtension)`. Its existing size-derived mechanism is
retained; no separate version constant or migration was introduced. The added
member changes the extension layout. Old save compatibility is not promised,
and saves from a different layout must not be forced through the version
check. Layout and save/load behavior still require a later build and runtime
verification.

## Scope boundary

The task requires stopping before a large Mission_Enter rewrite or an expanded
set of unproven movement hooks. Source and static disassembly show that the
native travel/landing state machine cannot simply be left in control while
speed is kept positive:

- `FlyLocomotionClass::Get_Status` at `0x0049CEF0` returns 1 while landing.
  `AircraftClass::Mission_Enter` uses that status to switch from TRAVEL to
  LANDING at `0x0040D4B6`.
- In LANDING, the same status sends execution through the positional correction
  block at `0x0040D4F4` through `0x0040D593`: the aircraft is nudged toward its
  NavCom by up to five coordinate units per axis. The radio/service handoff
  begins at `0x0040D5AC` after the landing status has cleared.
- `FlyLocomotionClass::Process_Landing` at `0x0049B360` also owns speed changes,
  landing-cell validation, fallback movement, touchdown flags, adjacency
  bookkeeping and destination clearing. The current target inserts its
  AircraftTracker landing hook at `0x0049B92C` in this function.
- `Movement_AI` at `0x00499F20` independently owns horizontal movement, vertical
  movement, destination slowdown and automatic landing. Its boundary fallback
  can call coordinate scattering, which is unsuitable as the new deterministic
  holding-flight algorithm.
- `Move_To(COORD_NONE)`, `Stop_Moving`, idle selection and radio RunAway can
  independently request terrain landing or choose another destination.

A complete cycle needs coordinated ownership of approach, final descent,
touchdown and dock-loss recovery across these paths. No small, verified patch
sequence preserving the native state machine was established. Replacing the
TRAVEL/LANDING behavior and the linked locomotor transitions would exceed the
small-hook approach permitted by this task's stop criterion. This is a scope
blocker, not a claim that fixed-wing aircraft are impossible in TS.

The native binary inspected was `references/ts-patches/input.dat`, checked
against TSpp mappings and the readable OpenTS reconstruction. OpenTS was used
as a control-flow reference, not copied into the target.

## Flight-cycle status

No new hooks were installed and no existing movement, radio, docking, reload,
tracker, spawn or mission hooks were changed. No new persistent mission state,
new locomotor, runtime aircraft field, RNG call or save migration was added.

Start, horizontal climb, non-hovering flight, Move arrival, idle/stop behavior,
terrain-landing prevention, dock search, busy-dock holding, approach geometry,
final descent, touchdown, dock-loss recovery and air/dock spawn handling remain
unimplemented for the new flight model. Existing TS/Vinifera behavior still
applies even when the new setting is true. Existing reload/service logic is
untouched, but fixed-wing integration with it has not been completed.

Attack runs, fighter AI, strafing changes, Carryall, Dropship, transports,
SpawnManager aircraft, taxiing, runway collisions and runway scheduling are
outside AF-0004A. The bool introduces no simulation decisions yet, but adds CRC
data: multiplayer comparisons require matching code and rules. Determinism of
a future flight controller has not been validated.

## Later manual checks

No build or tests were run for this change. After a later build, the data
foundation can be checked as follows:

1. Omit FixedWing and inspect false on newly created AircraftType extensions.
2. Set FixedWing=no and confirm false without the incomplete-feature warning.
3. Set FixedWing=yes and confirm true plus the warning; expect native flight.
4. Overlay yes with no and verify false; omit the key in an overlay and verify
   the existing value is retained.
5. Save/load true and false types; verify NoInit preserves each bool and that
   CurleyShuffle and ReloadRate optional data still load correctly.
6. Check the generated save version against the previous build and confirm
   incompatible old saves are rejected rather than forced to load.
7. Compare type CRCs with the flag toggled; use matching builds and rules for
   multiplayer checks.
8. Recheck Orca, Harpy, Carryall, transport, Dropship, Hunter-Seeker, existing
   Aftermath aircraft and SpawnManager aircraft for unchanged flight behavior.

The flight-cycle acceptance plan remains pending implementation:

1. Dock spawn and existing airborne reinforcement spawn retain their heights.
2. Start moves forward immediately while climbing, including a second launch.
3. Normal Move reaches its objective without stopping or landing there.
4. Idle and Stop return to a compatible free Dock.
5. No compatible/free Dock produces deterministic positive-speed holding and
   periodic retry, with no terrain landing or new RNG use.
6. Multiple aircraft do not steal the occupied dock's radio reservation.
7. Approach follows Landing_Direction; final descent retains forward motion.
8. Touchdown stops at the dock and retains tracker/map/adjacency bookkeeping.
9. Existing ReloadRate/service completes and leaves the aircraft parked.
10. Destruction, sale, capture or invalidation of the dock aborts the approach
    and selects another dock or holding flight without stale references.
11. Map edges, speed/ROT extremes, shroud, terrain and bridges do not produce
    invalid holding/approach targets or unintended ground contact.
12. Save/load every flight phase; compare multiplayer states and CRCs over
    repeated cycles; recheck native EMP/crash/death behavior.
