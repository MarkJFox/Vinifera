# AF-0004H6A — Manual FixedWing native attack bypass experiment

H6A lets an accepted manual ground-object Attack use the full native TS
Aircraft attack mission and Fly process after FixedWing takeoff. FixedWing=yes
stays enabled. CAP autoattacks retain the existing custom controller.

This is an experiment before a possible H6B reset. No native-attack runtime
success is claimed. No build, automated tests, runtime tests, test files,
commit or push were performed. Use a **new game**: the saved Aircraft extension
layout changes and the save basis is now **0x150000**, previously 0x140000.

## Why native Attack did not run

The user's accepted-command trace establishes MISSION_ATTACK=1 and a real
TECHNO_OBJECT target with native target kind 52. H5A transport already works.
The later mission=7 is MISSION_ENTER, used for returning/docking.

The current FixedWing interception, rather than command serialization, owns
the subsequent attack:

| Existing entry | Previous FixedWing behavior | H6A manual experiment |
| --- | --- | --- |
| Aircraft::Mission_Attack, 0x0040BA40 / 6 | For Controlled aircraft, return 1 without executing the native body | Suppress only during custom takeoff; then return 0 to the original entry trampoline and complete native body |
| Fly::Process, 0x00499600 / 6 | Replace native Process with FixedWing::Process | Keep custom startup; after release Controlled returns null and the full native Process runs |
| Fly::Stop_Moving, 0x00499AB0 / 8 | Request_Return instead of native stopping | Original method while manual/native ownership is active, including startup |
| Aircraft::Assign_Destination, 0x0040E1B0 / 7 | Custom navigation, Status resets, goal replacement and possible Return | Adapt the initial empty event destination once; subsequent writes use the original Aircraft method without custom Status resets |
| Aircraft::Enter_Idle_Mode, existing hook 0x0040B35A / 6 | FixedWing::Idle can clear target/navigation and request Enter | Do not intercept native Idle while the experiment owns the attack |

Generic MissionClass::AI/Mission dispatch is not replaced by FixedWing. It
calls the Aircraft virtual Mission_Attack, whose entry was previously skipped.
The custom Process instead called Attack_AI every locomotor frame. Attack_AI
and Attack_Arrived could call End_Attack on invalid target/range, rejected
ingress/pass/positioning exit, regroup failure, or world-edge no-progress.
Without an active CAP parent, End_Attack -> Idle -> Request_Return can queue
MISSION_ENTER and start dock search. Clear_Attack also clears TarCom/NavCom and
the Fly goals. Custom Assign_Destination can independently request Return for
an empty destination outside its queued-Attack special case.

These are verified source paths capable of producing the reported early
return. The brief supplied runtime observations do **not** identify which
particular rejection fired in that run. H6A bypasses these attack paths instead
of inventing a diagnosis or extending their geometry.

## Minimal ownership and startup adapter

Only FixedWing::Command, reached by the existing accepted synchronized event,
activates the experiment. Requirements are MISSION_ATTACK, a human House and
the exact supplied live, non-self, non-limbo ground ObjectClass target. Cell
attacks, automatic CAP/retaliation attacks and non-human orders do not opt in.
House::Is_Human_Player is simulation state, not the local PlayerPtr. No UI
pointer channel, cell-to-object reconstruction, target search or event change.

As before, an explicit command cancels the previous CAP parent. A new command
clears old native ownership; accepted Guard/GuardArea continue their existing
CAP setup. Automatic CAP acquisition does not call Command and stays custom.

```text
accepted manual object Attack
  -> AttackControl = NativePending; HANDOFF observation
  -> native event installs mission/target/destination
  -> startup adapter commences the queued Attack and initializes native Status=0
  -> with target and ammo, original Aircraft::Assign_Destination(TarCom) primes native navigation
       (original dock wake/radio release and Fly::Move_To)
  -> below cruise level: NativeTakeoff
       existing FixedWing Process / forward motion / climb / takeoff bookkeeping
       native Mission_Attack delayed, custom Attack_AI/Attack_Arrived skipped
  -> full flight level and !IsTakingOff: Native
       original Mission_Attack + original entire Fly::Process
  -> native mission actually leaves Attack
       clear ownership; existing FixedWing controllers may resume
       Enter specifically starts at FixedWing INITIAL with clean flight goals
```

For an already airborne aircraft at flight level, ownership passes directly
to Native. The initial null destination from the accepted event is consumed
by the adapter after native TarCom installation. Recursive priming with TarCom
falls through the existing Assign_Destination entry to its original body,
because ownership is already NativeTakeoff/Native. Subsequent native writes do
not reset Status or clear TarCom. Target loss/Ammo=0 during startup releases
native processing early so native code decides the ending, without a custom
attack abort. There is no new persistent target pointer.

Native ownership is sticky across target loss and native Status changes. It
must not be inferred from `TarCom != nullptr` every frame: native Status 3, 4
or 6 must never accidentally become custom EGRESS/REGROUP/other states after
target detach. No per-frame mission-timer reset occurs after native release.
The original entry trampolines run full bodies, not selected subroutines or a
second call to Fire_At. Existing hooks are reused; addresses/lengths and H5A
Object 0x0040B690/5, Cell 0x0040B740/8 remain unchanged.

## Flight bounds, completion and remaining custom systems

During NativeTakeoff, FixedWing still owns physical movement. Its existing H4
Attack_Movement_Coord correction remains necessary there, but no-progress
does not invoke custom End_Attack for the manual experiment. Climb can finish
and release the native controller. No new attack geometry is introduced.

After Native release, no H4 wrapper or array preflight is injected: Controlled
returns null and native Movement_AI performs its own outer In_Radar correction
and rejection (H4's verified block 0x0049A5A3..0x0049A6D2). Native Fly also runs
its own approach/edge/layer behavior. Native flight may leave Local Radar; the
allocated array is not declared valid flight space. No custom egress, staging,
Find_Safe_Egress, Safe_Attack_Segment, direction probes or TURNBACK run here.

Native target loss and Ammo=0 run through native Mission_Attack/Idle. The
adapter does not choose a special target-death outcome or force an early RTB.
When native code has actually changed the mission to Enter, the adapter
resets Status/goals and clears native landing intention before the existing
FixedWing Enter/dock search/approach/landing controller resumes. A queued
Enter alone does not prematurely end a still-current native Attack.

FixedWing custom Move, takeoff, Enter, landing, docking/reload/service, CAP,
Escort and no-dock survival remain available. No holding dimensions, weapons,
rules, native mission delays, CAP autoattack logic or FWDOCK selection logic
were changed. H3/H4/H5B attack helpers, states and diagnostics are retained for
the old custom path, not deleted or repaired in this experiment.

## State, save/load and CRC

AircraftClassExtension gains one explicit enum field, AttackControl:
Custom / NativePending / NativeTakeoff / Native. It initializes to Custom,
is included in the existing raw-blob save/load and Object_CRC, and retains
its loaded value through the NoInit constructor. No pointer/swizzle is added.
TarCom/NavCom, Status, Fly state and mission timer already belong to native
saved state. Developer observation maps never determine control or firing.

The field must survive save/load: forgetting it would interpret a saved native
attack as custom phases. Therefore the global save basis changes from checked
0x140000 to **0x150000**. Get_Save_Version_Number additionally includes extension
sizes and the existing debug-build offset; the basis is not the entire final
version value. Earlier saves are rejected. Mid-experiment saves still require
local validation; no load/runtime test was performed here.

## Diagnostics

Developer-only, bounded observations through existing entry points:

- NATIVE_ATTACK_HANDOFF once per accepted command: aircraft UID/state, requested
  mission, exact target/ref kind and UID, Ammo, position, facing, wasDocked,
  airborne, prior CAPMode, customAttackBypassed=true and ACCEPTED_PENDING.
- NATIVE_ATTACK_AIRBORNE on release at flight level, including an already
  airborne start. NATIVE_ATTACK_RELEASE distinguishes early startup release
  caused by target/ammo loss from a completed takeoff.
- NATIVE_ATTACK_MISSION_ENTER / NATIVE_ATTACK_FLY_ENTER once per command when
  the corresponding existing entry returns to its original trampoline.
- NATIVE_ATTACK_AMMO_CHANGE only when the observed Ammo changes. This is an
  observation of the actual counter, not proof of a specific projectile shot.
- NATIVE_ATTACK_TARGET_GONE once after native TarCom becomes null, without a
  custom abort. NATIVE_ATTACK_RTB/END when the mission actually leaves Attack.

Existing state output supplies current mission, queue, Status, target, Ammo,
Fly destinations and CAP context. Observation baselines reset after load;
logging adds no fire hook and never calls Can_Fire as a probe. Target-gone and
ammo observations can be seen on the next Aircraft AI entry. No frame log spam.

## Manual validation plan — user runs locally

Keep TESTPLANE FixedWing=yes and Primary=Proton; no weapon/rules change is
part of H6A. Start a new game and enable developer diagnostics.

| Test | Observe and record |
| --- | --- |
| A: fresh, fully loaded at dock | Click enemy Unit. Accepted target kind 52/same UID, HANDOFF, forward FixedWing takeoff, AIRBORNE, both native-entry events, actual approach/fire. No immediate Enter/dock search |
| B: target survives | Use a strong target. Native shot opportunities, overflight/post-shot delay, natural turn and second approach while ammo remains. No custom INGRESS/REGROUP/TURNBACK |
| C: target dies | Record native Status, TarCom clearing, queued/current mission and subsequent loiter/Guard/RTB behavior; do not assume the outcome from the log event name |
| D: Ammo=0 | Record real Ammo/pending-consumption changes, native attack ending, RTB, FixedWing approach, touchdown and normal service/reload |
| E: known edge target | Record native Local/outer position behavior, overflight, turn and repeat attack. No custom egress/regroup planner or post-release ATTACK_WORLD_EDGE from FixedWing |
| F: already airborne | Click a different enemy object. Immediate native handoff; no custom dock-abort or new forced takeoff |
| G: second target after first | Destroy first target, explicitly click second. New HANDOFF and native-entry observations for that target, without immediate landing |
| Controls | Static/Escort CAP still autoacquire through the old controller; no HANDOFF for automatic attacks. Guard/Move/Return replacement and ordinary non-FixedWing aircraft retain their existing paths |
| Save/load adapter | Save during NativeTakeoff and Native; restore phase, native Status/target/ammo and continuing flight. Older saves must be rejected |

Success requires actual runtime takeoff, native fire, native turn and repeated
approach without custom planner assistance, followed by working RTB/landing
when appropriate. Entry events prove dispatch release, not runtime success.

The main integration risks to inspect are dock wake/radio release, losing a
target while taking off, native/custom Status ownership, and transferring a
native-selected Return into the custom approach without native VTOL landing
continuing. If any fail, identify the missing adapter and its native status/
destination/mission sequence; do not add another attack geometry controller.

## Deferred H6B — not implemented

Only after a successful local H6A result should H6B move attack approach,
firing/strafe decisions, post-pass extension, Facing/ROT turns, repeated passes
and normal weapon/ammo behavior to native TS for the broader architecture.
FixedWing would retain takeoff, landing, docking, Holding/CAP, Escort and CAP
target selection/mission intent. Removal of proven redundant custom attack
code and CAP-to-native integration are separate work. H5C is also excluded.
