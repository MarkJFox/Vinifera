# AF-0004H1 — Explicit CAP provenance after production

Static source/binary investigation and implementation only. No build or tests
were run. This supersedes H's implicit AI/mission-based CAP entry described in
[AF-0004H](AF-0004H.md); its existing explicit CAP, attack and service paths remain.

## Production and initial idle path

For a normal player-owned FixedWing produced on a free dock without a rallypoint:

1. AircraftExtension's constructor initializes `CAPMode=None`, `CAPMission=NONE`,
   `CAPEscort=nullptr`, `CAPRearming=false` and `CAPOwner=-1`.
   Native Mission construction starts with CurrentMission,
   MissionQueue and SuspendedMission all NONE; NavCom and ArchiveTarget start null.
2. `BuildingClass::Exit_Object`, TSpp **0x0042C640**, takes the Aircraft branch,
   sets height zero (**0x0042C8EA**) and calls virtual Unlimbo at the dock
   coordinate (**0x0042C980**). The original Aircraft Unlimbo entry is
   **0x00408940**, replaced by Vinifera's `AircraftClassExt::_Unlimbo`.
3. Vinifera Unlimbo calls `FootClass::Unlimbo` (**0x004A2C70**), which calls
   `TechnoClass::Unlimbo` (**0x0062CB30**). After object placement, Techno invokes
   virtual `Enter_Idle_Mode(true, true)` at **0x0062CBEF**, then conditionally
   `Commence` at **0x0062CC07**. The binary supplies both boolean arguments as
   true; OpenTS's source labels differ on the second argument, so the binary
   is authoritative for that detail.
4. Virtual dispatch reaches `AircraftClass::Enter_Idle_Mode` (**0x0040B310**).
   After `FootClass::Enter_Idle_Mode` (**0x004A3AA0**), Vinifera's existing hook
   **0x0040B35A** calls FixedWing Idle if Controlled permits it. At ground level,
   without a mission/navigation order or mutual dock reservation yet, FixedWing
   Idle stops the locomotor and assigns **MISSION_GUARD (5)**; it does not set CAP.
   If Controlled is not yet available during Unlimbo, native grounded Idle
   instead clears destination/target, selects Guard for a human House at
   **0x0040B659**, assigns it at **0x0040B663**, and conditionally commences it at
   **0x0040B67B**. Both routes produce the same ordinary player Guard state.
5. Foot finishes locomotor Unlimbo/power initialization. Vinifera finishes its
   stationary spawn initialization. Only after successful Unlimbo does the
   building send HELLO (**0x0042C995**) and TETHER (**0x0042C9A7**).
   With no rallypoint the branch at **0x0042C9B5** exits without assigning a new
   flight order. NavCom/ArchiveTarget do not name an explicit Guard target;
   MissionQueue is normally NONE after Commence. If still queued, Guard is the
   internally generated idle assignment, not evidence of a command.
6. Aircraft AI (**0x004090C0**) starts its ordinary tick. H called CAP_AI here
   before the remaining native AI and mission dispatch. Mission AI dispatches
   virtual Mission_Guard (**0x0040DD10**) when its timer is due. Production does
   not directly call Mission_Guard inside Exit_Object/Unlimbo; it prepares the
   state which the following AI/mission processing executes.

These are static statements about the ordinary branch, not captured runtime
field readings. A rallypoint deliberately assigns Move. An occupied pad can
spawn an aircraft at the map edge with a positioning Move; ion-storm placement
also has a separate branch. Those native production paths are unchanged.

## Regression and correction

Immediately before the false entry, `CAPMode` is **None**. H's CAP_AI accepted
either queued or current Guard/GuardArea as sufficient proof, called Begin_CAP,
stored Static and the current position, and set CAP_INITIAL. Mission_CAP then
ran CAP_Flight, selected an orbit corner, released dock contact and requested
takeoff. The flight controller continued the orbit without a player command.

There were three other implicit entry/reset opportunities: CAP_Flight itself
created missing context; Assign_Destination could create it from a queued Guard;
CAP_AI could recreate an existing context from a queued mission and ArchiveTarget.
All are removed. Guard/GuardArea, MissionQueue, Team membership and ArchiveTarget
are mutable engine state, also used for production, idle, service, regrouping
and automatic area guard. They cannot reliably identify an explicit CAP order.

Begin_CAP now has exactly one call site: **FixedWing::Command**, called by the
existing accepted synchronized MEGAMISSION hook **0x004948A5**. The UI does not
write CAP state locally. The unchanged G path sends GuardArea with the current
cell; CTRL+ALT on an own object sends GuardArea with that object. Command records
Static/Escort and the original anchor/reference before native mission/destination
assignment. Assign_Destination consumes that context without recreating it.

| Entry / state | H1 behavior |
|---|---|
| CAP_AI with CAPMode None | Return without creating, resetting or launching CAP |
| CAP_Flight with CAPMode None | Return false without changing flight/order state |
| Mission_Guard with CAPMode None | Existing hook returns zero, replaying native Guard instructions |
| Mission_GuardArea with CAPMode None | Existing hook returns zero, replaying native GuardArea instructions |
| Airborne default Guard without CAP | Restore pre-H target/Move/Return fallback; no orbit creation |
| Ground default Guard without CAP | Native Guard handling, no CAP takeoff |
| Explicit synchronized Guard/GuardArea | Command creates context; normal H mission/takeoff/CAP path |
| Existing CAP across Attack/Enter/Sleep | Existing validation, cancellation and full-service resume |

The two mission hook addresses/lengths remain **0x0040DD10 / 5** and
**0x0040E0A0 / 10**. They gain only the CAPMode prerequisite. No new hooks.

## AI/script boundary

OpenTS's Team GUARD script waits/regroups, and native Team coordination also
assigns MISSION_GUARD. Native Aircraft Idle can select MISSION_GUARD_AREA for an
armed non-team AI House. Foot GuardArea can itself populate ArchiveTarget with
the current cell. Thus even GuardArea plus a non-null anchor is not reliable
command provenance at these generic entries.

H1 intentionally does not synthesize CAP for direct AI/script/map
Assign_Mission(Guard/GuardArea) calls without existing CAPMode. This restriction
applies to both missions, including explicit scripts whose source is no longer
identifiable at the generic handler. Existing CAP still executes for any owner,
and an accepted synchronized Guard command can still create it. No new AI/script
source hooks or persistent provenance fields are introduced.

## Scope and persistence

Only implicit CAP generation is corrected. Command's Move/Attack/Stop/new-Guard
cancellation semantics, Cancel_CAP, manual Move completion/Return, AF-0004E runs,
No_Dock_AI, G2 geometry, dock search/Find_Dock, holding, approach speed, Ammo, radio,
service and FixedWing=no paths are unchanged. Existing explicit CAPRearming
survives docking and resumes through the same full-service helper. The pre-H
airborne default Guard fallback is restored solely for aircraft without CAP.

No development logs were added. No extension fields or serialization/CRC/
swizzle/detach code changed. Save basis remains **0x140000**. A loaded H save
which already contains a false Static CAP cannot be retrospectively identified
from the same fields; H1 prevents new implicit creation rather than deleting
persisted CAP orders. An explicit Move/Stop replaces such an existing order.
