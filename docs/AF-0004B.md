Status: **RUNTIME VALIDATED** for the user-reported approach, descent, landing
and opposite-direction edge fallback. Codex performed source, interface,

The user successfully tested the feature in the game and confirms that the
configured actual approach direction works, aircraft approach from the
selected direction, descend and land. The map-edge fallback also works:
when the primary approach geometry is unsuitable, the aircraft successfully
uses the opposite direction.

The user supplied the following debug-log markers and facing values:


The example means that primary east was replaced by west for an unsuitable

## Configuration

Set `FixedWingLandingDir` in **RULES.INI**, in the destination BuildingType's
section, not its Art/Image section or the AircraftType section:

```ini
[GAAIRC]
FixedWingLandingDir=2

[NAAIRC]
FixedWingLandingDir=4
```

These section names are examples, not IDs recognized by the implementation.
Aircraft still need their existing compatible `Dock=` types and a usable
service building. The option neither creates a dock nor changes its capacity.

| Value | Final flight direction | Arrives from |
| --- | --- | --- |
| 0 | North | South |
| 1 | Northeast | Southwest |
| 2 | East | West |
| 3 | Southeast | Northwest |
| 4 | South | North |
| 5 | Southwest | Northeast |
| 6 | West | East |
| 7 | Northwest | Southeast |

The direction uses TS's eight-way FacingType convention. For example, value 2
constructs an approach west of the assigned dock and flies the final segment
eastward while descending. It changes the approach path, not a parked
aircraft's facing after landing.

A new type without the option retains the complete previous direction
selection and opposite-direction fallback. Applicable Rules/map overlays
preserve an earlier value when the key is omitted, matching existing type
extension loading conventions. An explicitly invalid value clears the
override and logs a `[FIXEDWING]` configuration warning with the type/value
and native fallback. The parser accepts one complete decimal integer 0..7
with existing ASCII whitespace handling; empty strings, -1, 8, suffixes,
floats, overflow and truncated values are rejected. The internal -1 sentinel
is not a configurable ninth direction.

## Existing landing cycle and integration

The existing FixedWing takeoff/move/CAP/landing/service cycle is present and
was reported runtime-working by the user before this feature. The subsequent
feature-specific acceptance is recorded above. AF-0004C through H6,
G2 approach fallback and D3c2 slot-aware docking already supply the controller
used here; no parallel flight controller or new hook is introduced.

Before this change `Geometry()` selected the building's primary facing before
HELLO, or the native eight-way `AircraftClass::Landing_Direction()` during
mutual dock contact. Native TS at 0x0040EE70 reads the radio peer's primary
facing in that case, so the candidate and reserved paths agree. The usual
N/S behavior comes from that building direction and G2's 180-degree fallback;
the controller is not limited to a hardcoded N/S geometry.

`AircraftClass::Pose_Dir()` at 0x0040BA30 returns global Rules PoseDir and is
used by existing native pose/spawn behavior. It is not a per-building runway
setting. Neither PoseDir nor native Landing_Direction is patched by this
feature. The local TSpp bindings and read-only OpenTS aircraft reference were
used to distinguish Dir256, eight-way facing and the type-specific dock query.

The added `Landing_Facing()` reads the selected dock's BuildingType extension.
`Native_Landing_Facing()` retains the previous selection. Geometry uses the
override when present and constructs the existing complete chain:

```text
D = assigned dock coordinate
back = selected final direction + 180 degrees
side = selected final direction + 90 degrees
P = Move(D, back, 8 cells)
G = Move(P, back, 6 cells)
S = Move(G, side, 6 cells)

DOWNWIND -> S
CROSSWIND -> G
TRAVEL -> P, align with selected direction
LANDING -> D, descend along the selected P-D axis
```

FacingType is explicitly converted through `DirType(FacingType)`, not the
Dir256 constructor or an unscaled raw integer. The 180-degree reversal still
uses `DirType(DIR_S)`, as in G2. Waypoint lengths, heading tolerance, approach
speed, ROT, pitch, climb/descent limits and touchdown thresholds are unchanged.

Dock_Candidate, Find_Dock, Go_Around, Arrived and controlled Process share this
Geometry function. The final direction remains committed in the existing
SecondaryFacing.Desired value. Process checks the currently selected geometry
against that heading; a changed direction causes the existing go-around,
not an immediate turn or position change. The actual descent uses the selected
Direction for its along-track projection and target height. Touchdown keeps
the existing short-segment, heading, pitch, dock-permission, Can_Enter_Cell
and Is_LZ_Clear checks followed by native Process_Landing (0x0049B360).

The grounded Mission_Enter handoff uses legacy geometry until LANDING has
actually been reached. This prevents the new option from making an already
parked/newly produced aircraft take off just to match a configured runway
heading. The completed configured landing still uses its selected heading
for the final service handoff. No production-facing setter, spawn adjustment,
Initialize_Spawn, Take_Off or Process_Takeoff change is added.

## Dock selection and safety

The preferred dock order and native per-type bay selection remain unchanged.
The direction comes from the candidate/reserved building actually used, not
the first type in AircraftType::Dock. Before HELLO, a MultiDock query predicts
the first free slot; after reservation, its registered slot supplies D.
Single-Dock continues using Building::Docking_Coord, including the existing
CustomDockCell adapter. Native/custom foundations and every MultiDock slot
therefore share the same direction selection while retaining distinct D.

Explicit destination replacement retains the existing Assign_Destination
cleanup and INITIAL state. Dock loss or destruction uses the existing
release/search/go-around flow; geometry is reconstructed from the new dock.
New commands, CAP, native attacks and native RTB ownership are not redesigned.

For an infeasible configured direction, selection is deterministic:

1. Validate the full configured approach.
2. Try its complete 180-degree opposite.
3. If both fail, try the previous native building-facing approach and its
   opposite, unless that pair was already checked.
4. If no complete approach is valid, reject that candidate and retain the
   existing search/holding/retry behavior. Never clamp or shorten the path.

At most four complete geometries are evaluated; there is no new RNG, retry
loop within a frame or saved fallback phase. With no override, only the
original pair is evaluated and its results are unchanged. The additional
native pair ensures a bad configuration does not disqualify a dock whose
previous approach remained usable. Developer-only FWDOCK diagnostics show
preferred/selected facing and distinguish a native-pair fallback from the
ordinary opposite fallback.

Geometry validates D/S/G/P, sampled segments against existing radar/local-map
bounds, and the existing bridge exclusion at D. It is not a new airspace or
terrain-clearance planner. Occupied docks, changing terrain, power/EMP and
landing obstacles retain the existing reservation, readiness, missed-approach
and recheck handling. If no compatible usable landing is available, the
aircraft may continue the existing holding route; the option does not promise
a landing through permanent obstruction or change the no-dock survival policy.

Different building types may have different directions. All slots on one
BuildingType use that type's direction; per-slot direction is not a new API.
Slot ownership, capacity and independent reload timers are unchanged, so the
new option does not itself add simultaneous landing traffic separation.

## Persistence, CRC and scope

BuildingTypeClassExtension appends one FacingType `FixedWingLandingDir`,
initialized to FACING_NONE (-1). The existing raw extension Save/Load size
includes it; NoInit preserves the saved value, and Load accepts only -1..7
without dereferencing an unswizzled owner. No Aircraft instance, native class,
COM interface or persistent approach/fallback state is added.

Aircraft_Docks_CRC emits the optional FWLD tag and direction, including for
Single-Dock types. The existing FRAMESYNC configuration aggregation includes
types with this override even when they have no custom foundation or MultiDock.
INI application invalidates the cached configuration CRC. Absent overrides
add no direction bytes to the prior CRC stream. The new direction and fallback
order are deterministic; multiplayer runtime validation remains pending.

The source save basis was **0x1C0000** before this change and is now
**0x1D0000**, following the existing 0x10000 layout-version steps. The final
save version also includes extension sizes and the existing debug adjustment;
no new full runtime value is claimed. Start a new game with the updated build;
older extension layouts must be rejected rather than reinterpreted.

Changed by this feature: fixedwing.cpp, buildingtypeext.cpp/.h, extension.cpp,
this document and Whats-New. No hook address, count, displaced instruction or
calling convention changes. No CMake/source-list change is needed.

VTOL, BalloonHover/NewJumpjet, rotor model/shadow animation, AF-0006C rates,
general aircraft production and existing takeoff logic are unchanged. The
pre-existing AF-0006C changes in aircraftext_hooks.cpp, footext_hooks.cpp,
AF-0006.md and Whats-New are preserved. Reference repositories are read only.
