## Current frame contract

Multi-frame HVA animation is automatic for a real AircraftType's main
`<GraphicName>.VXL` / `<GraphicName>.HVA` model, including FixedWing. Rotors and
propellers are animated sections of this model. No names, unit IDs, separate
rotor files or new INI keys are interpreted.

The common Aircraft_HVA_Frame helper selects both body and shadow frames:

    rate = WalkRate > 0 ? WalkRate : 1;
    frame = active ? (unsigned(GameFrame) / rate) % unsigned(FrameCount) : 0;

The frame advances in simulation ticks even at zero horizontal speed.
An aircraft is active when any of these conditions holds:

- Its original height above ground is positive: cruise, hover, airborne
  attacks, ascent/descent and an airborne crash are included.
- Its Fly locomotor reports Takeoff, Landing or elevation adjustment, even
  at the height-0 endpoints of those transitions.
- Its locomotor reports actual movement.

Fully parked aircraft use frame 0. The existing WalkRate supplies the
divider throughout active states. Values <= 0 use divider 1 in this visual
helper; existing AI parsing/progression is not changed or repaired.
IdleRate no longer drives this Aircraft HVA feature, including on a parked
helipad. It keeps its existing behavior for other consumers.

Equal-rate aircraft share a global phase while active, regardless of spawn
times. Pausing simulation freezes the frame. Camera visibility and rendering
frequency cannot advance animation. This is the AF-0006B Vinifera contract;
exact vanilla RA2/YR timing parity is not claimed.

## Causes confirmed before implementation

The local TS binary was inspected read-only:
C:/dev/Aftermath-Engine/references/ts-patches/input.dat.

1. A used TotalFramesWalked % FrameCount. The existing Foot AI hook at
   0x004A59E1 advances this counter while Is_Moving_Now() is true or while
   stationary with positive IdleRate. Zero horizontal speed can therefore
   freeze A during hover, vertical Takeoff/Landing or airborne attack.
2. Aircraft::Draw_It pushes section index 0 at 0x00408E38 before calling
   Foot's shadow wrapper at 0x00408E3D. No other section is submitted.
   The body renderer, by contrast, walks all model sections. The missing body
   is explained by section exclusion in the shadow path. If the test model's
   section 0 is its rotor, this produces the reported rotor-only shadow.
   The actual test model's section names/order were not supplied.
3. The low shadow renderer at 0x00635E20 selects HVA frame 0: EAX/EDX are
   zeroed at 0x00635E26/0x00635E28 before division by FrameCount at 0x00635E3E.
4. Techno's shadow wrapper at 0x00635860 checks a separate cache before
   rendering. A matrix-only change would leave cached silhouettes stale.
5. Aircraft::Draw_It saves the original height in EBX at 0x00408CFA and
   temporarily changes it to ground/bridge height for the shadow pass.
   Reading HeightAGL in that pass would misclassify flight as parked.
   The original height is restored after the shadow call.

## Body and full animated shadow

The existing A hook at 0x00408F68 now uses the shared tick-based helper.
It sets only frame and cache key (-1), then replays the original body call.
Lighting, remap, cloak/translucency, draw flags and the whole-object
roll/pitch/rocking matrix remain in the native rendering path.

The shadow pre-hook at 0x00408E38 selects its frame using EBX's original
height and changes the pending cache key to -1 for qualifying models.
The original CALL at 0x00408E3D invokes the Foot shadow wrapper exactly once.
That wrapper retains locomotor shadow eligibility and position adjustment.
Techno retains cloak/flicker/load-failure checks and the native blit.

A transient context stack carries frame, aircraft and model through that
synchronous call. The post-hook at 0x00408E42 pops it before native height
restoration. Each pre-hook pushes an entry, including an inactive entry for
native fallback, so a nested nonqualifying draw masks its outer context.
Deque storage keeps context addresses stable during nesting. Post matches
aircraft and expected return ESP; an unmatched return clears the stack and
current pointer. Regular matched returns restore the previous context, or
nullptr at outermost completion. Identity checks keep another object/model
from using it. It is not stored on an object, serialized or retained between
draws. It compensates for native temporary grounding and is not an animation
counter.

After native Reset (0x00666030), the new hook at 0x00635E96 submits every
model section to native Prep_For_Shadow (0x006661C0), using:

    camera = nativeCamera * nativeShadowMatrix;
    motion = HVA[frame * SectionCount + section];

B3 separates the common aircraft basis from the local section pose so native
flattening happens after HVA but before facing, ramp and isometric view.
The previous B/B1/B2 arrangement flattened in view space; elevated sections
could already have acquired a relative XY displacement before Z was cleared.

Prep_For_Shadow appends a record and expands shared min/max bounds without
clearing preceding records. Native Finish (0x00666720) renders their combined
silhouette and the existing path blits it once. Overlapping body/rotor
sections therefore combine before darkening the map instead of being
darkened repeatedly by separate section blits.

The camera matrix at 0x0074C6F8 is composed with the native aircraft basis
once per shadow draw; neither input is mutated. VoxelShadowLightSource at
0x0074C6E8 is still passed unchanged.
The earlier low-renderer frame-0 matrix setup remains harmlessly executed;
its single-section preparation is skipped.

Body and shadow are uncached for qualifying models. No new frame-key format
or five-bit limit is introduced, including for HVAs with more than 32 frames.
B2 gives this direct shadow blit the same virtual Get_Z_Gradient() result
used by the normal cached Aircraft shadow. Native Get_Z_Adjustment(), world
position, ground/bridge screen anchor, clipping and terrain height handling
stay unchanged. B3 changes the section projection before bounds are combined;
it retains native bounds generation, Finish and final blit. No altitude
offset is added.

## Eligibility and unchanged native paths

The helper requires the aircraft's actual main VoxelObject, valid VXL and
MotionLibrary data, FrameCount > 1 and matching positive section counts.
It allows at most 64 sections: the native shadow-record array starts at
0x00832740, holds 64 records of 0x3C bytes and ends at 0x00833640.

In the current TSpp API, MotionLibrary::Get_Layer_Count() returns frames;
Get_Section_Count() returns HVA sections. No section names are examined.

For one-frame aircraft, missing/failed data or unsupported/mismatched counts,
both call paths execute the native call with its original arguments. The helper performs no
modulo for FrameCount <= 1. This preserves native fallback behavior; it does
not repair malformed assets in the native loader/renderer.

## AF-0006B1 crash and native-call audit

### Evidence and limits

Read-only disassembly used the local TS image
`C:/dev/Aftermath-Engine/references/ts-patches/input.dat`, the existing
`build/RelWithDebInfo/Vinifera.dll` (B shadow hook RVA 0x33482), and bundled
`Syringe/Syringe.exe`. No inspected binary was executed or rebuilt.

The definite error in B is the nonqualifying path's `return 0` at
0x00408E3D: it asks Syringe to replay `E8 CE CE 09 00` from a different
address. Bundled Syringe's 0x0042D8D1..0x0042D8E6 copies the overwritten
bytes with ReadProcessMemory without relocating that displacement. If C
is the relocated instruction address, its target is C+5+0x9CECE, not
0x004A5D10. The error precedes entry into the shadow wrapper and thus can
occur before 0x00635E96. One-frame/native aircraft take that B fallback.
The supplied register values do not identify the aircraft's HVA frame count.

The loader's template and copy behavior also match its
[upstream source](https://github.com/Vinifera-Developers/SyringeEx/blob/master/SyringeDebugger.cpp).
Its jump-back is site+5; additional overwritten bytes at the original site
are NOP-filled. Therefore position-independent six-/nine-byte replays are
safe at the POST/body/preparation hooks. This is distinct from replaying
the position-dependent E8 CALL itself. PRE avoids it by ending exactly at
0x00408E3D, leaving that CALL at its original address.

The reported EIP 0x00F2CF78 and LastHookOrigin 0x00408E3D are consistent
with this wrong-target path, but a register report alone does not decode
the exact faulting instruction or map the generated trampoline allocation.
No supplied memory image establishes that precise mapping. B1 removes the
proven invalid path; runtime confirmation of the reported crash remains
pending. An HVA asset fault or a fault in 0x00635E96 was not established.

### B adapter verdict and B1 stack proof

The existing compiled B adapter sets ECX to the aircraft and pushes the
eight arguments in the correct reverse order. Reference parameters pass
their original pointer values. No saved register or return address is read
as an argument: its stack offsets are relative to the hook's saved native
ESP, where no CALL return address has yet been pushed.

Its manually invoked wrapper cleans its own newly pushed 0x20-byte C++
argument block. The subsequent saved-native-ESP increment discards the
different, originally pending 0x20-byte argument block. This is not double
cleanup of the same block. Bundled Syringe's POPAD replacement supports
saved ESP changes. The qualifying adapter therefore has no demonstrated
ECX, order, pointer, nonvolatile-register or cleanup mismatch; its explicit
continuation 0x00408E42 is correct. The proven invalid return/continuation
contract is instead the nonqualifying `return 0` replay of a relative CALL.
The old wrappercall and all explicit ESP writes are removed in B1.

Let Q be native ESP at PRE before its overwritten instructions:

| Point | Native ESP / contents |
| --- | --- |
| PRE | Q; +00 key, +04 cache*, +08 clip*, +0C point*, +10 matrix*, +14 bool |
| Just before original CALL | P=Q-8; +00 voxel*, +04 section, +08 key, followed by the other five arguments |
| Wrapper entry | P-4=Q-0C; return address 0x00408E42 at +00, eight arguments at +04..+20 |
| Native ret 20h / POST entry | P+20h=Q+18h; all original shadow arguments consumed once |

## AF-0006B2 terrain-depth audit (before B3 projection change)

### Static root cause and flat-versus-slope report

The first path-selection difference is B's qualifying cache key -1 at PRE.
In the native Techno wrapper 0x00635860, 0x00635949..0x0063594F converts
key != -1 to the low renderer's build-cache flag. With a normal key, the
renderer returns its silhouette without an immediate map blit; the wrapper
compresses it and re-enters the cache path at 0x00635AF0. Cache hits draw it
through 0x00635FA0. With key -1, the low renderer instead blits immediately
at 0x00635EF0..0x00635F6F. B1 therefore selected more than an uncached
version of the same draw: it selected a different native depth contract.

Foot::Get_Z_Gradient at 0x004A5CE0 forwards to ILocomotion::Z_Gradient
(vtable +0x3C); its no-locomotor fallback is 2. Native Fly inherits
Locomotion's 0x005066D0 implementation, returning 2 (ZGRAD_90DEG).
B2 calls the virtual getter; it does not hardcode 2 or replace a locomotor.

Bit_Blit selects a 24-byte gradient record from 0x006F24E8 at
0x00423593..0x004235B8. RLE_Blit selects the same table at
0x00423B26..0x00423B46. The relevant binary records are:

| Gradient | Six 32-bit record values |
| --- | --- |
| 0 / GROUND | 1, 1, 1, 1, -1, 1 |
| 2 / 90DEG | 1, 3, 1, 3, 1, 0 |

These records change initial depth calculation and its progression by
screen row, not the world-coordinate height. The ground record uses the
top-anchored branch and steps depth by -1 per row; 90DEG uses the
bottom/height-dependent branch and steps +1 per three rows. Consequently
they are not interchangeable even with identical shadow pixels and XY.
The darkening Z-read blitter at 0x00467A30 compares the candidate depth with
the terrain Z-buffer value at 0x00467A58 and skips when candidate >= terrain.

Thus a correctly generated mask can be rejected by terrain depth. Slopes
change the native terrain depth field and the ramp-dependent shadow matrix,
so visibility on a slope does not establish correct flat-terrain depth.
This explains the reported symptom as a depth-gradient mismatch rather than
evidence that the entire aircraft is below ground. The static audit proves
the two different contracts; it does not measure the exact candidate and
terrain depth values of the user's pixels. The claimed runtime resolution
of flat/slope visibility remains pending local testing.

### Section matrices, flattening and Finish

Let S denote the native shadow base matrix and H[f,s] its HVA matrix. In
the low renderer, entry ESP becomes hook ESP+0xE8 after the 0xD8 local
allocation and four saved registers. The base-matrix pointer is therefore
at hook ESP+0xF4. Native 0x00635E73 computes S * H[0,section] and copies
the result to the local matrix at hook ESP+0x58.

Native preparation uses a second matrix constructed as camera * identity
at 0x00635EB4, where camera is 0x0074C6F8. B's direct camera reference is
equivalent. B's per-section S * H[frame,section] uses the same multiplication
order and complete translation columns: X=[0][3], Y=[1][3], Z=[2][3]. No
component is reset or adjusted by B2. This is the locomotor shadow matrix,
not a newly substituted body Draw_Matrix or original-altitude matrix.

Prep_For_Shadow (0x006661C0) transforms each of four section-footprint
corners by the motion matrix at 0x00666209. It explicitly sets the resulting
Z to zero at 0x00666229 before camera transformation at 0x00666230, adds the
existing shadow light vector, flips screen Y, and expands common bounds.
Ground flattening therefore already occurs once, inside native preparation;
the hook must not add flight height or another ground translation.

The renderer appends one 0x3C-byte record per section. Finish
(0x00666720) loops the complete record array at 0x00666778..0x00666795,
rasterizes their union and returns the native six-word region: XY offset
and source rectangle. There is no one-section-only restriction in Finish.
At 0x00635F08..0x00635F2A the direct path adds that region's XY offset to
the native projected shadow point, then performs its ordinary clipped blit.
B2 does not modify bounds, region, pixel mask, clipping or screen position.

## AF-0006B3 multi-section alignment

### Result and approved projection contract

B3 moves the shared Aircraft shadow basis from Prep_For_Shadow's motion
argument to its camera argument. The local HVA pose is then flattened in
the common model plane before facing, ramp orientation and isometric view.
This removes the large height-dependent relative offset without editing
the asset, adding offsets or treating rotor sections specially. The user
has now runtime-validated B3: connected body/rotor shadows on flat terrain
and slopes, with no visible pivot, orbit or offset problems.

The native TS helper flattens after its supplied motion matrix, and the
original Aircraft caller has already included the isometric view in that
matrix. Extending that single-section setup to every section exposed the
different bottom-plane heights. This behavior is inherited from native
projection; it is not cumulative mutation or a bad HVA stride. Because B3's
original stop criterion excluded changing an exact native contract, the
agent requested a decision after reconstructing it. The user explicitly
selected the generic projection fix. The earlier tentative stop therefore
does not describe the final implementation.

### Matrix audit: first relative displacement

Define V as Get_Voxel_Draw_Matrix's isometric view, L as the native
locomotor shadow/ramp/facing matrix, S=V*L, H[f,s] as a loaded HVA pose,
C as the native camera and P as the operation (x,y,z)->(x,y,0).

The original TS Aircraft call builds S, not merely L. At 0x00408E0B,
Get_Voxel_Draw_Matrix (0x00666E30) copies IsometricViewMatrix from
0x008367F0. The pointer pushed at 0x00408E03 is L, the right operand of
operator* at 0x00408E16; the getter itself consumes no stack argument.
The earlier B1 disassembly annotation has been corrected accordingly.

The view is initialized at 0x00667A6E..0x00667AA4 as
Rotate_X(-60 degrees), then Rotate_Z(-45 degrees). The native initialization
constants are 0.017453292519943295, 60 and 45. C is initialized to identity
at 0x004DFF76. Native Fly obtains the ramp matrix and primary facing at
0x0049CBFD and 0x0049CC46. All of these inputs remain native in B3.

The previous loop was already independent per section:

```cpp
const size_t offset = frame * sections;
for (int section = 0; section < sections; ++section) {
    const Matrix3D transform = *matrix * matrices[offset + section];
    PrepareShadow(voxelLibrary, section, 0, camera, transform, light);
```

Neither matrix input was mutated. There was no S*H0*H1 chain. The index is
f*SectionCount+s, with 48 bytes per Matrix3D, matching native body indexing
at 0x00635B79..0x00635B9F and MotionLibrary's frame-major storage. The
body composes base*HVA at 0x00635BAD; reversing that order is not a fix.

The differing behavior is in the geometry passed through the chain:

- The visible renderer passes C*(V*DrawMatrix*H[f,s]) to Prep_For_Object
  at 0x00635BE4. That helper processes all eight bounds corners and the
  native volume renderer draws the voxel geometry.
- Prep_For_Shadow obtains only the first four bounds corners, all at the
  section's MinZ. The VXL loader builds them as (maxX,maxY,minZ),
  (maxX,minY,minZ), (minX,minY,minZ), (minX,maxY,minZ).
- At 0x00666209 it applies motion. At 0x00666229 it zeros the resulting Z.
  At 0x00666230 it applies camera, adds the common light offset and flips Y.
- In B2, motion=S*H. Section-Z has therefore already entered X/Y through
  V before P clears Z. Clearing that final Z does not undo the existing
  XY displacement. This is the first relevant relative alignment error
  in the expanded multi-section Aircraft path.

The visible rotor and upper fuselage can touch at Z=17..18. The shadow
uses the body footprint at Z=0 and rotor footprint at Z=17 instead, exposing
the different bases after view rotation. This is a footprint approximation
in view space, not proof of a physically correct height-dependent ray cast
from the configured light. The added light vector is the same for every
section and cannot by itself produce their relative displacement.

### Minimal implementation and terrain contract

Only the existing preparation hook body changes:

```cpp
const auto& native_camera = *reinterpret_cast<const Matrix3D*>(0x0074C6F8);

    const auto& transform = matrices[offset + section];
```

Ignoring the final common light offset and Y flip, the effective chains are:

```text
B2: C * P * S * H[f,s] * footprintCorner
B3: C * S * P * H[f,s] * footprintCorner
```

P still executes inside native Prep_For_Shadow. HVA rotation and translation
happen before P, so vertical rotation can still contribute to the posed
model's local XY. There is no early clearing of raw voxel Z before its HVA,
no per-section Z rewrite and no constant compensation. The common S is
applied after P. This is the explicitly approved change from the native
single-section projection contract, confined to eligible multi-frame main
Aircraft models; it is not claimed as original TS/YR rendering parity.
