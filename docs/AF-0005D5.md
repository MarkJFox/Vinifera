# AF-0005D5 — eastward Weapons Factory exit

Current status: IMPLEMENTED. The user confirms D5d runtime output on native
3x3 foundations for exits (3,1), (3,3) and (4,1), covering Mech, Hover and
Drive/Track66, factory release and subsequent production. D5e's narrowly
validated custom role, including Bib=yes, is user-confirmed for loading and
single output on a full 5x5 mask. After D5f, the user confirms automatic
consecutive-output clearing for normal vehicles and Mechs. Hover still blocks

Hover consecutive-output runtime validation is pending.

translated native Track13. See **Implemented D5 contract** below for the
authoritative configuration, hooks, safety checks and save-version change.
The original research is retained below as historical evidence. Its earlier
UnitSpawnCell proposal and requirement for old-save compatibility are
superseded by the implementation task; neither is part of the final API.

## Production, placement and completion are different operations

1. FactoryClass::Set(type, house), native `0x00496FC0`, creates the product
   with Create_One_Of. The product exists in limbo during construction; it is
   not newly allocated each time Exit_Object retries.
2. Vinifera's FactoryClassExt::_AI replaces native Factory::AI `0x00496EA0`.
   It advances production until completion/suspension. Has_Completed,
   Get_Object and Completed are bound at `0x00497470`, `0x004974A0` and
   `0x004974E0` respectively.
3. Player EVENT_PLACE uses HouseClassExtension::Place_Object. The old native
   House::Place_Object `0x004BEA10` is not the active player implementation.
   Before a Unit exit, Who_Can_Build_Me checks for an available factory. If
   there is none, FactoryExtension::IsHoldingExit keeps the completed product.
4. The selected builder calls native BuildingClass::Exit_Object
   `0x0042C640`. AI production uses Vinifera BuildingClassExt::_Factory_AI,
   installed at `0x00434FE0`, and calls the same spatial exit method.
5. Exit_Object returns 0=failure, 1=temporarily busy, 2=success. The callers
   are not interchangeable: AI retries 1 after PlacementDelay, abandons on 0,
   and completes on 2. The player wrapper can abandon/refund after a failed
   actual exit call; its earlier IsHoldingExit check is a separate mechanism.
6. A successful WeaponsFactory exit completes the production-manager job
   before the vehicle has finished driving out. Door/radio/tether state, not
   that FactoryClass object, then serializes physical egress.

## Native WeaponsFactory spawn

The special path requires WeaponsFactory=yes. Factory=UnitType without that
flag uses a different generic Find_Exit_Cell path and has no equivalent door
cycle. These must not be treated as the same implementation.

In the WeaponsFactory branch, Exit_Object marks the product locked and stores
Rally_Point_For(product) in ArchiveTarget. If the building is already in
MISSION_UNLOAD, it tries another factory or returns busy.

Vinifera's existing hook `0x0042CAB9` replaces alternative-factory selection;
it can choose a compatible different building type and considers distance,
production/naval compatibility and ownership. Recursion into the selected
factory's Exit_Object must therefore obtain that factory's own geometry.

For an available factory the native sequence is:

```text
++ScenarioInit
Unlimbo(Exit_Coord(), DIR_E)
  success:
    Mark(MARK_UP)
    Set_Coord(Exit_Coord())
    Mark(MARK_DOWN)
    RADIO_HELLO(product)
    RADIO_TETHER
    Assign_Mission(MISSION_UNLOAD)
    --ScenarioInit
    return 2
  failure: existing native failure path / ScenarioInit balancing
```

The coordinate helper is called twice. Patching only the first Unlimbo
argument would leave the subsequent Set_Coord at the old location.

BuildingClass::Exit_Coord, `0x00434580`, returns exactly
`PositionCoord + Coord(98, 188, 0)` for WeaponsFactory. Binary additions are
at `0x004345B4` and `0x004345B7`. The separate native ExitCoord Art value is
consulted only in the other branch, not as an override for this special case.

Facing is the immediate `0x40` (DIR_E), pushed at `0x0042CB6D`; Unlimbo is
called at `0x0042CB8D`. The second coordinate helper call is `0x0042CBB4`.
The building's facing/StartFacing does not substitute this direction.

## Door and physical exit state machine

BuildingClass::Mission_Unload is bound at `0x00433540`. Its first geometry
operation reads Class->ExitList[8], adds the building anchor and converts
that cell to a world coordinate. It does not call Find_Exit_Cell to find an
alternative free perimeter cell.

| Status | Native operation | Completion condition |
| --- | --- | --- |
| INITIAL | Product gets Guard/Commence; Door.Open_Door(DeployTime), production animation, redraw | Advance to CLEAR_BIB |
| CLEAR_BIB | Clear_Weapons_Factory_Bib scatters blockers around the fixed door cell | Advance to OPEN only when it returns false |
| OPEN | Wait for Door.Is_Door_Open; Unit gets Move; locomotor-specific egress; speed 0.5 | Advance to LEAVE after dispatch; missing contact closes the door |
| LEAVE | Keep the physical factory busy | Close only after building IsTethered becomes false |
| CLOSE | Wait for Door.Is_Door_Closed, then Enter_Idle_Mode/redraw | Factory can service the next exit |

The fields involved include Building::Status, Door, Radio, IsTethered,
PlacementDelay and Factory; Unit::Radio, Mission/MissionQueue, NavCom,
ArchiveTarget and navigation queues; and the locomotor's TrackNumber,
TrackIndex, HeadToCoord, DestinationCoord, IsDriving and occupation state.
These already participate in the existing native save/load lifecycle.

Drive uses Force_Track(66, doorCoordinate), with track-coordinate Z set to 0.
Tunnel locomotors take a separate Drive-piggyback path. Other locomotors use
an explicit destination at anchor+(3,1). D5 must not accidentally extend its
supported visitor scope into these other locomotor paths.

## Track13 is geometry, not pathfinding

OUT_OF_WEAPON_FACTORY is track number 66 (0x42), selecting Track13. The native
table at `0x006CF000` contains 69 records of three 32-bit values: X, Y and
Dir256. All 69 records were compared statically with OpenTS Track13:
zero mismatches. First offset is (-670,-68), the terminator is (0,0), and
facing is DIR_E throughout. The raw track's Cell marker is -1.

For the usual 3x3 weapons factory, ExitList[8] is (3,1):

```text
door cell center relative to anchor center: (+768,+256)
first Track13 point relative to door:       (-670, -68)
sum / original spawn:                      ( +98,+188)
```

The index is a role by convention, not a reliable property of arbitrary
ExitLists. For example, the native 3x2 list has (3,0) at index 8. A short
custom exit list is unsafe: both consumers dereference index 8 unconditionally.

DriveLocomotionClass::Force_Track `0x0047E470` sets TrackNumber and TrackIndex,
starts the driver toward the supplied endpoint, and records destination/speed
when start succeeds. Its COM return type is void; Mission_Unload cannot use
it as a checked success/failure operation.

Start_Driver calls Stop_Driver, sets HeadToCoord/IsDriving, invokes the target
cell's Goodie_Check and marks track occupation. This is not a complete
Can_Enter_Cell/path search over all crossed cells. While_Moving
`0x0047E740` walks the fixed samples. Smooth_Turn adds HeadToCoord to their
offsets (plus applicable TrackControl transformations). It updates actual
cell occupation on transitions. At track completion it stops the driver,
clears the track and invokes Per_Cell_Process(PCP_END).

Mark_Track manages the endpoint reservation and any configured intermediate
Cell marker; for Track13 that marker is absent. It does not remove the
building's foundation or temporarily turn every corridor cell into free land.

A different endpoint with the original spawn causes a discontinuity at the
first sample. Two independently chosen points do not become a valid track
merely by exposing two INI keys. Generic Move is also not an automatic
replacement: ordinary navigation must not be assumed to traverse occupied
WeaponsFactory cells like the forced track.

## Bib clearing, blocking and release

Clear_Weapons_Factory_Bib, entry `0x0042FF70`, reads ExitList[8] and checks
Cell_Techno while excluding this building. If occupied, it calls Incoming
on the exit cell and, where occupied, its eight adjacent cells, then returns
true. Otherwise it returns false. It requests scatter; it does not clear a
foundation cell, force-delete an occupier or guarantee that a static blocker
can move. Mission_Guard also calls this helper, so safety cannot be restricted
to the one Mission_Unload call site.

There are separate blockage phases:

- Before placement: factory selection/IsHoldingExit can retain a completed
  limbo product. Failed placement is not universally retried by every caller.
- After Unlimbo: CLEAR_BIB retains the spawned, tethered vehicle while the
  native exit is occupied. It does not select the next ExitList candidate.
- After dispatch: the native forced track is not a new per-cell obstacle
  planner. A custom corridor needs an explicit safety contract; a test of the
  endpoint alone does not prove no stacking over its whole span.

Unit::Per_Cell_Process, entry `0x006511B0`, performs the relevant release
checks under PCP_END. It considers IsTethered, missions, NavCom arrival,
Contact_With_Whom and the building occupying the current cell. The building
comparison protecting WeaponsFactory release is visible at `0x0065175C`;
the RADIO_UNLOADED call is at `0x00651772`.

Vinifera's Building RX replacement at `0x004268C0` passes RADIO_UNLOADED to
TechnoClass::Receive_Message and returns RADIO_RUN_AWAY for WeaponsFactory.
The existing queue/rally/AI/harvester continuation then runs. Door LEAVE
waits on the resulting untethering. Do not add a second reservation owner or
force early release just because a custom endpoint has been reached.

An unoccupied hole inside a large mask is not necessarily an exterior exit:
the ordinary vehicle may still be enclosed by occupied cells after untethering.

## Smallest candidate configuration: one translated native track

This is a design candidate, NOT an accepted/implemented INI contract.

Prefer Art `UnitSpawnCell=X,Y`, relative to the building anchor, with the same
X/Y axes as Foundation entries. Preserve the original east track's shape and
derive its complete translated tuple:

```text
S = configured local spawn cell
translation = S - Cell(0,1)
E = S + Cell(3,0)                         # local door/track-end cell
spawnCoord = Coord(anchor+S, buildingZ) + Coord(98,-68,0)
trackEndXY = Coord(anchor+E, buildingZ).XY
initialFacing = DIR_E
```

The internal (98,-68) offset stays within the configured cell. This preserves
`spawnXY = trackEndXY + (-670,-68)`. A raw cell-center spawn would not preserve
that equality. Exposing the subcell correction as a modder pixel offset is
unnecessary.

For this translation-only candidate, a second UnitExitCell is redundant.
It would imply independence which Track13 does not provide. Free spacing,
rotation, arbitrary curved corridors or two independent points need a
different complete movement contract; they are not supplied by this candidate.

Validation would have to establish:

- The configured building is an ordinary land UnitType WeaponsFactory,
  without Refinery, FreeUnit, aircraft/infantry/repair/naval or deploy roles.
- S is in bounds and occupied in the actual mask, not merely its rectangle.
- Every cell crossed by the translated native track has the intended
  occupation/terrain relationship. An unoccupied interior cavity is not a
  guaranteed exit. E must reach usable exterior space.
- Map bounds, bridge state, heights and dynamic occupation are safe when the
  output is attempted and when the door dispatches it, not only at INI load.
- Only supported Wheel/Track Drive products enter this contract; reject or
  route unsupported products without unsafe native fallback or endless busy.
- Door drawing/art agrees with the translated corridor. Geometry settings
  cannot relocate pixels inside an existing SHP animation.

A first conservative shape can put S three cells west of an exterior east
edge with the three internal row cells occupied. That is a restriction of the
native-track candidate, not proof that arbitrary masks need to be rectangular.
Native foundations could use the same explicit opt-in after actual native-mask
validation; S=(0,1) on the usual 3x3 factory reproduces the original tuple.

No key / no D5 contract must preserve the entire native output path. Invalid
custom-factory configuration must retain the current safe rejection/fallback,
not enable a custom mask while silently using the old output geometry.

## Save/load and CRC: compatibility gate

Current AbstractClassExtension::Internal_Save/Internal_Load write/read a raw
blob of Get_Object_Size(). BuildingTypeClassExtension returns sizeof(*this).
Extension::Get_Save_Version_Number adds that size, in addition to the existing
0x1A0000 basis and other sizes. Simply appending a bool/Cell to the class would
therefore change both the stream layout and the calculated version. Keeping
the visible basis unchanged does NOT make existing saves compatible.

No such fields or version changes were made here. The existing D4b layout,
Cross-Playthrough policy, DemandLoad fix and swizzle contracts remain untouched.

Before implementation, choose and verify a compatibility mechanism. Possible
directions requiring separate design are explicit legacy-layout migration or
an optional, versioned auxiliary configuration stream with type identity checks
and legacy absence meaning no D5 configuration. Neither is an existing proven
per-type optional-field mechanism in this path. Reusing Infantry/Aircraft/Repair
fields or object padding would hide ownership/layout problems and is rejected.
Reparsing current ArtINI after load is not equivalent to restoring saved type
configuration and must not silently be substituted for persistence.

CRC integration must hash canonical scalar configuration with a distinct
domain, preserve the old stream when absent, include explicit native-foundation
configurations in the existing FRAMESYNC configuration collection, and invalidate
derived caches on parse/reset/load. No CRC or synchronization change is made
by this research-only document.

## Why implementation stopped and concrete next step

The source proves several mechanisms but does not by itself establish safe
arbitrary custom egress. In particular:

1. A void Force_Track plus an endpoint-only bib test does not prove safe
   dispatch over an arbitrary mask/terrain corridor or recovery when start
   does not establish driving. A complete preflight/dispatch failure contract
   must be audited against the actual holding/completion callers.
2. A generic Move replacement has not been proven to cross occupied factory
   cells, preserve end-of-track PCP timing, honor queued player orders and
   release the tether exactly once. It must not be installed speculatively.
3. A free UnitExitCell cannot be combined with unchanged Track13. The
   translation-only candidate needs one shared geometry result used by both
   spawn calls, both door consumers, destination interception and readiness.
4. Compatible persistence for new configuration is not supplied by adding
   normal raw extension fields. A deliberate compatibility design is needed.

Next increment: audit and implement the translated Track13 candidate as one
complete contract, after specifying compatible configuration persistence.
Trace original and translated sample cells, endpoint reservations, Goodie_Check
failure and blocked dispatch through the actual player/AI caller paths. Audit
the exact registers, stack buffers, displaced bytes, continuations and existing
hook overlap at every chosen substitution. Only then enable the WeaponsFactory
validator exception, parser, shared geometry helpers, persistence and CRC
together. Do not ship a spawn-only intermediate patch.

Subsequent user runtime coverage should include two queued products, exterior
and interior blockers, map edges/heights, native no-key behavior, Wheel/Track,
unsupported products, alternative-factory selection, player orders, building
loss and saves in INITIAL/CLEAR_BIB/OPEN/LEAVE/CLOSE, plus an old pre-D5 save.
This describes future coverage; no build, compiler, automated test, game launch
or runtime test was executed for this research.

## Implemented D5 contract

The implementation uses one optional, strict decimal pair in the building's
effective ArtINI/GraphicName section:

```ini
UnitFactoryExitCell=X,Y
```

It is the local **door/track-end cell**, relative to the building anchor,
using the same X/Y axes as Foundation entries. It is not a spawn cell, rally
point, pixel offset or world coordinate. No UnitSpawnCell, UnitExitCell,
exit-facing option, rotated track or global track data is introduced.

Let B be the building's anchor cell, E the configured pair and Z its height:

```text
worldExitCell = B + E                     # checked as ints before short conversion
doorCoord = worldExitCell.As_Coord(Z)      # cell center
spawnCoord = doorCoord + (-670,-68,0)      # exact first native Track13 point
spawnCell = B + E - (3,0)
translation from native reference = E - (3,1)
spawnFacing = DIR_E                       # original native PUSH 40h, unchanged
```

Mission_Unload receives E in place of its ExitList[8] value. The original
native conversion, Drive Track 66 dispatch, Z=0 track argument and speed 0.5 remain.
Drive's existing HeadToCoord-relative sample interpretation translates the
whole unchanged Track13. Both Exit_Coord consumers receive the same spawn.
Assign_Destination and the no-contact readiness cell receive the same
translation E-(3,1); the native queue logic and comparisons are retained.
Mech uses the native Assign_Destination branch rather than Track66. Its
caller now supplies E too, so the native exit comparison accepts it instead
of queuing the old (3,1) request and returning before assigning the exit.

For a normally cell-centered native 3x3 factory, E=(3,1) gives door offset
(768,256) and spawn offset (98,188) relative to PositionCoord, exactly the
original geometry. Its destination and readiness translations are zero.

### Vanilla equivalence and the identity path

D5c checks this invariant before every one of the nine geometry hooks:
native (not custom) BSIZE_33, E=(3,1), actual native ExitList[8]=(3,1),
and PositionCoord equal to its cell center. If all hold, no effective
geometry override exists: the geometry handlers return 0 and the original
native instructions run. D5g adds one deliberate non-geometric exception:
Clear_Bib handles a released Hover blocker at the native exit, with or without
the key. Spawn validation, dispatch, recovery and all geometry identity checks
remain native; see the D5g section for the clearing-only exception.

The saved Set/Cell configuration and its CRC remain present. This is a
geometry identity, not a parser reset or special case for a building/unit
ID. Custom masks, different native sizes/lists, uncentered anchors and
nonzero translations still use the translated contract below. In particular,
custom 3x3 masks never bypass their own geometry/safety handling.

### Defaults, eligibility and validation

The Set field is false by default and after INI reset. Without the Art key,
the parser returns immediately and all D5 hooks replay their original code.
There is no automatic activation from CustomFoundation=yes or WeaponsFactory.
The existing custom-foundation rejection/native fallback for an unconfigured
WeaponsFactory is retained.

Explicit configuration supports pure land Factory=UnitType / WeaponsFactory
types on either native or custom foundations. It does not turn a generic
UnitType factory into a WeaponsFactory. Refinery/Weeder/FreeUnit, repair,
reload/service, aircraft/infantry/naval, deploy and conflicting special roles
are excluded. The custom foundation scope exemption requires a valid explicit
D5 configuration; existing Infantry/Helipad/Repair exemptions remain intact.
Visual BibShape is allowed for this validated contract. Native foundations
retain support for Bib=yes/IsBibbed, as used by GAWEAP. Since D5e, a pure
custom-foundation D5 Unit WeaponsFactory may retain it too: the explicit
mask owns every occupied row, and no implicit bib row is appended. Other
custom roles receive no new Bib exemption. See the D5e audit below.

Parsing rejects missing components, trailing garbage, overflow and truncation.
E.X must be in [-32765,32767] so E.X-3 fits a Cell; E.Y must fit a signed short.
E must not be an occupied cell of the actual mask: the physical exit cannot
finish inside the factory's own occupied footprint. Native masks are checked
against the bounded native Occupy_List, not a synthesized rectangle.

There is no required foundation width/height, no required rectangular mask,
no requirement that spawn or corridor cells belong to the mask, and no
requirement that E lie within the bounding box. E can be outside it or in an
open part of an irregular mask. The mod must provide exterior access from E;
an enclosed hole is not made into an escape route by this feature.

An invalid key/role logs a normal configuration warning and leaves the
override disabled. A rejected custom factory retains the existing native
foundation fallback rather than publishing a custom mask with old geometry.
If the complete custom scope check rejects the type later, it also warns
and the existing foundation reset clears the D5 anchor.
At runtime, world-cell additions are checked before Cell conversion. A spawn
or endpoint outside Map.In_Radar is refused before ++ScenarioInit/Unlimbo.
Negative spawn lepton coordinates are rejected before Coord::As_Cell can
truncate them toward zero and alias an in-map cell.

returns the anchor; MOV CX,[EAX] and MOV DX,[EAX+2] load only its low words.

#### Proven blocker and minimal fix

D5c's `Unit_Factory_Cell_Clear` calls
`Can_Enter_Cell(cell, FACING_E, -1, nullptr, true)` for corridor cells outside
the producing building. Unit.Can_Enter_Cell (`00655330`) calls the native
virtual Can_Reach (vtable+180h) at `0065554C`, passing cell_level by reference.
For Unit's native vtable this resolves to Foot's `entry_180` / Can_Reach
at `004A5020`. Disassembly confirms the source behavior:

- `004A5099–004A50CE`: -1 is resolved only for the previous bridge cell's
  special deck case. It is not a general "use ground height" default.
- `004A50D4–004A50F9`: subtract destination Cell.Height from that cell level.
  On ordinary level-zero ground this is -1-0=-1.
- `004A5198–004A51C5`: an absolute difference of one requires a matching
  ramp. Flat ground has none, so `004A51BF` returns 7 (MOVE_NO).
- With ordinary nonnegative higher ground levels, -1 likewise produces an
  invalid transition on a flat corridor. The caller's MOVE_OK test fails.

The endpoint B+(3,3) is outside the native 3x3 factory (also outside its
native bib row because X=3). Therefore even with no blockers and valid
terrain, the four-cell corridor loop necessarily invokes this bad height
argument there. `Clear_Unit_Factory_Exit` returns true and the existing
`0042FF70` hook keeps Mission_Unload in CLEAR_BIB at `0043363C`. INITIAL
already requested door opening, explaining the open door with no movement.
If OPEN is reached from another state, `00433670` performs the same query
and returns to CLEAR_BIB before Force_Track. The (3,1) identity bypasses both
extra checks; Mech/Hover return early from the Drive-only corridor query.

Consequently, for this proven flat-ground failure, Force_Track(66) is not
called: no Track66 HeadToCoord/index is installed, no Track66 motion or
PCP_END occurs, no end-of-track RADIO_UNLOADED occurs and the tether/busy
state remains. Constructor TrackNumber/TrackIndex are -1/-1, but their
exact later runtime values in the reported run were not captured. This is
a pre-start failure, not an observed track-completion or radio defect.

**D5d changes only the height argument to `product->Get_Cell_Height()`.**
That is the native pattern in drive.cpp (for example lines 1105, 1398 and
1479). On the supported level corridor it supplies the actual level, so a
flat-to-flat check has difference zero. Bounds, overflow, bridge exclusion,
ground-height equality, occupier checks, native passability, four-cell
coverage and all retry states stay in place. No occupation bits are cleared.
`0043392D` was re-audited: its original seven bytes set Status=3, EAX remains
the acquired IPersistStream pointer, continuation `00433934` tests/releases
it, and it performs no origin calculation. It is unchanged. All nine D5
hooks, their lengths/bytes/register/stack/flags contracts and continuations
are unchanged; there is no new hook or patch address to validate.

No unit-ID checks, new fields, layout, INI, CRC or save changes are made.
Save basis remains 0x1B0000 (last user-observed full value 0x1F0450).
The existing D5c identity guard, D5a bib compatibility, D4b and all unrelated
systems remain unchanged. The earlier translated-Hover ion-storm limitation
is not addressed by this Drive-only correction.

#### Complete native Clear_Weapons_Factory_Bib contract

Entry `0042FF70` is __thiscall (ECX=Building). Native callers include
Mission_Guard at `0043039D` and Mission_Unload's CLEAR_BIB state at
`00433635`. A true return means "blocked/requested clearing", not "cleared".
Mission_Unload tests AL at `0043363A`: true waits at `004339B3`; false sets
OPEN at `0043364F`. No separate D5 retry timer is needed.

1. Check IsWeaponsFactory. Otherwise return false.
2. Load packed ExitList[8] at `0042FF97`, add Building.Get_Cell(), and get
   that map cell. For the native 3x3 reference it is B+(3,1), the actual
   door/Track66 endpoint, not the spawn or a bounding-box center.
3. Call Cell_Techno(Point2D(0,0), false, this) at `00430011`. It scans the
   ground object chain for the nearest Techno, excluding this building.
   There is no owner filter: own/allied/enemy Units, Infantry, Buildings
   and other ground-chain Technos may trigger it. Terrain alone is not
   a Techno; aircraft count only if actually in that ground cell chain.
4. If the endpoint has no such object, return false immediately. Native
   Clear_Bib does not require eight empty neighbors or a four-cell corridor.
5. Otherwise call endpoint.Incoming(COORD_NONE,true,true,false) at
   `00430045`. Then enumerate FACING_N, NE, E, SE, S, SW, W, NW. For each
   adjacent cell with a Techno other than this building, call
   Incoming(endpoint.As_Coord(),true,true,false) at `0043009D`.
6. Return true even if some requested objects cannot move. Later native
   calls inspect actual occupation again. D5 additionally bounds-checks
   map cells; it does not convert a request into immediate permission.

Neither IsBibbed, Height(true), foundation Width/Height nor an implicit
bib row occurs in this routine. CustomFoundation's mask affects actual
occupation and candidate passability, not its eight-neighbor offsets.
The extra Y rows can block some candidate cells, but 5x5 by itself is not
an explanation for an infinite wait. BibShape is not an occupation source.

`CellClass::Incoming` (`004577D0`) snapshots its ground occupiers, then
calls their virtual Scatter at `00457927`. With nokidding=true its normal
scatter/IQ permission gate is bypassed, while each object's own Scatter
rules still apply. Unit Scatter is `00658D80`:

- Can_Scatter still refuses Sleep/Sticky/Unload and trains; active facing
  rotation can defer it. Guard/idle is eligible. forced=true bypasses the
  ordinary mission's IsScatter preference, not collision or terrain checks.
- nokidding=true permits replacing a navigation target, subject to native
  rotation/dumping restrictions. The factory is not passed as a Threat
  object: the argument is a Coord. There is no special tether bypass.
- COORD_NONE selects native Nearby_Location around Destination_Coord
  (`005161A0` call at `00658E8E`) and assigns the chosen native destination.
  The search expands square rings, potentially beyond the eight neighbors;
  it checks normal map occupancy, terrain, speed and height. It is not a
  fixed move to exit+(1,0).
- A nonzero threat selects a direction away from that coordinate, with
  native random facing adjustment, and checks up to eight adjacent cells
  around Destination_Coord. Native Can_Enter_Cell and height checks select
  the legal destination; the native routine assigns Move/destination.
- Buildings/terrain/immovable objects do not become movable because they
  receive Scatter. Incoming may dispatch to all objects in its snapshot,
  but they retain their own virtual behavior. Infantry keeps its native
  Scatter restrictions, including its moving/combat checks.

The native bib/own-building authorization in Can_Enter_Cell is retained;
mask cells are not simply deleted from occupation. Some native bib-edge
cells can legitimately be traversable, while other own-mask cells block a
candidate. Actual target choice depends on live occupation, mission,
Destination_Coord and random state and cannot be read from this log.

#### Incoming and virtual dispatch

The native `Clear_Weapons_Factory_Bib` entry is 0042FF70. It reads the ninth
exit-list cell, adds BuildingCell and tests ground-layer Cell_Techno excluding
the building. At 00430045 it calls **CellClass::Incoming**, not a Techno method:

```cpp
void CellClass::Incoming(const Coord& threat, bool forced = false,
    bool nokidding = false, bool bridge = false); // 004577D0, thiscall
```

The endpoint gets `(COORD_NONE, true, true, false)`; the eight occupied
neighbors get `(exit.As_Coord(), true, true, false)` at 0043009D. COORD_NONE
is the all-zero Coord, an absent threat source, not a destination and not
the SDK Scatter declaration's default Coord(-1,-1,-1). `forced` bypasses the
mission's ordinary scatter preference; `nokidding` bypasses Incoming's
elite/ability/IQ/Rules scatter permission gate and Scatter's ordinary
existing-NavCom refusal. These are not a `scared` argument. `bridge=false`
selects the ground object chain. Neither boolean disables terrain/collision
checks or every mission/facing restriction.

offset 144h (call 00457927). The dispatch is:

| --- | --- | --- |
| ObjectClass | 00585040 | Base no-op, void |
| TechnoClass / FootClass | No separate Scatter override | Inherit the object's concrete derived override |
| UnitClass, including Drive, Mech and Hover | 00658D80 | Native ground-unit Scatter, void |
| InfantryClass | 004D60A0 | Infantry override, void |

#### Exact native mismatch and target selection

Unit::Scatter first tests Can_Scatter, mission scatter permission, primary
facing rotation and the NavCom/nokidding gate. Can_Scatter retains Sleep,
Sticky, Unload and train restrictions. Hover is not explicitly excluded.

At 00658DDE–00658E0C the threat is compared with zero. The zero-threat branch
at 00658E12 calls Nearby_Location at 00658E8E, with
`Destination_Coord().As_Cell(), Class->Speed, -1, MZONE_NORMAL, IsOnBridge,
Point2D(1,1), false, true`. It then assigns the returned cell, if nonempty,
at 0065925E. This branch does not request MISSION_MOVE itself.

Native Nearby_Location (005161A0) starts at radius zero
(0051627E/00516288), so the current destination cell is a candidate.
Map/Cell Is_Clear_To_Move uses movement terrain, zone and the cell's
occupation flags; the ground flags test at 00459190–004591B2 does not walk
the Cell_Techno object chain used by the factory's blocker test.

Hover's movement reservation is different from object-chain presence.
While_Moving (004CF820) clears the previous HeadToCoord reservation through
Unit::Clear_Occupy_Bit at 004CF85C, then clears HeadToCoord. A hovering object
can remain physically in that cell's object chain after its transient move
reservation has been cleared. This lets radius-zero Nearby_Location select
the very cell which Clear_Bib still correctly sees as occupied by the Hover.

This is a selected but useless target, not a fundamental lack of Hover move
support. Unit::Assign_Destination (00657520) can do nothing if the target is
already NavCom. Otherwise Hover::Move_To (004CF660) stores the destination;
Start_Of_Move (004D0D40) recognizes the current cell at the appropriate
height, calls Stop_Moving and clears the linked NavCom. No spatial escape
results, and the factory sees the same object on the next retry.

The nonzero-threat branch (00658EC1 onward) instead chooses among eight
adjacent cells around Destination_Coord, in a native order biased away from
the source with native angular randomness. It retains paralyzed, dumping,
rotation and target guards; for each candidate it uses native map bounds,
Can_Enter_Cell with **Get_Cell_Height()**, terrain/occupation and bridge
logic. SpeedType/MovementZone suitability is evaluated by the existing
movement checks; it does not substitute the zero-branch MZONE_NORMAL search.
On success it calls Assign_Mission(MISSION_MOVE) at 00659242, then the
ordinary virtual Assign_Destination at 0065925E. No valid adjacent candidate
means no assignment. This is the same directional branch already used by
the factory's neighbor clearing and D5f corridor requests.

The mismatch exists in the native binary, independent of D5 geometry. It
does not imply that every Hover scatter always fails. A released Hover with
different reservations/goals can get a useful zero-threat result. Nor does
the supplied log alone prove that no separate facing/mission refusal ever
occurred; the fix retains those refusals.

Hover was not an unused stock unit category: Westwood's original manual
describes the GDI Hover MLRS and vehicle production from War Factories
(printed pages 13, 23 and 38). See the
[original TS manual](https://static.wikia.nocookie.net/cnc_gamepedia_en/images/b/be/Manual_Tiberian_Sun.pdf/revision/latest).
No claim that Westwood omitted this case because Hover was unproducible,
or any historical explanation of the defect, is supported here. A separate
unmodified-vanilla runtime test was not performed by Codex.

#### Hover movement, release and state comparison

height. Head_To_Coord (004CF5F0) falls back to the linked PositionCoord when
HeadToCoord is empty. Stop_Moving (004D0B70) clears the destination/path when
destination and head differ. Native path failure, power-off and Ion Storm
sensitivity remain effective and are not altered.

Hover Process (004CED20) and While_Moving contain the PCP_END calls for
arrival. Unit::Per_Cell_Process (006511B0), at its tether/arrival branch
0065175C, sends RADIO_UNLOADED at 00651772. The building's existing
Receive_Message path (004268C0) delegates to Techno's native handling:
UNLOADED sends UNTETHER and OVER_OUT; OVER_OUT clears the contact and
untethers. Factory LEAVE/CLOSE and follow-up production use this ordinary
release. There is no private D5 Hover arrival/release state machine.

For D5g, release is also an explicit runtime precondition: **IsTethered must
be false and Radio must be null** before the directional substitute is used.
An active factory partner is not forcibly detached, retargeted or treated as
released. This makes the implementation independent of an unrecorded
assumption about that object's flags in the supplied log.

For Drive and Mech the Incoming/Unit::Scatter dispatch and void return are
identical. Drive::Start_Driver reserves its head through Mark_Track;
Stop_Driver clears HeadToCoord/IsDriving without clearing that arrived-cell
bit. Mech::Mark_Head_To(COORD_NONE) explicitly restores the occupation bit at
PositionCoord. In contrast, Hover::Stop_Driver clears its head reservation
without restoring a current-cell bit, and While_Moving also clears the
head reservation. Their ordinary stopped occupation therefore prevents the
radius-zero free-cell result that can occur for Hover. Nearby_Location can
choose a different free cell, assign native NavCom and start Drive/Mech
movement. No invented per-instance before/after missions or exact chosen
coordinates can be supplied from this log. The observed contrast is the
user's automatic clearing for Drive/Mech and failed native Hover case.

In the question's alternatives, the proven defective path is a combination
of **E (reservation/object-chain mismatch)** and **C (same-cell goal accepted
and already completed)**. It is not an intentional global prohibition on
Hover scattering, and does not justify a general Hover mission rewrite.

#### Minimal implementation and hook contract

D5g changes only buildingext.cpp, buildingext.h, buildingext_hooks.cpp and
the two D5 documentation files. New helpers identify RTTI_UNIT plus the
**live** locomotor CLSID via the existing IPersistStream query, require full
release, obtain the effective configured exit or native ExitList[8], and
detect a released Hover on its ground object chain. The fallback is limited
to land UnitType WeaponsFactories, not naval/float factories. No ID lookup,
new mask rule or product eligibility rule is added.

When such an endpoint is being cleared, the helper reproduces Incoming's
snapshot dispatch with nokidding=true. Only each released Hover receives
the factory cell center as a nonzero **source**, not a destination. Other
objects in the same snapshot still receive COORD_NONE. Without a released
Hover, the original Incoming(COORD_NONE,true,true) call remains. Neighbor
Incoming and D5f corridor snapshot/scatter remain unchanged. All destination
selection, mission assignment, collision and movement happen in native
Unit::Scatter/Assign_Destination/locomotion, with no custom Move-East command.

The existing 0042FF70 hook is sufficient; **no new hook is added**. Its active
condition is extended from effective D5 geometry to effective D5 geometry
OR a released Hover endpoint blocker, so native identity and key-absent
factories get the same scoped correction. The other eight hook bodies and
the geometry identity predicate remain unchanged.

ABI: native thiscall ECX=Building; six displaced bytes
`83 EC 20 53 55 56` are SUB ESP,20h / PUSH EBX / PUSH EBP / PUSH ESI.
The active helper runs before that prologue, sets EAX to the blocked boolean
and continues at **004300C3**, the bare RET, with the original incoming stack
and no argument cleanup. Syringe's saved register context preserves the
non-result registers; no FPU instruction or new stack slot is displaced.
EFLAGS are not a function-return contract: native callers explicitly test AL
(Unload's test at 0043363A after call 00433635; Guard call at 0043039D).
The inactive return 0 still replays the complete native prologue. Address,
length, displaced instructions and continuation are unchanged.

Clear_Bib still returns **true=blocked** for the current attempt, even after
a scatter request. Only a later real occupancy/passability recheck permits
OPEN. D5f's four-cell Drive corridor and OPEN recheck are preserved, as are
the D5d Get_Cell_Height fix and D5e role guards. Track66, Track13, DIR_E,
Spawn=Door+(-670,-68,0), E translation, Mech/Drive dispatch, rally/ArchiveTarget,
CustomFoundation masks, repair, helipad, FixedWing, infantry, refinery and
naval systems are not modified by D5g. Static preservation is not a new
runtime regression-test result.

No persistent fields, class layout, virtual methods, Save/Load, CRC or save
version are added/changed. The header adds one nonvirtual query only.
The save basis remains **0x1B0000**; the last user runtime value remains
**0x1F0450**, not a newly measured value. Snapshot vectors are temporary.
