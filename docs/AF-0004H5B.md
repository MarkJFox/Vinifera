# AF-0004H5B — Unarmed turnback after unavailable CAP attack regroup

After completed egress, FixedWing CAP autoattacks still try both existing
REGROUP sides first. If neither route fits, a live target and positive ammo
permit an unarmed TURNBACK toward the current target. A successful fresh
geometry check returns through the existing INGRESS controller. A bounded
watchdog or invalid target/ammo/flight conditions end the attempt cleanly.

This increment was inspected statically. No build, automated tests, runtime
tests, test files, commit or push were performed. The behavior described below
is implemented behavior to validate locally, not a claimed H5B runtime result.

## Confirmed user observations and root cause

The supplied H5A runtime result confirms that Escort now works:
UI_OBJECT_GUARD_AREA -> target kind 52 -> CAP_SET_ESCORT, followed by vehicle
tracking and enemy acquisition near the Escort. H5B leaves that transport and
Escort selection intact.

The separate attack case reached ATTACK_TARGET_PASSED, spent one ammo unit
(5 -> 4), and reached ATTACK_EGRESS_COMPLETE. Both subsequent ATTACK_REGROUP
candidates reported invalid outer-radar next-ingress/staging points. Existing
code then ended the attack and resumed CAP. The same run also demonstrated
successful ordinary REGROUP -> INGRESS -> committed passes elsewhere.

`Start_Regroup` constructs next ingress at `R + 4*U` beyond the target in the
outward direction, another `2*U` beyond that, and lateral staging at `4*U` on
either side. Each candidate requires current->staging->ingress->target to fit.
Those future points can cross outer In_Radar even when the current completed
pass and its shorter safe egress fit. These are different geometric questions.
Failed future staging therefore does not prove that the aircraft cannot turn
back or that the preceding pass was unsafe.

## Native TS principle and evidence

Primary native evidence remains `C:/dev/Aftermath-Engine/references/ts-patches/input.dat`.
The H4 reconstruction in [AF-0004H4](AF-0004H4.md) distinguishes native binary
confirmation from OpenTS reconstruction. Relevant supporting sources are
`references/OpenTS/code/aircraft.cpp`, `fly.cpp` and `facing.cpp`, with TSpp
signatures in `TSpp/src/tspp/tspp_definitions.cpp`.

- Native Aircraft attack uses Is_Strafe, straight-flight lock and a post-shot
  mission delay. It does not require the FixedWing lateral staging/next-ingress
  corridor. Once unlocked, destination steering and Facing/ROT bring it back
  toward its target.
- Native Fly::Nearing_Target at `0x0049BBA0` eventually calls
  FacingClass::Set_Desired (`0x00496590`) for the primary facing toward its
  movement destination. The inspected block at `0x0049BCEB..0x0049BE5E` shows
  the strafe/lock/proximity gating and the facing call. OpenTS `fly.cpp` explains
  the matching branch; H5B reuses the existing FixedWing equivalent steering.
- Reconstructed `FacingClass::Set_Desired` starts from Current(), assigns the
  desired facing and derives turn time from angular arc / ROT. It does not snap
  the current facing to the new heading.
- Native Mission_Attack at `0x0040BA40` checks Status against 10 at
  `0x0040BA51..0x0040BA58`; larger unsigned values branch to its default at
  `0x0040C502`. H5B's TURNBACK value is deliberately outside native firing
  status slots, protecting a temporary native-controller fallback.

The H5B turnback is an adaptation of this steering principle inside the
FixedWing state machine. It is not a copy of the native strafe shot sequence
or native three-cell steering gate. No Ares/Antares/Phobos behavior is needed
to define TS flight bounds. All references were read only.

## Activation and state transitions

The only entry to `Start_Turnback` is in `Attack_Arrived`, after the real
EGRESS exit plane was reached and ATTACK_EGRESS_COMPLETE was emitted:

```text
EGRESS_COMPLETE
  -> target/ammo/range still usable?
  -> unchanged Start_Regroup: side A, then side B
       accepted: unchanged REGROUP -> INGRESS -> ATTACK_PASS
       both rejected:
         active valid CAP + Ammo > 0 + valid aircraft flight point?
           -> TURNBACK
           -> fresh safe ingress available?
                -> existing Start_CAP_Ingress -> INGRESS
                -> normal alignment and Start_Pass -> ATTACK_PASS
           -> invalid/expired/stuck?
                -> existing End_Attack -> CAP or RTB
```

This includes initial run=0 positioning EGRESS from CAP_TO_E and subsequent
armed-run EGRESS. It does not replace ordinary REGROUP, intervene before
EGRESS_COMPLETE or add a fallback to explicit non-CAP attacks. Static and
Escort CAP share the same controller and entry conditions. Unlimited/negative
Ammo does not enter this new positive-ammo fallback; its existing path remains.

`TURNBACK = 0x100` is an explicit AttackStatus. Existing FixedWing status
numbers 0..4 are unchanged. Value 0x100 does not alias native Aircraft firing
states 0..10. No native/UI hook address or instruction length changes.

## Movement during TURNBACK

The aircraft keeps TarCom and NavCom pointing to the same current attack
target. Each controlled frame refreshes Fly::DestinationCoord from that
target's current Center_Coord. It clears the straight-flight lock and continues
ordinary cruise. Existing Process uses current-position->DestinationCoord
heading outside ATTACK_PASS/EGRESS, so PrimaryFacing.Set_Desired and the normal
ROT interpolation produce the turn. It does not force left/right or assign a
new artificial off-map staging point.

H5B writes the Fly movement destination directly. Calling the public
FixedWing Assign_Destination here would also run mission/command-navigation
handling, so it is unsuitable for changing only an attack movement goal.
The current target is not searched for again or replaced. Escort context stays
intact; the target of TURNBACK is the enemy TarCom, not the moving CAPEscort.
If the attack later ends, existing CAP logic samples the then-current Escort.

TURNBACK has its own early-return branch in Attack_AI, and Attack_Arrived
does not interpret its movement as an ingress arrival or pass-plane crossing.
There is no Fire_At call or new Can_Fire shortcut in this phase. The existing
ATTACK_PASS firing branch remains the only armed FixedWing attack phase.
Even crossing the target during the turn is unarmed.

## Fresh ingress and direction preference

Let `R = Attack_Range(a)` and `U = Turn_Room(a)`, both unchanged existing
helpers. Every TURNBACK retry uses the current aircraft position, current
primary facing and current target position.

1. Require planar distance to target >= U, and the existing Heading_OK
   tolerance between current primary facing and current target bearing. This
   is a turn-capture gate, not a new ingress-distance formula or permission
   to fire.
2. Use the live target bearing and its opposite as two candidate attack axes.
   Compare their forward vectors to the previous outward axis: try the axis
   facing more against that old axis first. If it fails, try the other. This
   retains counter-pass preference where both are safe; it does not force
   alternation over safety or retain an obsolete frozen target position.
3. Construct each fresh ingress at the unchanged distance `R + 4*U` behind
   the current target along the candidate axis. Require existing
   Safe_Attack_Segment for current->ingress and ingress->target, then the
   unchanged Find_Safe_Egress for that immediate pass, with the existing
   standard/minimum distances. No future REGROUP chain is checked.
4. These candidate checks are quiet. Failed per-frame probes emit no candidate
   matrix. On a valid candidate, emit ATTACK_TURNBACK_READY, then call the
   existing Start_CAP_Ingress with that candidate first. It repeats the normal
   full ingress/immediate-egress checks and emits the ordinary ingress/probe
   logs. An unexpected rejection takes the bounded abort path.
5. After reaching the actual ingress, normal target refresh, heading/target-plane
   checks, Start_Pass validation and finally Can_Fire/In_Range_Of govern the
   committed pass. READY itself is not PASS_COMMITTED or firing permission.

The actual aircraft need not already be `R + 4*U` away at READY. That distance
defines the **selected ingress waypoint**, which the aircraft must still fly
to. Requiring it immediately would exclude common cases where normal egress
is `R + 2*U`. The opposite candidate can require an unarmed transit past the
target toward its full ingress; normal ingress and pass checks still follow.
This is also why READY does not immediately convert current heading into a
firing pass.

## Bounds, watchdog and abort

H4 Native_Flight_Point, Inside_Array, Safe_Attack_Segment, Find_Safe_Egress
and Attack_Movement_Coord implementations are unchanged. TURNBACK can leave
In_Local_Radar, but raw array membership is not enough: outer In_Radar and
the existing technical guard remain required. Every actual attack movement
step still goes through H4's world-edge correction before coordinate commit.
No visible-edge clamp or direction-specific map branch is added.

At entry, compute one finite simulation-time budget:

```text
rotRaw    = max(1, PrimaryFacing.ROT.Get_Raw())
turnTicks = ceil(65536 / rotRaw)
v         = max(1, Full_Speed(a))
runup     = R + 4*U
travelTicks = ceil(2*runup / v)
budget    = turnTicks + travelTicks
deadline  = Frame + budget
```

Integer calculations use 64-bit intermediates and saturate to the int limit.
This allows one full facing revolution plus a full-ingress out-and-back travel
time. It is a conservative retry horizon derived from existing flight
semantics, not proof that every target is reachable. The deadline is set once;
moving targets or repeated unsuccessful geometric checks do not extend it.
Geometry decides READY; elapsed time only decides failure.

The deadline is checked both by Turnback_AI and the existing per-aircraft
CAP_AI entry. CAP_AI still runs while Controlled temporarily yields the Fly
process to native handling, so loss of custom movement does not pause the
watchdog. Existing target/ammo/parent invalidation is also respected.

| Abort reason | Action |
| --- | --- |
| TARGET_INVALID | Existing attack target is dead, inactive, limbo, airborne, out of the existing playable/leash rules, or absent; End_Attack resumes valid CAP |
| NO_AMMO | Ammo no longer positive; existing empty-ammo rearm/RTB path remains responsible for Ammo=0 |
| NO_VALID_REENTRY | Deadline expired, weapon range is unusable, or fresh ingress unexpectedly fails; existing End_Attack |
| WORLD_EDGE_STUCK | H4 corrected/rejected step retains the previous position; existing End_Attack through the TURNBACK abort wrapper |
| ESCORT_INVALID / CAP_INVALID | Existing parent validity checks failed; retain their existing cancel/return behavior; no new lifetime rule |

For an abort that resumes valid CAP, set the existing MissionClass::Timer to
the same derived retry horizon (using the currently available range, zero
when the target is gone). CAP movement/leg selection continues each frame,
but its normal mission threat scan waits for the timer. CAP_Leg and its
arrival branch do not reset that timer. This prevents immediate next-frame
reacquisition of the same failed setup. Explicit accepted player commands
retain their existing timer reset and can replace the order immediately.
No target blacklist or new acquisition algorithm is introduced.

## State, persistence and synchronization

No AircraftExtension/TypeExtension field or layout changes. The temporary
phase uses existing native serialized fields:

| Field during TURNBACK | Meaning |
| --- | --- |
| MissionClass::Status | TURNBACK=0x100 |
| TarCom / NavCom | Existing attack object reference |
| Fly::DestinationCoord | Live physical target position |
| Fly::HeadToCoord.X/Y | Previous outward axis, encoded as a one-cell direction vector; used only for candidate preference |
| Fly::HeadToCoord.Z | Absolute watchdog deadline in simulation frames |
| MissionClass::Timer after CAP abort | Existing acquisition retry delay |

HeadToCoord is phase-specific metadata in TURNBACK, **not a physical waypoint**
or target height. All arrival/plane interpretation is skipped for that phase.
Normal ingress/pass/clear/command helpers replace it on transition. Existing
Fly destination/heading code does not use it as a movement goal in TURNBACK.

The existing engine save/load already carries Mission Status/Timer and the
Fly object fields. Native Fly Load at `0x0049CD60` delegates to the base object
loader; its Get_Object_Size at `0x0049D3B0` returns 0x58. OpenTS
`fly.cpp::Serialize` explicitly includes DestinationCoord and HeadToCoord.
Native Locomotion Save/Load at `0x00506590` / `0x005065F0` transfers the object
size through the stream; reconstructed `saveload.cpp` also serializes Frame.
Thus no new serialization, swizzle, save-size, extension CRC layout or global
save-basis change is needed. The checked current basis remains **0x140000**.
Save/load during TURNBACK still needs local validation, including the existing
restoration of the simulation frame on which native timers depend.

All gameplay decisions use synchronized native state and deterministic helper
results. No developer Watch entry controls flight or timeout. One additional
Watch bool suppresses repeated TURNBACK ATTACK_WORLD_EDGE messages; it is
diagnostic-only, unsaved and cleared with existing watch/load handling.

## Logging

New developer-only messages are bounded state transitions:

- ATTACK_TURNBACK_BEGIN: once after both ordinary sides failed; includes
  sequence/run/previous phase, REGROUP_UNAVAILABLE, current position and bounds,
  target identity/position, facing, distance, Ammo and watchdog remaining.
- ATTACK_TURNBACK_READY: once when fresh geometry succeeds; includes selected
  direction, ingress, selected safe egress, passValid and nextRun. Ordinary
  NEXT_INGRESS_SELECTED, ATTACK_DIRECTION_PROBE and committed-pass events follow.
- ATTACK_TURNBACK_ABORT: once for the actual abort reason before the existing
  CAP/RTB transition. Invalid-parent handling logs before its existing cleanup.

ATTACK_REGROUP, ATTACK_EGRESS_COMPLETE, ATTACK_TARGET_PASSED, ATTACK_BREAKOFF,
AUTO_ATTACK_RESUME_CAP and all H2/H3/H4 diagnostics remain. ATTACK_WORLD_EDGE
keeps its existing behavior outside TURNBACK; during one TURNBACK only the
first correction is printed. No failed-candidate or turn-progress frame spam.
The full normal State formatter still supplies Escort context and movement
fields. HeadToCoord's metadata meaning in this phase is documented above.
