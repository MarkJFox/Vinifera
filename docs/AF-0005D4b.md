# AF-0005D4b — Ground Repair Cell on Native and Custom Foundations

Status: the user reports working CustomFoundation off-center ground repair with
BibShape, UnitReload and the Foundation=Custom editor marker. Native-foundation
support is implemented but not built or runtime-tested here; full acceptance remains pending. Baseline:
`f4cfed3b63a918599d31858147e59fdff8257b2d`. Contract:
[AF-0005D4a research](AF-0005D4a-Research.md), GO WITH RESTRICTIONS.

## Configuration

A compatible `UnitRepair=yes` building can use exactly one occupied service cell
inside either its native foundation or its active custom foundation.
`UnitRepairCell=X,Y` belongs to the
building's effective ArtINI/GraphicName section.

Native example (normal building registration and assets are unchanged):

```ini
; Rules
[GADEPT]
UnitRepair=yes
UnitReload=yes

; Art
[GADEPT]
Foundation=3x3
UnitRepairCell=1,2
; CustomFoundation is absent/no. BibShape remains compatible.
```

The native pair must exist in the actual Occupy_List, not just the 3x3 bounds.
No custom mask or custom dimensions are stored for this native configuration.

The existing foundation parser remains unchanged: the actual dimension keys are
`Foundation.X/Y`, with consecutive `Foundation.0..N` entries. The conceptual
`CustomWidth/CustomHeight/CustomFoundationCells` spellings in the task example
are not new aliases. `Foundation=Custom` may remain as an external map-editor
compatibility marker. The native TS parser is unchanged and converts that
unknown enum name to `nativeSize=0` / `BSIZE_11`. Zero alone is not a D4b role
conflict: an active valid contract supplies the effective occupied foundation.
If the contract is rejected, that native fallback may become visible. No code
restores an artificial 3x3 size, and no warning requests removal of the marker.
An ordinary native Foundation value can still be used when no marker is needed.

UnitReload=yes

[MYREPAIR]

Foundation.9=4,1
Foundation.10=0,2
Foundation.11=1,2
Foundation.12=2,2
Foundation.13=3,2
Foundation.14=4,2

The pair uses the existing strict decimal integer reader: whitespace around
integers/comma is accepted; missing components, extra components, floats,
hexadecimal notation, integer overflow, truncated strings and trailing garbage
are rejected. Coordinates are validated as integers before conversion to Cell.
The same strict parser runs in both foundation modes. No additional key is needed.

The service cell is relative to the building anchor, inside the effective
bounds and present in the occupied mask. Its world point is the cell center
with the building's Z. It is not a SHP offset, free halo cell or XYZ offset.
At runtime the helper also verifies map membership, this building's occupier,
no bridge at the service cell, and ground height equal to building Z.

## Eligibility and fallback

Both modes require the same validated ground repair role: UnitRepair,
Factory/ToBuild=RTTI_NONE and a valid occupied UnitRepairCell. Native mode uses
the real native Size, Width/Height and Occupy_List(false). The native bounded
mask scan follows the TSpp BuildingOccupyLists row capacity (24 Cells), stopping
at REFRESH_EOL; it never synthesizes a rectangular mask. The current PE's
Occupy_List at 0043FED0 returns the native OccupyList or an empty EOL list;
BuildingType Read_INI selects the Size-specific 24-Cell row.

Custom mode additionally requires enabled/valid CustomFoundation, canonical
bounds/mask and cardinal connectivity. The existing occupied-cell validation
and connected-mask restriction are unchanged. Native Size remains an in-range
fallback enum (including BSIZE_11 / zero from the editor marker).

UnitReload may be yes or no, and BibShape may be present or absent. Neither
activates UnitRepairCell. BibShape is visual only: its pixels do not participate
in occupation, passability, service-cell validation, Cell_Building or exit search.
IsBibbed remains forbidden and is independent of BibShape.

The existing role exclusions remain: Aircraft/Helipad roles, HoverPad,
Refinery/Weeder/DockUnload, factories/CY/barracks, Hospital/Armory, FreeUnit,
Dock lists, aircraft MultiDock, walls/gates/fences/plugs/tiles/overlays/upgrades,
deploy/mobile-building contracts, special placement/naval roles and reverse
Dock/DeploysInto references. UnitRepair plus UnitReload is compatible; UnitRepair
plus Aircraft/Helipad/Factory infrastructure is not. The D3b helipad exception
and D3/D3c Aircraft eligibility are unchanged.

In custom mode, a missing/invalid repair cell or role rejects the entire custom foundation,
clears the repair-cell fields and retains the existing native Foundation
fallback. It never publishes a large repair mask with an implicit center
service point.

In native mode, absence of the optional key preserves native center repair.
A malformed, out-of-range, unoccupied or role-incompatible explicit point is
ignored with a DeveloperMode warning: Set remains false and the point=(0,0).
Native Size, OccupyList, dimensions, placement and center-repair fallback are
not changed. This does not activate a custom foundation or a custom exit.

| Rejection | Meaning |
| --- | --- |
| MALFORMED_CELL | Missing, malformed, overflowed or truncated pair |
| OUT_OF_RANGE | Pair outside effective width/height |
| NOT_OCCUPIED | In bounds but absent from occupied mask |
| ROLE_CONFLICT | Incompatible role, IsBibbed or conflicting reference |
| DISCONNECTED_MASK | Occupied mask has separate cardinal components |

### GADEPT role compatibility

The initial rejection log identified ROLE_CONFLICT. Five subsequent config runs
reported by the user isolate the old UnitReload and BibShape exclusions; they
also establish that Foundation=Custom does not prevent D4b acceptance. Earlier
advice to remove that marker is superseded by its required editor compatibility.
No Rules/Art file or native foundation parser is changed by this role fix.

Previously Custom_Unit_Repair_Role_Error rejected IsCanUnitReload and a non-null
BibShape. The final scope validator independently rejected UnitReload outside
the Aircraft-helipad role and a BibShape pointer or nonempty Art key outside
that role. Both layers now allow those properties only after the D4b ground
role, connected mask and occupied repair cell pass. IsBibbed and all unrelated
conflicts remain excluded. Post-load validation uses the same updated role
helper; no additional saved flag is needed.

Ground visitors still require the existing UnitClass/Drive runtime checks,
UnitRepair and valid configuration for the selected foundation mode, plus the relevant Radio/NavCom
relationship. All current service consumers pass a concrete visitor to the
point helper. Aircraft cannot pass that visitor predicate and are never sent
to UnitRepairCell. The existing custom-foundation RX entry gate still excludes
unsupported visitors from that contract. Native-mode admission remains native;
unsupported visitors do not use the explicit point or its coordinate adapters.
A bare UnitReload flag never activates D4b.
Native UnitReload code, D3/D3b/D3c1/D3c2 and the ten D4b runtime hooks are
unchanged. This compatibility change adds neither Aircraft service nor ground
reload logic; UnitRepairCell remains exclusively a Ground UnitRepair point.

### Native-foundation extension

The original gap was deliberate gating, not a new runtime-hook failure:
Finalize_Custom_Foundation returned before reading UnitRepairCell whenever
CustomFoundation was disabled. The old service eligibility also required
IsCustomFoundationEnabled && IsCustomFoundationValid; Load required a custom
mask for every saved point. Those requirements now apply only to custom mode.

Is_Unit_Repair_Cell_Eligible represents a configured point in either mode.
Is_Custom_Foundation_Unit_Repair_Eligible additionally requires the active
custom mask and remains the Find_Exit_Cell/custom-exit guard. The shared
Building point helper uses the general predicate. RX DOCKING already consumes
that helper, and IM_IN diagnostics now require its validated current contact.
The custom-only RX admission guard stays custom-only, preserving native Radio
and UnitReload admission semantics on native foundations. No new hook,
trampoline, address or ABI is added.
Foot destination, both Drive paths, PCP arrival, Guard, Repair INITIAL/IDLE,
RX DOCKING, Can_Demolish, Sell, Capture and AI Zone reuse the same helper.

Custom-mode configuration trace (native mode branches after mask-request reset
to the same pair/role parser and native mask validation):

| Stage | State and outcome |
| --- | --- |
| Constructor/defaults | Enabled/Valid/Set=false, bounds/count=0, repair cell=(0,0); native flags are not yet final. |
| Native BuildingType Read_INI/Art | Native UnitRepair/UnitReload and Size are read before extension finalization. Effective GraphicName selects Art; unknown native Foundation text may become Size=BSIZE_11. |
| BuildingTypeExt Read_INI | Reads existing extension/Aircraft settings and fetches images. It does not publish D4b or parse/reset UnitRepairCell. |
| Custom foundation parser | Finalization resets owned custom state and rereads that same effective Art section. For the supplied mask: Enabled=true, bounds=5x5, count=25, Valid=false pending scope, Set=false, point=(0,0). |
| Ground role validation | GADEPT may retain UnitRepair=true, UnitReload=true and BibShape. IsBibbed=false and the remaining role guards are still required. |
| Connectivity and repair-cell parser | After role success, the complete canonical occupied mask is available. Strict pair/bounds/occupation checks set Set=true and point=(1,1); (1,3) is also occupied in this mask. |
| Complete scope validation | The validated ground_repair predicate exempts only this contract from the old UnitRepair/UnitReload/BibShape exclusions. IsBibbed and the other exclusions remain; only after success is Valid=true published. |
| Fixups | Rules fixups run after Objects; the existing fixups do not reset D4b fields or rewrite Size. Aircraft finalization follows the foundation pass and does not change this count=1 ground role. |

With no CustomFoundation, an explicit UnitRepairCell is now parsed and validated
against native occupation. Without the key the native path remains unchanged.
An invalid native point disables only the optional point. An invalid requested
custom contract still falls back as a whole. No halo cells are admitted in either mode.

The user now reports that the real custom GADEPT combination with BibShape,
UnitReload and the editor marker accepts an off-center point and repairs a
ground visitor there. Keep that setup for the custom regression in Native D
below. Native support and the remaining A–T cases are not yet confirmed.

The existing BuildingTypeExt fields are `bool CustomUnitRepairCellSet`
(default false) and `Cell CustomUnitRepairCell` (default 0,0). There are no
new BuildingExt/UnitExt fields, saved pointers, visitors, slots or timers.
Their historical names now also represent native-foundation points. No rename,
field, layout change or additional saved mode is needed: the existing custom
foundation flags distinguish the two modes.

## Supported visitors and helpers

Supported visitors are active, alive, non-limbo UnitClass vehicles with Wheel
or Track speed, Normal/Crusher/Destroyer terrestrial MovementZone, configured
Drive CLSID `4A582741-9839-11D1-B709-00A024DDAFD1`, and that same actual
runtime CLSID. IPersistStream QueryInterface/GetClassID checks the real
locomotor before the typed Drive cast; a piggybacked locomotor is excluded.

Aircraft, Infantry, Hover, Subterranean, train/tunnel, naval/amphibious,
Carryall-toted, falling/sinking/bridge, teleport/other locomotors and special
non-vehicle/spawn/missile units are excluded. Loaded transports are excluded;
an empty otherwise ordinary Drive transport can qualify. CurrentTube and
an Aircraft radio partner also exclude temporary special travel states.

`BuildingClassExtension::Custom_Unit_Repair_Coord` is the shared read-only
point helper. It checks the type contract, optional visitor and map point.
The Contact helper requires reciprocal native Radio; the Nav helper additionally
requires Unit NavCom equal to that building. None changes Radio, mission,
power, reservation or health. The AI query uses the same point without requiring
an already established reservation.

For custom foundations, the existing Building RX replacement rejects unsupported
D4b service entrants for CAN_LOAD/HELLO/DOCKING/IM_IN; IM_IN also requires the reciprocal contact.
The native construction-yard HELLO is preserved as a construction contact.
Native foundations retain native admission and Radio semantics; only supported
Ground UnitRepair visitors use the explicit point. Normal repair buildings
without a point and other existing RX roles retain their paths.

## Native service lifecycle

Reservation remains exactly `Unit.Radio <-> Building.Radio` through native
scalar HELLO. CAN_LOAD does not reserve. There is no GroundVisitor array,
second owner, first-free selection, queue or parallel service. A second
visitor must follow the existing native refusal/retry behavior.

The local adapters replace only the building target point: Foot destination,
Drive Process and While_Moving, Unit PCP arrival, Building Guard,
Mission_Repair INITIAL/IDLE, RX DOCKING, Can_Demolish, Sell/Deconstruction,
Capture and the Find_Docking_Bay zone endpoint. Visitor center, native
identity/NavCom checks, exact arrival cell, IM_IN and locomotor Power_Off
remain native. The owner's own Z call at 0x0047F8A7 is untouched.

Native repair State/Stage, INITIAL/IDLE/DURING, tolerance including <150,
URepairRate, NEED_TO_MOVE, Sleep, power and NavCom clear are retained.
Strength, Repair_Cost, Repair_Step, House money and REPAIR responses
ROGER/ALL_DONE/CANT/NEGATIVE remain in the native Techno receiver.
There is no new health increment or D3c1 reload timer.

Unit Can_Demolish, building Sell and Capture use the same actual service point
only for the valid current contact; sell choice, ownership, RunAway and
OVER_OUT policy stay native. Manual Move/Stop removes the native NavCom/contact
conditions; adapters do not issue orders or pull an aborted visitor back.
EMP, IsOn, House power, locomotor power and IonStorm policy are unchanged.
Destruction/detach/limbo rely on existing native cleanup; no new peer reference
needs clearing. No artificial HELLO-to-TETHER protocol is added.

There is no global Center_Coord or Docking_Coord override and no D4b
Can_Enter_Cell hook. Native UnitClass::Can_Enter_Cell already admits its
own UnitRepair radio-partner building on occupied cells.

## Departure and AI

Native foundations keep native Find_Exit_Cell and ExitList[Size], along with
the existing Rally/Archive precedence. A native UnitRepairCell never selects
the custom outer-exit path. Its wrapper and the exit helper both require the
custom-mode predicate.

For custom foundations, the existing Find_Exit_Cell adapter handles D4b before
its unchanged D1 infantry branch. It searches the outer effective bounding-box ring deterministically:
increasing X, top then bottom; increasing Y, left then right. The chosen point
must be in radar, outside the occupied mask/bounds, not occupied by this
building, and visitor Can_Enter_Cell must return MOVE_OK. No random draw or
native small-size ExitList is used for this role.

If no candidate succeeds, the result is CELL_NONE. Existing caller retry/contact
handling remains responsible; no fake success, teleport, forced OVER_OUT or
occupation bypass occurs. ArchiveTarget/Rally precedence remains unchanged;
only the Find_Exit_Cell fallback is replaced. Internal obstacles still use
native pathfinding; D4b does not guarantee a route through blocked terrain.

Find_Docking_Bay uses UnitRepairCell for the ground zone endpoint. House,
alliance, type identity, CAN_LOAD, Radio availability, MovementZone, leader and
search policy remain native. Ranking at 0x00637FF2 intentionally still uses
native building distance. Automatic MISSION_REPAIR search still depends on
the configured Rule->RepairBay type; arbitrary UnitRepair buildings are not
added to a new AI strategy.

`references/ts-patches/input.dat`, SHA-256
`BC4C15D826AAEBEACE3FEC6360EB687E5662CBA8745605093254931DCDB3AE1B`.
Original instructions/register provenance were re-read before installation
and checked again after editing. Existing source hooks were checked for overlap.
No reference file was modified.

All addresses below are hexadecimal. The bytes are the displaced window.
Every new hook falls back with return 0: execute the original replay/trampoline.

## Save, NoInit, CRC and diagnostics

D4b's save basis remains 0x1A0000 (the original bump was from 0x190000), before
the project's normal size/debug additions. Native support reuses the same raw
fields and makes no further version/layout change or migration.

The normal constructor and INI reset initialize false/(0,0). The unchanged
NoInit constructor has no new member initializers and preserves the loaded
POD. The existing raw Get_Object_Size/Save chain includes both fields.
Load checks owned canonical POD and fails closed on an invalid stored point;
it never dereferences unswizzled owners/peers. After the load's final
SwizzleManager.Reset, the type-only validator rechecks membership, full role,
mode-specific mask/occupancy and custom connectivity. For a native saved point,
early Load checks only owned coordinate limits; actual native dimensions and
occupation are verified after swizzle. No Building/Unit post-swizzle structure or
new swizzle pointer registration is introduced.

Custom_Foundation_CRC appends the domain 0x47525054 (GRPT), Set, X and Y
when the explicit repair point is set. Existing foundation Enabled/Valid and
mask hashing remain; absence retains the old optional-field stream.
Object_CRC and the existing cached FRAMESYNC config CRC both consume it.
The tagged Set/X/Y/domain payload is unchanged. The only FRAMESYNC integration
change is including types with CustomUnitRepairCellSet in the existing config
collection predicate, even when CustomFoundation and Aircraft MultiDock are off.
Without this inclusion, native points would be missing from that config checksum.
No pointers, world coordinates or building-instance values are hashed.
Existing config/reset/load invalidation also invalidates this derived CRC.

All new [GREPAIR] diagnostics explicitly require Vinifera_DeveloperMode:
CONFIG_REQUEST and CONFIG_ACCEPTED / CONFIG_REJECTED per finalization pass,
with validator, effective section and relevant role/native-size values on rejection.
CONFIG_REQUEST includes foundationMode=NATIVE/CUSTOM, UnitRepair, UnitReload,
loaded BibShape, IsBibbed, nativeSize, customFoundation, explicitly named custom
bounds/count and the requested UnitRepairCell. CONFIG_ACCEPTED identifies the
mode and point (native width/height for NATIVE). Invalid native points emit
CONFIG_IGNORED with their reason; custom rejection remains CONFIG_REJECTED.
IM_IN traces the native entry message and EXIT_SELECTED a departure selection. There are no
Drive/frame logs or repeated EXIT_BLOCKED logs in retry loops. No separate
SERVICE_BEGIN trace or changes to native service Stage are added.
